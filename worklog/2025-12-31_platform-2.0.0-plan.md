# dts-platform 2.0.0 后续完善计划（基于技术协议 + 当前代码扫描）

更新时间：2025-12-31  
范围：`source/dts-platform` + `source/dts-platform-webapp`（不含实施服务；外部 BI/ETL 以“链接/对接”方式为主）  
目标：把已添加的 2.0.0 菜单“占坑”能力补齐为**可用业务闭环**；按当前优先级顺序推进：**数据标准 → 数据资产&元数据 → 指标管理 → 质量巡检 → 安全策略 → ETL 对接入口**（可视化已通过河图+Metabase落地，不扩展 Superset）。

## 0. 已完成（代码已落地）

更新时间：2026-01-02

### 0.1 数据标准（主题域化 + 导入）
- 数据标准的 `domain` 作为“主题域”（如财务/库存/项目…），不再绑定登录人的部门；列表筛选与详情编辑按主题域使用。
- 新增 CSV 模板下载与 CSV 导入（Excel 可另存为 CSV），按 `code` 做 upsert（存在则更新，不存在则新增）。
- `security_level` 支持：数字/中文/字符串码混用，统一解析到 `dts-common` 的 `SecurityLevelCatalog`；对外显示用中文。

### 0.2 数据资产（行级安全字段映射）
- 数据集支持配置“数据密级字段 + 部门字段”的**字段角色映射**（不同业务系统字段名不统一时可人工覆盖）。
- 行过滤同时生效：
  - 数据密级：支持**数值字段（0~3）**与字符串字段两种模式；按“人员密级可见上限”生成 `<=` 或枚举集合过滤。
  - 部门：按登录人部门（`dept_code`）过滤。

### 0.3 审计（中文可读）
- 新增并统一补齐审计动作码（中文显示）：`CATALOG_SECURITY_MAPPING_VIEW` / `CATALOG_SECURITY_MAPPING_EDIT` / `MODELING_STANDARD_LIST` / `MODELING_STANDARD_IMPORT`。

### 0.7 数据规划管理（版本 + 评审 + 发布）
- 数据规划版本历史：`GET /api/modeling/plans/{id}/versions`。
- 数据规划发布：`POST /api/modeling/plans/{id}/publish`（同时写入版本快照）。
- 评审流程（轻量）：`GET /api/modeling/plans/{id}/reviews`、`POST /api/modeling/plans/{id}/reviews/submit`、`POST /api/modeling/plans/{id}/reviews/{reviewId}/approve|reject`。

### 0.8 指标口径与术语库（版本 + 评审 + 发布 + 引用）
- 术语版本历史：`GET /api/modeling/glossary/terms/{id}/versions`。
- 术语发布：`POST /api/modeling/glossary/terms/{id}/publish`（同时写入版本快照）。
- 评审流程（轻量）：`GET /api/modeling/glossary/terms/{id}/reviews`、`POST /api/modeling/glossary/terms/{id}/reviews/submit`、`POST /api/modeling/glossary/terms/{id}/reviews/{reviewId}/approve|reject`。
- 引用关系（轻量检索）：`GET /api/modeling/glossary/terms/{id}/references`（返回引用该术语的数据标准/指标清单）。

### 0.9 数据模型规范与模板（版本 + 发布 + 预置模板）
- 模型模板版本历史：`GET /api/modeling/templates/{id}/versions`。
- 模型模板发布：`POST /api/modeling/templates/{id}/publish`（同时写入版本快照）。
- 预置 ODS/DWD/DWS/ADS 模板（Liquibase Seed，默认 `ACTIVE` + `v1`）。

### 0.10 数据集成与存储（2.x：星环为主，平台统一入口）
- 平台提供“外部平台入口配置”（用于星环/TDH 统一跳转入口；支持启用/停用/备注，写审计）：
  - `GET /api/infra/external-links`
  - `GET /api/infra/external-links/{entryKey}`
  - `POST /api/infra/external-links/{entryKey}/visit`（打开入口前写审计，作为“访问兜底”）
  - `GET /api/infra/external-links/{entryKey}/check`（连通性检查：HTTP/耗时，用于运维排障）
  - `GET /api/infra/external-links/{entryKey}/status`（可选：状态回显；拉取一个轻量 JSON 状态接口并显示，用于“最近运行态/失败原因”只读回显）
  - `PUT /api/infra/external-links/{entryKey}`
  - `DELETE /api/infra/external-links/{entryKey}`
- 平台提供“外部平台作业/任务登记”（仅登记+审计兜底，不执行；用于把 2.1~2.6 的关键作业/任务与星环页面建立可追溯链接）：
  - `GET /api/infra/external-artifacts`（支持 `entryKey/type/keyword/enabledOnly`）
  - `GET /api/infra/external-artifacts/{id}`
  - `POST /api/infra/external-artifacts`
  - `PUT /api/infra/external-artifacts/{id}`
  - `DELETE /api/infra/external-artifacts/{id}`（禁用）
  - `DELETE /api/infra/external-artifacts/{id}/purge`（物理删除）
- 平台提供“数据交换文件台账”（只记录批次/文件状态，用于 2.2 的审计留痕与运维排查）：
  - `GET /api/infra/exchange-files`（支持 `entryKey/status/keyword/enabledOnly/limit`）
  - `GET /api/infra/exchange-files/{id}`
  - `POST /api/infra/exchange-files`
  - `PUT /api/infra/exchange-files/{id}`
  - `DELETE /api/infra/exchange-files/{id}`（禁用）
- 已预置 6 个 ETL 模块入口（默认 `enabled=false`，需数据管理员填写 URL 后启用）：
  - `EXPLORE_ETL_ADAPTERS`（2.1 多源集成适配器）
  - `EXPLORE_ETL_FILE_EXCHANGE`（2.2 数据交换与文件接入）
  - `EXPLORE_ETL_TRANSFORM`（2.3 数据加工与转换）
  - `EXPLORE_ETL_ORCHESTRATION`（2.4 流程编排与作业管理）
  - `EXPLORE_ETL_WAREHOUSE_LAYERS`（2.5 数仓分层管理）
  - `EXPLORE_ETL_RECONCILIATION`（2.6 装载对账校验）

## 2. 总体落地策略（适配研究所小团队场景）

### 2.1 产品策略
- **指标管理必须闭环**：指标字典/维度字典/计算规则/发布/引用检查/变更留痕，形成“从定义到使用”的主线。
- **元数据/血缘先做轻量底座**：以现有 catalog 表为核心，优先“自动采集 + 手工补录 + 变更历史 + 影响提示”。
- **质量闭环优先“可用”**：规则 → 计划（定时/手动） → 运行 → 发现问题 → 指派/处理 → 复核/关闭。
- **ETL 不自研**：以星环为主，平台侧只做“对接入口 + 配置 + 运行态/结果态回显（可选）”。
- **可视化不再扩 Superset**：河图做大屏设计，Metabase 做自助分析；平台侧负责“链接管理 + 过滤展示 + 审计兜底”。

### 2.2 权限与密级（跨模块共用）
- 统一采用“字符串码 + 数字等级”的内部标准（前端显示中文，后端统一码值/数字比较）。
- 人员密级：`GENERAL(0)`、`IMPORTANT(1)`、`CORE(2)`（系统仅到 CORE）
- 数据密级：`PUBLIC(0)`、`INTERNAL(1)`、`SECRET(2)`、`CONFIDENTIAL(3)`
- 访问规则（按你们最新口径）：  
  - 一般人员：可看 `PUBLIC/INTERNAL/SECRET`  
  - 重要人员：可看 `CONFIDENTIAL`（以及更低）  
  - 核心人员：理论可看“绝密”，但系统数据密级只到 `CONFIDENTIAL`，所以核心 == 重要 的数据访问上限

> 本计划不处理旧数据兼容；统一以新标准推进（旧值在导入/采集时做归一化）。

### 2.2.1 口径确认（已与甲方/产品侧对齐）
- 数据标准 Excel 导入模板字段：`code/name/domain/scope/owner/tags/description/示例/取值范围`（先按此最小集落地）
- 标签（tag）：允许自由输入（不强制字典）
- 指标分组：按“主题域”分组（例如财务/库存/项目…），用于指标检索与导航
- 质量问题单默认责任人：所级数据管理员（可能多名，通过 admin 接口查询“数据管理员列表”并用于指派）
- 行过滤必须落地两类条件：
  - 数据密级：基于登录人自身密级（精准匹配/不高于自身密级）
  - 部门：基于登录人所属部门（仅显示本部门范围数据），业务表中的部门字段统一为 `dept_code`
- 字段命名不统一：各业务系统的“数据密级字段/部门字段”命名不一致，需要平台侧提供**可配置映射**（按数据集/表配置），而不是仅靠固定字段名猜测。
- 星环对接：先做纯 URL 跳转（不做 token/SSO 参数透传）

### 2.3 业界功能对标（Databricks / Microsoft / Snowflake / 星环等）与取舍
目标：把业界产品的“通用能力模型”拆解成**本项目可落地的功能清单**，用于指导后续编码；原则是“轻量闭环优先、低运维成本优先”。

#### 2.3.1 横向通用能力（所有模块共用）
对标 common patterns（Databricks、Microsoft、Snowflake、星环/滴普等产品的“好用”共性）：
1) **统一检索与筛选**
   - 全局搜索（名称/编码/描述/标签/负责人），支持 facet（域/部门/密级/状态/标签/更新时间）。
2) **版本与状态机**
   - 任何治理对象（标准/指标/规则/策略）都要：草稿 -> 评审/校验 -> 发布 -> 废止/归档，并能回溯版本与变更说明。
3) **责任与协作**
   - 负责人（owner/steward）、责任部门；质量问题/审批支持处理记录（先轻量）。
4) **影响分析（轻量）**
   - 先不追求“全自动字段级血缘”，但必须能记录引用关系：指标引用数据集/字段；报表引用指标/数据集；规则/策略作用范围。
5) **审计与留痕**
   - 创建/编辑/发布/废止/删除/授权/策略变更/触发任务都要写审计；页面侧至少能按时间/对象/操作者过滤。

#### 2.3.2 数据标准（模型与标准）
对标：Purview/Unity Catalog 的“术语+标准”、星环/滴普的“标准库与落地检查”。
- 最小闭环：草拟（手工/导入）→提交评审→发布→影响提示→废止/退役
- 常见基本功能（按优先级）
  1) 标准条目（编码、名称、业务域/适用范围、责任人/责任部门、标签、示例、状态机）
  2) 版本快照与变更摘要（口径冻结、版本对比可后置）
  3) Excel 导入导出（模板固定、错误回写、导入批次审计）
  4) 落地提示（被哪些数据集字段/指标/质量规则引用；先提示不强阻断）
  5) 标准落地检查（后置：对照元数据字段命名/类型/枚举值合规）

#### 2.3.3 数据资产目录（数据资产）
对标：Unity Catalog / Purview 的“资产门户”、Snowflake 的“对象发现+标签”。
- 最小闭环：采集生成清单→补录负责人/说明/标签/密级→检索与被使用→变更留痕
- 常见基本功能（按优先级）
  1) 资产发现：搜索 + facet（域/标签/密级/负责人/更新时间），可选收藏
  2) 资产详情聚合：基本信息 + Schema + 标签/分类 + 血缘 + 生命周期 + 质量概览 + 权限概览
  3) 认证/重要性（轻量）：管理员可打“推荐/官方认证”，用于业务筛选可信资产
  4) 热度/使用统计（轻量）：基于审计聚合最近 7/30 天访问/查询/预览次数、被引用次数（指标/报表/查询模板）

#### 2.3.4 元数据采集与维护（数据资产）
对标：Purview 扫描、OpenMetadata/Amundsen 的“采集+补录+变更历史”。
- 最小闭环：触发/定时采集→看运行状态与差异→补录业务元数据→变更回溯
- 常见基本功能（按优先级）
  1) 采集运行可观测：运行历史（开始/结束/耗时/成功失败）、差异统计（新增/变更/删除）
  2) Schema 漂移提示（轻量）：字段新增/删除/类型变化的变更事件与详情页提示
  3) 字段级业务元数据：中文名/口径/示例/备注/敏感标记；批量编辑后置

#### 2.3.5 指标管理（治理与质量）
对标：语义层/指标平台（Databricks SQL/Metric Store 思路、Power BI 语义模型、国内厂商的“指标字典+口径治理”）。
- 最小闭环：定义指标→绑定数据集/维度→配置计算规则→校验→发布→被使用→变更影响提示
- 常见基本功能（按优先级）
  0) 主题域分组（你们口径）
     - 指标必须归属一个主题域（财务/库存/项目…），并作为列表筛选与导航树的第一层分组。
  1) 口径治理：责任人、口径说明、版本对比（后置）、变更必须有 changeSummary
  2) 可用性保障：SQL 校验（语法/字段存在/权限/行数限制）、示例 SQL 一键复制
  3) 发布一致性校验：发布前检查引用清单并提示影响；发布后口径冻结（改动走新版本）
  4) 轻量语义层增强（后置）：参数化指标、维度下钻模板、指标分组视图（不替代外部 BI）

#### 2.3.6 质量巡检（治理与质量）
对标：Great Expectations/Databricks expectations、Purview 的 data quality 视角、国内厂商的“规则+任务+闭环”。
- 最小闭环：维护规则→建计划→自动运行→失败生成问题→处理/复核/关闭→趋势统计
- 常见基本功能（按优先级）
  1) 规则库：完整性/一致性/唯一性/范围/枚举/正则等（采样与剖析后置）
  2) 调度与历史：执行窗口、运行趋势、最近失败原因（失败重试先手动）
  3) 问题闭环：指派、处理记录、证据、关闭原因；按数据集/规则/责任人统计

#### 2.3.7 安全策略中心（安全合规）
对标：Snowflake（tag + masking + row access policy + access history）、Unity Catalog 权限、国内厂商“密级+脱敏+授权矩阵”。
- 最小闭环：标注密级/分类→授权→配置行过滤/脱敏→预览与解释→审计追溯
- 常见基本功能（按优先级）
  1) 策略可解释：“为什么看不到/为什么被脱敏”，展示命中的授权/策略/密级判断
  2) 策略预览：脱敏 preview（现有接口）；行过滤 preview（建议补齐轻量模拟接口）
  3) 最小权限：授权审批后置，但授权/策略变更必须留痕与可追溯

> 强制落地（你们口径）：行过滤至少支持两类条件同时生效：按“数据密级（<= 人员密级）”与“部门（= 登录人部门）”。
>
> 设计约束：字段名不统一，因此行过滤不能写死 `data_level/dept_code`；需要“字段角色映射（Field Role Mapping）”配置能力，并支持自动识别 + 人工覆盖。

#### 2.3.8 ETL 对接入口（数据开发）
对标：平台作为“统一入口/编目与可观测聚合”，ETL 引擎交给星环（客户现状）。
- 最小闭环：管理员配置入口→业务一键进入→（可选）回看关键作业运行态→失败跳转定位
- 常见基本功能（按优先级）
  1) 统一入口：可配置跳转 URL；支持按环境（dev/prod）配置
  2) 轻量可观测（可选）：只读拉取作业清单、最近运行、失败原因、SLA（取决于星环 API）

## 3. 分阶段计划（建议顺序 + 验收口径）

### Phase 0：收敛标准/补齐底座（1~2 周）
1) **统一密级定义与归一化入口**
   - 后端：抽取统一的 `SecurityLevel`/`Classification` 定义与转换（字符串码/中文/数字互转），并集中在 `dts-common` 或 `dts-platform` 的单一位置供全模块引用。
   - 前端：统一使用同一套 `normalizeClassification()`/显示文案，避免各页面各写一套映射。
   - 验收：同一字段在“资产列表/标准/指标/查询预览/可视化链接过滤”显示一致；接口入参支持数字/中文混写并归一化。
2) **菜单与路由对齐检查**
   - 校验 portal_menu metadata 的 `sectionKey/entryKey` 是否完整；确认占坑菜单都能进入对应页面（至少显示“建设中”提示）。
3) **审计覆盖检查（兜底）**
   - 以“资产/指标/质量/报表链接”为样板：保证增删改查 + 关键动作（触发采集/触发质量运行/点击报表）都有审计记录。

### Phase 1：数据标准闭环（1~2 周）
目标：让“数据标准”从 CRUD 升级为可发布、可追溯、可复用（支撑资产/指标/质量）。
1) **标准版本与发布流程完善**
   - 明确状态机：`DRAFT -> PUBLISHED -> ARCHIVED/DEPRECATED`（与现有接口对齐）。
   - 发布/废止对外提示：影响范围（引用到的数据集/指标/质量规则）先做轻量联动（仅记录引用关系，先不强阻断）。
2) **导入/校验能力补齐（轻量）**
   - Excel 导入（模板固定、批量校验、错误回写），并记录导入批次与审计。
3) **附件/加密与健康检查**
   - 复核 `DataStandardSettingsResource` 的加密 key/存储设置可用性；补齐“管理员可见”的配置校验与提示文案。
4) **验收**
   - 能导入一批标准；能发布/废止；能查看版本/变更说明；关键操作写审计。

### Phase 2：数据资产 & 元数据闭环（2~4 周）
目标：让“数据资产目录/元数据采集/生命周期/血缘入口”形成可持续维护的闭环，并能为后续指标/质量提供支撑。
1) **数据资产目录（增强可用性）**
   - 资产分类/标签/负责人/使用说明的补录与审计留痕；按部门/密级/标签筛选；使用统计（可先做点击/访问审计聚合）。
   - 实现细节建议：列表页统计口径以“当前用户可见资产”为准（ABAC/RBAC 后再分页，适配小规模数据集数量场景）。
2) **元数据采集与维护**
   - `CatalogSyncResource` 已支持触发采集：补齐定时调度、运行历史、失败重试、差异统计（新增/变更/删除）。
   - 字段级业务元数据维护（注释/标签/敏感标签）与变更历史展示（先做轻量 history 表或 audit 辅助记录）。
3) **生命周期管理**
   - 基于 `LifecyclePage` 对接字段：补齐到期提醒（站内通知/待办占位）、归档/销毁审批先不做强流程（先记录状态变更与审计）。
4) **自动血缘入口准备**
   - 先把“手工血缘 + 自动血缘”规则定好（AUTO_* 不可直接删，支持 `force=true`），为后续 Phase 4 打底。
5) **验收**
   - 能稳定采集、看状态、可回溯；资产可被补录与检索；生命周期字段能维护并留痕。

### Phase 3：指标管理闭环（2~3 周）
目标：让“指标”可定义、可校验、可发布、可追溯，并能服务报表/大屏与查询。
1) **指标字典完善**
   - 指标分类体系（原子/派生/复合）、版本管理（版本号 + 变更说明）、责任人/部门、数据密级、引用关系（报表/看板/查询模板）。
2) **维度体系完善**
   - 维度层级（父子）、编码规则、字典项维护；维度与指标绑定（用于生成示例 SQL/下钻筛选）。
3) **计算规则最小可用**
   - 计算规则以 SQL 为主（已具备编辑/预览），补齐：校验（语法/字段存在/权限）、示例生成、运行资源限制（limit/timeout）、结果落库（可选）。
4) **发布与一致性校验**
   - 发布状态机：`DRAFT -> PUBLISHED -> DEPRECATED`
   - 一致性校验：发布前检查“被引用对象列表（报表/查询模板/指标间引用）”并给出影响提示。
5) **验收**
   - 业务用户：能查到已发布指标、看口径、复制 SQL 模板；数据管理员：能发布/废止并看到影响提示。

### Phase 4：质量巡检与问题闭环（2~4 周）
目标：从“规则+执行”升级为“计划+闭环”。
1) **巡检计划（QualityTasks）**
   - 计划：绑定规则集合/数据集集合、执行频率、执行窗口、通知人。
2) **运行与问题（QualityIssues）**
   - 每次运行生成 run + issue（当失败/阈值越界），issue 支持：指派、处理记录、复核、关闭。
3) **验收**
   - 能按计划自动触发；失败会生成问题单；问题单可关闭并留痕。

### Phase 5：安全策略中心最小可用（2~4 周）
目标：把已有的“脱敏规则/行过滤规则/数据集授权”做成可管理、可审计、可解释的策略中心。
1) **访问权限矩阵（建议落地为“数据集授权 + 行列策略汇总视图”）**
   - 汇总展示：按数据集查看 grants / row-filter / masking 的生效情况；按部门/用户查看可见资产列表。
2) **脱敏策略中心（接入现有 CatalogResource API）**
   - 用真实接口替换静态原型页：维护 `masking-rules`，提供 preview 与策略生效范围解释。
3) **安全总览页（替换静态数据）**
   - 从 catalog 中按密级聚合资产数；展示最近高风险操作审计摘要（若审计查询 API 暂缺，可先展示“平台侧已记录”的统计）。
4) **日志审计与报表**
   - 若平台侧不直接存审计库：通过 dts-admin 提供审计查询 API，并在平台侧仅做展示。
5) **验收**
   - 能创建/编辑/预览脱敏规则；能配置行过滤规则；权限矩阵能解释“为什么看不到某资产”。

### Phase 6：ETL（星环）对接入口（1~2 周）
目标：平台侧提供“统一入口”，但不做 ETL 引擎。
1) **对接方式（推荐 1 + 2）**
   - 方式 1：菜单直接跳转星环（可配置 URL + SSO/Token 转发可选）
   - 方式 2（可选）：只读拉取作业列表/最近运行状态/失败原因，展示在平台内（不负责创建/编排）
2) **验收**
   - 业务人员从平台能快速进入星环；管理员能看到关键作业运行态（若启用方式 2）。

## 4. 模块落地 checklist（按模块拆解 PR）

> 下面按“数据标准 → 数据资产&元数据 → 指标管理 → 质量巡检 → 安全策略 → ETL 对接入口”的优先级，把每个模块拆成可执行的 PR 颗粒度（DB/后端/前端/验收口径）。  
> 说明：本清单面向“轻量闭环”，不追求一次性做大而全。

### 4.0 已有模块增强（非占坑页面，但需要补齐闭环）

#### 4.0.1 数据标准（DataStandardsPage / DataStandardDetailPage）
目标：从“CRUD”升级为“可评审、可发布、可导入、可落地提示”的闭环。
1) 后端
   - 导入：新增 `/api/modeling/standards/import`（上传 Excel -> 校验 -> 写入 -> 返回错误明细/导入批次 id）
     - 模板字段按口径：`code/name/domain/scope/owner/tags/description/示例/取值范围`
   - 引用关系（轻量）：新增 `modeling_standard_reference`（可先只记录：datasetId/tableId/columnId/indicatorId/qualityRuleId）
   - 影响提示：发布/废止时返回引用数量与清单摘要（先提示不强阻断）
2) 前端
   - 列表：补“导入/导出、提交评审、发布、停用、退役”的快速操作；导入失败可下载错误明细
   - 详情：版本列表、附件、变更摘要；发布/废止前弹窗展示影响提示
3) 验收
   - 能用 Excel 导入 50+ 条标准；能提交评审/发布/停用/退役；关键动作写审计；能看到版本与变更说明。

#### 4.0.2 数据资产目录（DatasetsPage / DatasetDetailPage）
目标：让资产“好找、好看、好用”，并形成最小的资产运营闭环。
1) 后端
   - 过滤与聚合：支持按域/密级/标签/负责人/更新时间过滤；支持返回 facet 统计（可选，先后置）
   - 使用统计（轻量）：基于现有审计聚合生成 `dataset_usage_stats`（或查询时聚合）用于详情页展示
   - 认证标记（轻量）：dataset 增加 `certified`/`certifiedBy`/`certifiedAt`
2) 前端
   - 列表：增加常用筛选（域/密级/标签/负责人）；支持保存筛选（后置）
   - 详情：聚合展示 Schema/血缘/生命周期/质量概览/权限概览（同页 tabs）
3) 验收
   - 业务用户能在 3 次点击内找到数据集；能看到负责人/说明/密级；能从详情页跳到血缘、质量、权限。

#### 4.0.3 元数据采集与维护（MetadataPage / CatalogSync）
目标：把“采集”做成可观测、可回溯、可补录的闭环。
1) 后端
   - 运行历史：`catalog_sync_run`（startedAt/finishedAt/duration/status/message/diffStats）
   - 差异统计：新增/变更/删除的表/字段数量 + 关键变更明细（字段类型变化等）
   - Schema 漂移事件（轻量）：`catalog_schema_change_event`，用于详情页展示“最近变更”
2) 前端
   - MetadataPage：显示运行历史、差异统计；失败可查看错误详情；支持一键重试（先手动）
   - 字段补录：字段级中文名/口径/示例/敏感标记，显示变更历史（可先读审计）
3) 验收
   - 能看到每次采集的结果与差异；能定位失败原因；字段补录可被检索到并留痕。

#### 4.0.4 指标管理（Indicators / Dimensions / ComputeRules / Publish）
目标：把指标做成“定义-校验-发布-被使用-变更影响提示”的闭环。
1) 后端
   - 引用关系：指标 <->（数据集/字段/维度/报表链接/查询模板/其他指标）记录与查询
   - 版本与冻结：发布生成 snapshot（口径冻结），变更走新版本；支持版本回滚（后置）
   - 校验：SQL 语法/字段存在/权限/limit/timeout（校验失败给出定位信息）
2) 前端
   - 指标详情：口径、维度、计算 SQL、引用关系、版本历史、变更摘要
   - 发布弹窗：展示“引用影响提示”与校验结果（通过才允许发布）
3) 验收
   - 指标发布后可被查询/报表引用；变更会提示影响；发布历史可追溯。

#### 4.0.5 质量规则与合规检查（QualityRules / Compliance）
目标：把“规则+执行”做稳，并为后续“计划+问题闭环”打底。
1) 后端
   - 规则模板（可选）：内置常用规则（完整性/唯一性/范围/枚举/正则）一键创建
   - 运行归档：运行记录可分页查询、可按 datasetId/ruleId/status 过滤
2) 前端
   - 规则页：提供“从模板新建”；规则与数据集绑定更直观
   - 合规页：运行详情弹窗完善（元数据 JSON 展示、metrics 结构化展示）
3) 验收
   - 常用规则 5 分钟可配置并跑通；能快速定位失败原因并沉淀到问题单（Phase 4）。

### 4.1 模型与标准（modeling）

#### 4.1.1 数据规划管理（业务域/主题）
最小可用：**规划条目 CRUD + 版本/发布 + 审计**。
1) DB
   - 新表：`modeling_plan`（domain、topic、ownerDept、version、status、contentJson、publishedAt…）
   - 可选：`modeling_plan_version`（做成 append-only 的变更历史）
2) 后端
   - 新增 REST：`/api/modeling/plans`（分页/查询/创建/更新/发布/废止）
   - 权限：MAINTAINER（沿用 CATALOG_MAINTAINERS 或新增 MODELING_MAINTAINERS）
   - 审计：create/update/publish/deprecate 全记录
3) 前端
   - 替换 `FeaturePlaceholder`：表格 + 详情抽屉 + 发布按钮
   - 支持按部门/主题/状态筛选；导出（可后置）

#### 4.1.2 口径与术语（Glossary）
最小可用：**术语/口径条目 CRUD + 与指标互链**。
1) DB：`modeling_glossary_term`、`modeling_glossary_relation`（term <-> indicator）
2) 后端：`/api/modeling/glossary/terms`、`/api/modeling/glossary/relations`
3) 前端：术语列表/详情；在指标详情页展示“关联术语”

#### 4.1.3 模型规范与模板（ODS/DWD/DWS/ADS）
最小可用：**模板库 + 命名规则校验器（可先规则文本）**。
1) DB：`modeling_template`（layer、namingRule、fieldsTemplate、reviewChecklist…）
2) 后端：`/api/modeling/templates`
3) 前端：模板列表；支持导入导出（可后置）

### 4.2 治理与质量（governance）

#### 4.2.1 质量巡检计划（QualityTasks）
最小可用：**计划 -> 触发运行 -> 结果入库 -> 通知**。
1) DB：`quality_task`、`quality_task_rule_ref`、`quality_task_run`
2) 后端
   - `/api/governance/quality/tasks`：CRUD + enable/disable
   - `/api/governance/quality/tasks/{id}/runs`：运行历史
   - 调度：可先用 Spring Scheduler（本地）+ 数据库锁，后续再接更强的调度器
3) 前端
   - 替换占坑页：任务列表/创建；运行历史；一键手动触发

#### 4.2.2 问题闭环与工单（QualityIssues）
最小可用：**失败生成 issue + 指派/处理/关闭**。

### 4.3 安全合规（security）

#### 4.3.1 用真实“策略中心”替换静态页面
1) 把 `source/dts-platform-webapp/src/pages/governance/MaskingPoliciesPage.tsx`（假数据）替换为：

   - 行过滤规则：对接 `CatalogResource` 的 `row-filter-rules`
2) 把 `source/dts-platform-webapp/src/pages/security/data-security.tsx` 替换为：
   - 从 catalog 聚合“各密级资产数/最近更新/风险操作摘要”

#### 4.3.1.1 行级安全“字段映射”（必须做，解决字段命名不一致）
目标：每个业务系统字段名不统一时，仍能稳定落地“按数据密级 + 按部门”的行过滤。
1) 数据模型（建议二选一，优先 A）
   - 方案 A（推荐）：新增 `catalog_dataset_security_mapping`
     - datasetId
     - dataLevelColumnId（或 columnName）
     - deptColumnId（或 columnName）
     - deptMatchMode（先只做 EQUALS；后置支持 LIKE/IN/映射表）
     - enabled（是否启用强制行过滤）
   - 方案 B（可选）：复用 `CatalogColumnSchema.tags/sensitiveTags`，给列打内置语义标签
     - 例如内置标签：`__ROLE_DATA_LEVEL__`、`__ROLE_DEPT__`
     - 风险：标签是自由输入，容易被误改；但实现改动小
2) 解析策略（后端）
   - 优先读取 “显式映射” → 找不到再走 “候选字段名自动识别”（现有 `DatasetSecurityMetadataResolver` 的策略）
   - 对 “数据密级字段”要做类型兼容：
     - 字符串列：用 `DataLevelSqlHelper.buildPredicate(UPPER(TRIM(col)))`
     - 数字列：用 `col <= maxAllowedRank`（或 `col IN (...)`），避免对数值列调用 TRIM/UPPER
   - 对 “部门字段”：当前统一为 `dept_code`，默认谓词为 `col = :deptCode`（deptCode 来自 token claim `dept_code` 或请求头 `X-Active-Dept`）
3) 运行时强制点（后端）
   - 在 `SecuritySqlRewriter.guard()` 中把 predicate 扩展为：`dataLevelPredicate AND deptPredicate`（两者都启用时）
   - 当某数据集启用了强制行过滤但缺失映射：默认 **拒绝执行**（fail-closed），并给出明确错误/审计原因，避免“漏过滤”
4) 前端入口（最小可用）
   - 在数据集详情/元数据页增加“安全字段映射”卡片：
     - 下拉选择：数据密级字段、部门字段（从 schema 列表选，避免手输）
     - 开关：是否启用行级强制
     - “预览策略”按钮：展示将会追加的 WHERE 条件（用于联调与排错）
5) 验收
   - 同一套行过滤逻辑，对不同系统不同字段名的表都能生效（通过“映射配置”实现）
   - 无映射时不误放行：启用强制后，缺映射直接拒绝并可定位原因

#### 4.3.2 访问权限矩阵（最小可用）
- 核心是“解释权限为什么生效/不生效”：
  - 维度：用户/部门/数据集
  - 内容：grants + row-filter + masking + 数据密级
- 先做“展示与查询”，后做“在矩阵里直接编辑策略”（编辑仍走已有 API）。

#### 4.3.3 审计查询与报表
- 若审计库在 dts-admin：新增 dts-admin 审计查询 API（分页/过滤/导出），平台侧页面只做消费展示。

## 5. OpenMetadata 作为元数据底座的评估（先不引入）

结论：**当前客户规模（~300 人、数据量百万/千万级、运维为主）优先不引入 OpenMetadata**，原因：
- 额外引入组件多（metadata service / ingestion / ES/OpenSearch 等），运维复杂度显著上升；
- 现有 `catalog` 体系已能覆盖“采集、补录、血缘、策略、审计”最小闭环；
- 未来如出现“多数据源、多团队协作、强血缘与资产门户”诉求，再评估引入更合适。

触发重新评估的条件（建议）：
- 数据源数量上升到 10+ 且频繁变化；需要对接更多引擎（Kafka、API、文件交换等）；
- 需要字段级血缘、任务级血缘、跨系统影响分析成为强刚需；
- 需要成熟的数据资产门户能力（订阅、评价、热度、推荐）并能长期维护。

## 6. 风险与依赖（落地前需要确认）
- Keycloak Token 中的 `dept_code/person_security_level` 是否在所有入口（platform/admin/webapp）一致可取。
- 达梦/PG 等数据库在客户环境的账号隔离与最小权限策略（尤其是行级/脱敏要落到查询层）。
- 星环平台是否提供可用的只读 API（用于方式 2 的作业状态回显）。
- 审计日志存储位置与查询方式（平台侧是否需要独立“审计查询库/索引”）。
