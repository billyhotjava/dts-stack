# OPS-001

## Module

`dev-up.sh`

## Symptom

`./dev-up.sh --mode local` failed immediately against the bootstrap-generated `.env`:

- runtime env copy was created successfully
- shell then aborted on line 6 of the copied env file
- the first placeholder value looked like `AIRFLOW_FERNET_KEY=<secrets:airflow_fernet>`

This blocked all further runtime walkthrough work on the customer `2.2.1` branch.

## Reproduction

1. Ensure the repository `.env` is the bootstrap-generated file with `<secrets:...>` placeholder values
2. Run `./dev-up.sh --mode local`
3. Observe the failure:
   - `/tmp/dts-stack-env.runtime.*: line 6: syntax error near unexpected token newline`

## Expected Behavior

`dev-up.sh` should be able to consume the generated `.env` without shell-evaluating placeholder secret syntax. The script should either start the stack or move on to the next real runtime blocker.

## Candidate Fix Area

- `dev-up.sh`

## Verification Command

- `./dev-up.sh --mode local`

## Root Cause

`dev-up.sh` copied `.env` to a temporary runtime file and then ran `source "$ENV_RUNTIME"`.

That is unsafe for bootstrap-generated env files, because placeholder values such as `<secrets:airflow_fernet>` are valid `.env` content for config tooling but invalid shell assignment syntax when sourced directly.

## Fix

- replaced direct `source "$ENV_RUNTIME"` with a line-by-line env loader
- export each `KEY=VALUE` pair literally, without shell evaluation
- keep comments and blank lines ignored

## Verification Result

- Before fix:
  - `./dev-up.sh --mode local`
  - failed immediately on runtime env line 6 with shell syntax error
- After fix:
  - `./dev-up.sh --mode local`
  - no longer fails on `.env` parsing
  - proceeds into Docker Compose processing
  - current next blocker becomes a separate env/compose completeness issue ending in `invalid proto:`

Result: the original `.env` parsing bug is fixed, and runtime debugging can continue on the next real startup blocker.
