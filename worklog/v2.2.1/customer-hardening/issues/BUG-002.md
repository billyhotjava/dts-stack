# BUG-002

## Module

`source/dts-platform`

## Symptom

After downgrading the customer baseline to `2.2.1`, the backend test baseline was not stable:

- Mockito-based tests on JDK 21 could fail before execution because the inline mock maker could not self-attach
- old compiled test classes left under `target/test-classes` from a newer branch polluted the downgraded workspace
- several tests no longer matched the current `2.2.1` production signatures and Spring test context

## Reproduction

1. Run `./mvnw -ntp test` or a focused test command in `source/dts-platform`
2. Observe Mockito/JDK 21 attachment problems before unit tests are fully executed
3. Observe failures from tests that no longer match the active branch state, including stale compiled classes that do not exist in `src/test/java`

## Expected Behavior

The downgraded `2.2.1` baseline should have a stable `dts-platform` unit-test phase so customer bug-fix and feature work can start from a clean backend baseline.

## Candidate Fix Area

- `source/dts-platform/pom.xml`
- `source/dts-platform/src/test/java/com/yuzhi/dts/platform/service/security/SecuritySqlRewriterTest.java`
- `source/dts-platform/src/test/java/com/yuzhi/dts/platform/service/sql/QueryDatasetServiceTest.java`
- `source/dts-platform/src/test/java/com/yuzhi/dts/platform/web/rest/IngestionTaskProxyResourceTest.java`
- stale build output under `source/dts-platform/target/`

## Verification Commands

- `./mvnw -ntp -Dtest=SecuritySqlRewriterTest,QueryDatasetServiceTest,IngestionTaskProxyResourceTest test`
- `./mvnw -ntp test`
- `npm run backend:unit:test`

## Root Cause

`source/dts-platform/pom.xml` did not pass an explicit Mockito javaagent into surefire or failsafe, so JDK 21 test runs depended on inline self-attachment that is unstable in this environment.

The downgraded branch also inherited stale compiled test classes in `source/dts-platform/target/test-classes` from a newer code line. Those classes did not correspond to any source file in the current `2.2.1` branch, which made the local test baseline misleading after the downgrade.

On top of that, three active tests had drifted behind current code:

- `SecuritySqlRewriterTest` still asserted the older no-department-column rewrite behavior
- `QueryDatasetServiceTest` did not provide the now-required `ModelingSqlModelRepository`
- `IngestionTaskProxyResourceTest` did not mock the newer filter beans required by the slim `@WebMvcTest` context

## Fix

- added `mockito.agent.argLine` in `source/dts-platform/pom.xml`
- wired the Mockito javaagent into both surefire and failsafe `argLine`
- cleaned stale compiled output under `source/dts-platform/target/`
- updated `SecuritySqlRewriterTest` to match the current guarded SQL behavior and failure mode
- updated `QueryDatasetServiceTest` with the missing repository mock
- updated `IngestionTaskProxyResourceTest` with the missing filter mocks

## Verification Result

- `./mvnw -ntp -Dtest=SecuritySqlRewriterTest,QueryDatasetServiceTest,IngestionTaskProxyResourceTest test`
  - `BUILD SUCCESS`
  - `Tests run: 8, Failures: 0, Errors: 0, Skipped: 0`
- `./mvnw -ntp test`
  - `BUILD SUCCESS`
  - `Tests run: 65, Failures: 0, Errors: 0, Skipped: 0`
- `npm run backend:unit:test`
  - unit phase is green, but the overall `verify` command still fails later in this sandbox because:
    - Testcontainers integration tests cannot access `unix:///var/run/docker.sock` (`Operation not permitted`)
    - Maven checkstyle resolution cannot create tracking files under `/home/billy/.m2/repository/com/puppycrawl`

This means the backend unit baseline is now stable, and the remaining `verify` failures are environment or permission constraints rather than the original test-baseline bug.
