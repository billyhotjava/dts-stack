# Sprint-12 设计：逻辑建模执行按钮统一

## 背景

当前 `逻辑建模` 页面同时存在两套执行入口：

1. 顶部工具栏
2. 中部“流水线”按钮

这两套入口在命名和实际动作上并不一致：

- 顶部按钮显示为“提交上线”
- 流水线末步骤显示为“发布上线”
- 两者背后触发的 dbt operation 也不一致

这会直接导致用户无法判断：

- 该点哪一个入口
- 当前动作是单模型还是整组模型
- 当前动作到底是 `compile`、`test`、`run` 还是 `build`

## 目标

先统一界面交互，保证页面只有一套可执行入口；流水线仅表达状态，不再承担执行职责。随后将这套唯一入口对应的后端执行链收口，避免前端统一后仍然因为 Airflow DAG 未透传 `vars` 导致 `dbt` 实际执行结果错误。

## 方案

### 推荐方案

保留顶部工具栏为唯一执行入口，并按方案 1 拆成两组：

- 主流程：`编译`、`测试`、`上线`
- `更多`：`提交变更`、`同步模型`、`文档`、`回退`

将中部 `ModelPipeline` 改成只读状态组件：

- 保留“编译 / 测试 / 提交变更 / 发布上线”四个阶段的状态展示
- 不再允许点击触发执行
- 不再接受 `modelSelector`、`onStatusChange` 之类与执行耦合的输入

### 为什么不保留流水线为执行入口

如果保留流水线为执行入口，顶部工具栏里的 `同步模型 / 文档 / 回退 / 上线` 仍然会继续存在，页面会继续保留两套命令体系，不能真正消除歧义。  
如果把 `提交变更` 继续保留为主按钮，会和 `上线` 在认知上形成两个相近“提交”动作，仍然不够清晰。

## 用户影响

- 页面上执行动作只从顶部工具栏发起
- 顶部就能完成完整主流程，不需要再去底部 Git 区提交
- 关键动作只保留 `编译 / 测试 / 上线` 三个主按钮，认知负担更低
- 流水线只反映状态，不再出现“发布上线”和“提交上线”并存的操作冲突
- `上线` 统一为 `dbt build`
- 专题绑定、source 映射等运行时变量会随同唯一执行入口进入 Airflow / dbt，不再因为 DAG 未透传 `vars` 而回退到默认源表

## 风险

- 现有依赖 `ModelPipeline` 的状态回写逻辑需要同步简化
- 如果某些状态完全依赖前端本地更新，改成只读后需要依赖页面刷新或上层状态更新

## 验证点

1. 页面仍能正常展示流水线状态
2. 流水线按钮不可点击
3. 顶部存在 `编译 / 测试 / 上线`
4. `更多` 中包含 `提交变更 / 同步模型 / 文档 / 回退`
5. 底部 Git 区不再出现内联提交输入
6. Airflow 动态 DAG 生成结果包含 `--vars`
7. `pnpm build` 通过
