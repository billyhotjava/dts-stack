# 数据开发中心实施计划（P0-P3）

## 目标

在不与其他 session 发生代码冲突的前提下，先完成方案收敛与任务拆解，然后按 P0->P3 逐步落地。

## 执行边界（本 session）

- 工作根目录：`worklog/v2.2.1/platform/development`
- 本轮先完成：任务细化、实施顺序、验收口径与风险前置。
- 代码改动将按任务卡逐一进行，并在每个任务卡中记录影响文件与回归命令。

## 波次安排

## Wave 1（P0）

1. P0-01 主流程收敛（移除 ZIP 导入）
2. P0-02 历史 API 面清理（旧 explore CRUD）
3. P0-03 dbt 运行最小参数化（selector/target/run|test）

验收门槛：

- 主流程只保留 ODS 一键生成 + 单文件导入。
- 历史裸 CRUD 接口下线或封禁。
- dbt run 支持最小参数化且可审计。

## Wave 2（P1）

1. P1-01 SQL Workbench 异步化 + 结果分页
2. P1-02 脚本开发 MVP（CRUD/版本/运行/日志）
3. P1-03 编排可观测入口（列表/最近运行/失败重试）

验收门槛：

- 长查询不阻塞请求线程。
- 脚本功能不再是静态占位页。
- 编排页可观测且可操作。

## Wave 3（P2）

1. P2-01 dbt DevOps 能力包（compile/test/docs）
2. P2-02 模型质量基线（自动测试模板）
3. P2-03 语义契约对齐（模型-指标-看板）

## Wave 4（P3）

1. P3-01 GitOps/CI Gate
2. P3-02 多环境多架构回归矩阵
3. P3-03 运营指标体系

## 风险前置

- 功能分叉风险：ZIP 导入残留引发流程混用。
- 接口债务风险：旧 API 被第三方脚本调用。
- 性能风险：SQL 同步执行在高并发下放大线程占用。
- 运维风险：dbt 能力扩展时缺乏统一失败分类与追踪。

## 回滚原则

- 每个任务独立可回滚，不做跨任务混合提交。
- P0 任务在发布前必须附回归命令与证据。
