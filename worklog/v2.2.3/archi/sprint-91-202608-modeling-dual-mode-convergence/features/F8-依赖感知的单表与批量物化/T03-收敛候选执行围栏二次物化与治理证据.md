# T03: 收敛候选执行围栏、二次物化与治理证据

**优先级**: P0
**状态**: CODE_COMPLETE / E2E_PENDING
**依赖**: F8/T01、F8/T02、F7/T03；复用 Sprint-76 控制面

## 目标

将 plan 中的 BUILD/REUSE 落到既有 release candidate、build/test/materialization dispatch 与 observation，补齐 DBT_MANAGED 的 ODS 来源围栏，并确保二次物化只新增执行证据、不复制模型或资产。

## 执行契约

- 创建 candidate 时重新解析 F6 snapshot 和 F8 preview；entry 钉住 model/implementation/dependency checksum。
- 浏览器先预览计划，再编译计划中全部 `BUILD` 节点（包括自动展开上游），编译后重新预览并提交新 checksum；服务端在同一事务内锁 plan、复核 checksum、写 candidate/attempt，禁止 preview 与写入之间的 TOCTOU。
- BUILD 节点按拓扑加入同一 candidate；已验证 REUSE 节点以 pinned read-only proxy 进入 bundle，不创建重复 candidate entry。
- 跨规划上游只允许消费 `PUBLISHED` 且 exact pin、环境、target、relation evidence 全部匹配的 `REUSE`；请求根模型必须归属当前规划，当前规划不得代替其他规划重建模型。
- DBT_MANAGED 与 DESIGNER_GENERATED 共用相同 source availability fence；`GENERATED` 不得再跳过 ODS source binding 的可用性校验。
- 每次请求只产生一个 batch correlation；每个 BUILD 模型有独立 candidate entry、attempt、dispatch、relation observation。
- build → test → quality → review → publish 的每一阶段沿用既有显式命令；UI 不自动审批或自动发布。

## 二次物化不变量

- 复用同一 `modelSpecId`、model identity、implementation identity（除非用户已提交新修订）和 CatalogAssetKey。
- 新增 candidate/execution/dispatch/observation/lifecycle/audit 历史；不得新增第二个逻辑模型或重复资产登记。
- 用户再次物化只提交原候选 root，服务端按最新计划仅为 `BUILD` 子集创建 pipeline run；`REUSE` 条目沿用之前的精确成功证据。再次失败后的 retry 保持该次部分执行范围，不回退成全候选重跑。
- 发布、质量与工作台按候选 entry 汇总各自最近一次精确成功 attempt，不能用“最新 dispatch 的行数”等同完整候选证据。
- 失败重试与再次物化分开：相同 attempt 的 retry 保持幂等；用户主动再次物化创建新执行记录。
- 物理 relation 只在 exact pin + environment + target 匹配时 REUSE；仅表名相同不等于可复用。

## 治理交接

向 Sprint-93 提供稳定证据：candidate pins、dependency checksum、artifact checksum、relation observation、quality run、publication、lineage projection correlation。Sprint-93 只消费这些事实，不反向改写建模/物化状态。

## 错误与恢复

- 执行前任一 pin 漂移：candidate `STALE`，返回稳定原因，重新 preview/new candidate。
- source 不可用、上游 relation 未验证或 selector 冲突：保持 BLOCKED，不用裸 dbt `+selector` 绕过。
- 失败允许既有 retry/rollback；回滚只改变发布/物理指向，不删除历史 ModelSpec/implementation/artifact。
