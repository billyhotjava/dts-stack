# T01：恢复索引构建与测试基线

**优先级**：P0
**状态**：READY
**依赖**：无
**类型**：Delivery Baseline / Tooling Repair（不修改业务行为）

## 可测试目标

普通工作用户在干净 worktree 上能够刷新 `s10-stack` GitNexus 索引，并分别执行 Platform `QueryDatasetServiceTest`、Analytics `QueryExecutionFacadeTest` 与前端两类 runner；任何失败都进入真实测试断言，而不是权限、runner 或无界扫描错误。

## 输入、输出与错误契约

| 项目 | 契约 |
|---|---|
| 输入 | 当前 commit、GitNexus config、vendored path、两个模块 root-owned `target/`、既有 pnpm/node runner |
| 输出 | fresh index 证明、排除/超时配置或可重复刷新命令、普通用户可写的隔离 target、四条聚焦命令与 exit code |
| 安全边界 | 不删除未知用户构建产物；先 `stat/lsof/ps` 确认 owner/活跃写入；优先 Maven `-D...outputDirectory` 或经确认后修复模块 target ownership |
| 失败 | 索引仍 stale、worker 仍卡死、target 活跃 owner 不明时停止，记录 exact blocker，不用 root 代跑 |

## 实施步骤

1. 读取 GitNexus status/config，定位 vendored OpenMetadata Python 是否可在索引配置中安全排除；不改变源码目录。
2. 使用有界命令刷新索引并证明 commit 对齐；若工具仍失败，保存最小日志和可复现 path，升级为 BLOCKED。
3. 对 Analytics/Platform `target/` 做只读 owner 与活跃进程检查；选择隔离输出或最小 ownership 修复。
4. 分别执行两个 Maven 聚焦测试；前端将 `node --test` 与 `vitest` 分开执行。
5. 为活跃编码范围 F1～F4、F6 列出拟修改 symbol，建立逐项 `gitnexus_impact(direction=upstream)` 记录模板；HIGH/CRITICAL 必须先告知并裁剪。

## RED → GREEN

- RED：索引落后 2 commit；刷新停滞；两个 Maven 测试编译前 permission denied；runner 混跑 exit 1。
- GREEN：index commit=current；普通用户执行两个后端测试进入并完成断言；Node 4/4 与 Vitest 各自独立通过；命令在第二次运行可重复。

## 影响范围与验证

- 允许影响：`.gitnexus`/工具配置（如确需）、模块局部构建输出权限/命令、Sprint 证据。
- 禁止影响：Java/TS 业务 symbol、运行数据库、容器数据、用户业务文件。
- 工具配置若需入库也必须先走 impact/变更审查；提交前运行 detect_changes，期望无业务执行流变化。

## Definition of Done

- [ ] fresh index、current commit 和可重复 analyze 命令有证据。
- [ ] Platform/Analytics 聚焦测试由普通用户运行，exit code 与 test count 记录。
- [ ] Node/Vitest runner 边界固化，混跑问题不再出现。
- [ ] 没有以 root 构建或破坏性删除掩盖权限问题。
- [ ] 每个编码 Task 的首批 impact target 已列出，HIGH/CRITICAL 进入显式风险门禁。
