# Sprint-64: 数仓规划能力升维——业务过程、分层注册、粒度与总线矩阵

**时间**: 2026-07
**状态**: IN_PROGRESS
**类型**: Warehouse Planning / Kimball Methodology / UI-first
**目标**: 把数仓规划从"主题域目录 + 固定 DWD 维度入口"升维为"建模有据可依"的规划能力：业务过程决定建什么事实、分层注册决定建在哪、粒度声明决定一行是什么、一致性维度登记决定复用什么。

## 背景

对标 DataWorks 智能建模四模块后确认：当前 `/governance/subjects` 只有主题域树 CRUD（目录学），分层是 workbench 硬编码卡片 + URL 枚举，业务过程、粒度、一致性维度完全缺失。缺了这三样，规划页只是给建模页传 domainId 的参数工具，客户面对"进度域"仍不知道该建几张表、每张装什么、能复用什么。

素材优势：业务过程可从 PJM 真实场景提炼（节点计划闭环/质量归零/风险释放）；分层红线在 model-governance.md 已成文；一致性维度种子=dbt 侧 8 张 canonical 维表；粒度问题在 dts-metrics 评审中已被点名。落地成本在产品化，不在设计。

## 关键决策

- **processId 纳入旅程白名单**：沿用 Sprint-63 3.3 决策模式，`JOURNEY_CONTEXT_PARAM_KEYS` 增加 `processId`，连锁改动（LABELS/快照/校验 API 名/既有测试回归）计入 F1/T01。
- **分层注册表先静态受控对象**：以类型化 ts 常量承载层定义/职责/依赖方向/命名前缀（素材=model-governance 红线），同时由 Sprint-64 后端 API 返回同一契约；workbench 保留静态回退并优先消费 API 注册表。
- **grain 是维度候选门禁的必填项**：扩展 Sprint-63 的 dimensionCandidateGate，未声明粒度不得生成模型候选。
- **一致性维度种子数据 = 8 张 canonical 维表**（完成情况/节点类型/风险等级/质量状态/质量分类/更改类别/签署状态/风险分类），登记先行、复用推荐后行。
- **正交边界**：项目空间（权限协作轴）不进本 sprint；规划页只管业务语义轴（主题域/业务过程）与技术组织轴（分层）。
- 全部新对象 UI-first：先以 session/静态对象完成首用链路，再补齐 Sprint-64 API 和 Liquibase 持久化；API 不可用时显式回退到 session，不伪装远端已保存。
- **评审增补（2026-07-11 重构评审四结论）**：① 概念三层链"主题域⊃业务过程⊃业务对象"以概念卡+登记入口前移产品化；② 模型管理页修复前端与 modelingApi 六层契约不一致，客户视图五层、STG 技术层默认折叠；③ "逻辑建模（SQL）"更名"高级建模（SQL）"，叙事定型"维度建模出草稿，高级建模精加工"；④ 单产物原则：普通/高级建模共用同一份 dbt 模型（SQL+schema），低代码页显性声明产出物。
