# T03：明确业务分类与业务活动边界

**优先级**：P0
**状态**：DONE
**依赖**：F1-T01

## 目标与用户结果

用户先选择“管什么业务”的业务分类，然后直接登记维度或创建四类表；业务活动只在需要说明明细事实来源时出现。

## 范围与不做

- 范围：domainId、businessActivityRef/processId 的客户含义、必填阶段、页面位置和兼容映射。
- 不做：不建立新的业务分类表，不为业务活动建设独立复杂工作台。

## 输入条件

| 场景 | domainId | businessActivityRef | 缺失行为 |
|---|---|---|---|
| 创建计划 | 可后补 | 不显示 | 创建后引导完善分类 |
| 进入模型设计 | 必填且已确认 | 不要求 | 缺分类阻塞并给修复路由 |
| 创建 DIMENSION | 必填 | 不接收 | 只校验分类与维度自身字段 |
| 创建 FACT | 必填 | 可选 | 允许保存；草稿以粒度为硬条件，进入实现前再校验上游输入 |
| 创建 SUMMARY/APPLICATION | 必填 | 不接收 | 由上游模型投影活动范围 |

## 预期输出

- `domainId` 作为新模型共同分类字段；
- `businessActivityRef?` 作为 FACT 的可选元数据；
- 旧 `processId` 单向兼容映射；
- 去除 domain/process 全局组合门禁的规则。

## 详细设计

1. 业务分类直接复用 catalog domain；WarehousePlan 只保存引用和确认状态。
2. F1 定义纯规则输入 `DomainResolution=AVAILABLE|MISSING|ARCHIVED|FORBIDDEN`；F2-T02 由 catalog/权限 owner 提供真实解析。本 Task 不以当前仅能查 UUID 的 CatalogDomain 假装已经覆盖归档和域级权限。
3. SubjectAreasPage 保留分类树、责任人和治理统计，移出候选确认、维度目录和矩阵等建模表单。
4. 业务活动可在 FACT 表单的“业务说明”折叠区选择或录入；不是主页面，不先于模型存在。
5. 若旧 processId 有值，兼容层映射为 activityRef；新 API 不再写旧 processId。
6. 数据域/主题域历史参数统一解析到 domainId；冲突时以显式 domainId 为准并返回诊断，不静默覆盖。

## 异常与权限

- domainId 不存在、已归档或无权访问时返回稳定 blocker 和修复路由。
- FACT 的 activityRef 失效只产生 WARNING，不阻止保存或发布；非 FACT 新请求携带该字段返回字段级校验错误，兼容读取只作诊断而不复制到新 revision。

## 实施与测试设计

1. 先补四类模型 domain/activity 校验矩阵测试。
2. 修改基线与 ModelSpec 验证器，删除全局 process 必填。
3. 前端根据 modelType 渲染业务活动字段。
4. 回归旧 URL 中 domainId/processId 的读取和新 URL 不再写入。
