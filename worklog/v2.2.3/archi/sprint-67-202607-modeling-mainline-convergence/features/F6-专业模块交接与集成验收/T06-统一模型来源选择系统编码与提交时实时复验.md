# T06：统一模型来源选择、系统编码与提交时实时复验

**优先级**：P0
**状态**：IN_PROGRESS
**依赖**：F2-T03、F3-T03、F3-T05、F4-T03

## 目标与用户结果

新建或编辑模型并选择直接物理来源时，用户只需从当前 WarehousePlan 已确认的来源中按业务名称选择，再补充上游来源分层、作用和 JOIN 等建模语义。`sourceBindingId/ref/kind/resolvedVersion` 、维度系统编码和层级系统编码由系统生成或关联带出，不再要求用户复制 UUID、版本或自行构造唯一代号。FACT 草稿也可以暂不选择物理来源，或改用锁定 revision 的上游 ModelSpec；该分阶段门禁由 F3-T06 统一。

## 问题来源

2026-07-22 人工测试发现，模型表单将“来源标识”“来源登记 ID”和“已确认版本”作为普通文本框暴露。首次使用者无法知道这些值应从哪个页面获取，也可以误填其他计划的绑定或伪造版本。维度编码和层级编码同时作为人工必填项，将唯一性和稳定性责任错误地交给了操作人。

另一个容易混淆的边界是：只有“数据连接”不足以成为直接物理来源。连接只说明通道可用；若选择具体物理表，该表必须先完成元数据同步，能在目录中解析，并在当前计划的“来源盘点”中确认纳入。保存 FACT 逻辑草稿不要求来源，也不要求先完成 ETL/ELT；但已选择的物理来源不得尚未同步、无法解析或未经确认。

2026-07-22 继续人工测试确认：连接已测试成功且正式目录已有表时，模型页仍会因当前计划的 `modeling_warehouse_plan_source` 为空而阻断。这不是元数据缺失，而是“具体表 → 当前计划”关联缺失；原空态文案将两种状态混为一谈，来源盘点也缺少从已验证连接直接选表的主路径。

容器重建并重启后再次人工验证发现，上一轮只补了独立“来源盘点”页和跳转入口，未闭合正在编辑的模型表单：用户离开 Drawer/详情页登记来源后，原表单既不能感知保存结果，也不会自动刷新可选来源，因此仍停留在同一阻断提示。该问题属于前端上下文与回写链断裂，不是连接、元数据同步、ETL/ELT 或容器版本问题。

## 契约与所有权

| 字段/动作 | 用户责任 | 系统责任 |
|---|---|---|
| 规划物理来源（可选） | 需要直接绑定物理输入时，按业务名称、具体表/节点和来源类型选择 | 只查询当前 `planId` 中 `CONFIRMED + CURRENT + AVAILABLE` 的完整绑定 |
| 连接到规划 | 在已验证连接下选择 Schema 和具体表，点击“加入当前规划并确认” | 只查询正式目录中已同步且有权读取的表，自动生成 `CONNECTION_TABLE` locator |
| `sourceBindingId` | 不输入 | 由所选规划来源带出 |
| `ref/kind/resolvedVersion` | 不输入 | 由所选来源的权威解析结果带出 |
| 来源分层、作用、别名、JOIN | 按建模语义确认 | 校验类型和必填条件 |
| 维度系统编码 | 只输入维度名称和业务定义 | 创建草稿时生成稳定唯一编码，编辑时只读 |
| 层级系统编码 | 只输入层级名称和顺序 | 在所属维度内生成稳定编码，编辑时只读 |
| 保存模型 | 提交业务选择 | 不信任前端隐藏值，按当前 `planId + bindingId` 重新解析并校验类型、引用和版本 |

## 交互与失败策略

1. 创建页和详情编辑页使用同一个 WarehousePlan 来源清单；不建第二套数据源 API 或前端缓存事实。
2. 切换建设计划时，先清空已选来源和上一计划的请求结果，再加载新计划的分类和来源，防止竞态回写。
3. 不自动选中唯一来源；“主要来源”仍是需要用户确认的业务决策。
4. 已保存来源变为过期或删除时，保留为禁用诊断项；同一绑定出现新版本时，不静默升级，必须由用户明确点击“采用当前版本”并保存新的模型 revision。
5. 来源列表为空、加载失败或无权限时，页面显示不同的可恢复状态，并只导航至当前 `planId` 的 canonical 来源盘点。
6. 只要提交包含 `sourceRefs`，后端 resolver 就实时复验；跨计划绑定、未确认来源、已失活连接、未同步表、解析失败或版本漂移均 fail closed，不接受前端伪造值。FACT 草稿未选择 `sourceRefs` 时不得伪造一条来源来通过保存。
7. 连接选择器只展示 `ACTIVE + lastVerifiedAt + JDBC`；表选择器通过带 `sourceId` 的正式目录 API 查询，不把 live Schema 探测误当成已同步证据。
8. Schema/表目录使用服务端关键词检索；已选择表保留提交快照，延迟搜索响应不得清空或替换用户已选事实。
9. 来源库存发生 409 时必须重新读取最新版，按 `bindingId` 合并本地确认/排除决定并保留并发新增来源；同一具体表不得重复登记，也不得递归自动重试。
10. 新来源只有服务端实时解析为 `AVAILABLE` 才能落库；`MISSING/FORBIDDEN/PROVIDER_ERROR` 统一 fail closed，不增加版本、不泄露探测细节。
11. 计划清单、基线、来源、策略和 candidate preview/confirm 都执行计划对象级读取授权；部门角色只能使用认证令牌中的权威部门，不能通过 `X-Active-Dept` 切换到其他部门，目录部门匹配必须规范化后精确相等。
12. 连接 URL、账号、属性或密钥等配置发生变化后，系统立即清空 `lastVerifiedAt`；重新测试成功前，该连接及其表不能新增到规划来源。
13. 模型新建和详情编辑表单内始终提供“管理规划来源”；弹窗先读取权威计划生命周期和规划策略，未知状态默认只读。用户确认来源后必须自动重载当前 `planId` 的权威库存；刷新失败或仍有 `CANDIDATE` 时保留弹窗并允许 latest-only 重试，写入/刷新进行中禁止关闭或销毁，刷新成功且全部决策完成后再关闭，不要求离开表单或手工刷新。

## 验证矩阵

| 场景 | 预期 |
|---|---|
| 当前计划有多个来源 | 以业务名称、实际表/节点标识和来源类型搜索选择 |
| 选中来源 | `bindingId/ref/kind/resolvedVersion` 自动关联，用户只继续确认分层/作用/JOIN |
| 只建立连接 | 不出现在可选来源；提示先同步具体表并在来源盘点确认 |
| 连接已验证、目录已同步、计划尚未绑定 | 明确提示“连接测试不会自动加入规划”；按连接 → Schema → 表加入并确认 |
| 在模型表单内登记来源 | 不离开当前新建/编辑上下文；保存后弹窗关闭，规划来源下拉立即出现新绑定 |
| 从其他资产目录登记候选 | 弹窗保持打开，必须将候选设为“确认纳入”或“排除”并保存后才能返回模型表单 |
| 来源保存进行中 | X、遮罩和 Esc 均不能销毁弹窗；写入完成后父表单一定执行来源重载 |
| 计划已发布/归档或状态读取失败 | 内嵌来源管理默认只读，不以前端旧缓存放开维护动作 |
| ETL/ELT 未运行 | 已同步且已确认的表仍可用于模型设计；后续实现/发布门禁独立校验 |
| FACT 草稿尚未确定输入 | 允许保存粒度设计；进入实现前补有效物理来源或锁定 revision 的上游模型 |
| FACT 选择上游 ModelSpec | 不要求再选该上游对应的具体物理表；由 F3-T06 校验 revision 和循环依赖 |
| 同时选择物理来源和上游模型 | 两类引用都必须当前有效，不能用其中一类掩盖另一类漂移 |
| 切换计划 | 旧计划的来源绑定立即清空，延迟响应不能回填 |
| 同时编辑来源盘点 | 重新加载最新版后按 bindingId 合并；保留并发新增项，本地排除原因不丢失，同一来源不重复 |
| 新来源实时解析失败 | 统一拒绝且不落库、不推进 sourcesVersion，不返回可用于资源探测的内部状态 |
| 跨部门计划/header 伪造 | 计划返回遮蔽 404；部门用户伪造 `X-Active-Dept` 仍只能看到认证部门及 global 来源 |
| 部门编码后缀碰撞 | `dept-a/dept-ba`、`10/10010` 均按不同部门处理 |
| candidate preview/confirm | preview 执行对象级读取门禁，confirm 执行计划维护门禁，无跨计划写入旁路 |
| 已验证后修改连接配置 | 验证时间立即失效；必须重新测试成功后才能登记具体表 |
| 编辑旧模型 | 不可用来源只读诊断；同一来源升版时必须明确“采用当前版本”，不被静默升级或丢弃 |
| 新建/编辑维度 | 维度和层级系统编码自动生成、只读显示，不因名称修改而变化 |
| 伪造隐藏字段/版本漂移 | 后端以提交时当前计划事实复验并拒绝，不产生新 revision |
