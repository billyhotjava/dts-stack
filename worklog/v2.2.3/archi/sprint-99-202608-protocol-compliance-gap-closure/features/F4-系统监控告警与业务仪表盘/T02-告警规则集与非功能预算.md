# T02: 告警规则集与非功能预算

**优先级**: P0
**状态**: DRAFT
**依赖**: T01

## 目标
定义一组"触发即代表真有问题"的告警规则，配套抑制策略避免风暴，并把阈值来源写成可审计的非功能预算。

## 技术设计 (Contract-first)
- **输出契约** `services/dts-prometheus/rules/dts-platform.yml`：
  | 告警名 | 表达式要点 | for | severity |
  |---|---|---|---|
  | `ServiceDown` | `up{job=~"dts-.*"} == 0` | 3m | critical |
  | `IngestionTaskFailureBurst` | `increase(dts_ingestion_task_failed_total[15m]) > N` | 5m | critical |
  | `AuditWriteFailure` | `increase(dts_audit_write_failed_total[10m]) > 0` | 5m | critical（审计中断属合规事件）|
  | `LoginLockoutBurst` | `increase(dts_login_locked_total[10m]) > N` | 5m | warning（疑似暴力破解，联动 F1/T02）|
  | `JvmHeapHigh` | `jvm_memory_used/max > 0.85` | 10m | warning |
  | `DiskSpaceLow` | 宿主机/数据卷剩余 < 15% | 10m | critical |
  | `HttpErrorRateHigh` | 5xx 占比 > 5% | 5m | warning |
  | `BaselineCheckFailed` | `dts_baseline_check_status{} == 0` | 30m | warning（联动 F2）|
- **抑制**（alertmanager `inhibit_rules`）: `ServiceDown` 触发时抑制该服务的 `HttpErrorRateHigh` / `JvmHeapHigh`，避免一次宕机产生 N 条告警
- **分组**: `group_by: [alertname, job]`，`group_wait: 30s`，`group_interval: 5m`，`repeat_interval: 4h`
- **接收器**: 默认 webhook 占位 + 文档说明现场如何替换为邮件/短信/内部通知；**不做多级升级策略**（组织模型未定）
- **错误路径**: 规则语法错误 → prometheus 启动失败。**必须先 `promtool check rules` 再提交**
- **产出** `assets/nfr-budget.md`：每条阈值的来源与依据（协议指标 / 现网基线观测 / 经验值），无依据的阈值不得进规则集

## 影响范围
- `services/dts-prometheus/rules/`、`services/dts-alertmanager/alertmanager.yml`
- `assets/nfr-budget.md`（新建，闭合 Gate G1 的 GAP 行）

## 验证 (RED→GREEN)
- [ ] `promtool check rules` 通过
- [ ] 人为停 dts-ingestion → 3 分钟后 `ServiceDown` 出现在 Alertmanager
- [ ] 抑制生效：服务宕机期间不产生该服务的 Heap/ErrorRate 告警
- [ ] 人为触发 5 次登录失败锁定 → `LoginLockoutBurst` 触发（与 F1/T02 联调）
- [ ] 告警恢复后自动 resolved

## Definition of Done
- [ ] 架构：全部规则 promtool 通过 + 至少 3 条规则真实触发验证
- [ ] UI：不适用
- [ ] 切片：故障注入 → 告警到达 → 恢复 全过程证据入 `it/evidence/`
- [ ] Gate G1 非功能预算行由 GAP 改为 PASS
