## 四、A 组逐维度核验

### A1 性能监控 —— 🟡 partial
- **证据**: `application.yml:106-117` micrometer 开启 http/jvm/process/system 指标 + 分位直方图;prometheus 抓取端点 `/management/prometheus`;Grafana 部署清单 `source/dts-{platform,admin,common}/src/main/docker/grafana/provisioning/dashboards/JVM.json`(JHipster 自带 JVM 仪表盘)。
- **缺**: 仪表盘只有 JHipster 自带 **JVM.json**(Uptime/Heap/CPU/Threads/HTTP I/O),**无业务级性能面板**(无采集吞吐、无 SQL/dbt 执行、无 API SLA、无 metrics 服务面板)。`monitoring.yml` 顶部注明 "intended for development purpose, it's your responsibility to harden it for production",且 `network_mode: host` + `GF_SECURITY_ADMIN_PASSWORD=admin`,为开发态脚手架,未生产化。主 `docker-compose-app.yml` 未编排 grafana/prometheus 服务(仅 Traefik 自身 prometheus 指标)。

### A2 错误日志 —— 🟡 partial
- **证据**: micrometer `logback: true` 暴露 log event 计数(JVM.json 含 "Log Events (1m)" 面板);`logfile`/`loggers` actuator 端点已暴露(`application.yml:71-72`);各服务有 `ApiExceptionHandler`/`ExceptionTranslator` 统一异常处理。
- **缺**: 无集中式错误日志聚合(无 ELK/Loki/OpenTelemetry log pipeline),无基于错误率的告警阈值,错误日志仅落本地文件 + log 计数指标。

### A3 资源使用 —— 🟡 partial
- **证据**: micrometer `process/system: true`(`application.yml:110-112`)采集 CPU/内存/系统负载;JVM.json 含 Heap/Non-Heap/CPU/Load/Threads 面板。
- **缺**: 仅 JVM 进程级资源;无主机/容器/磁盘/DB 连接池等资源面板,无资源阈值告警。

### A4 数据采集任务执行情况 —— ✅ covered(4月评估遗漏,实为已实现)
- **证据**:
  - 域模型 `dts-ingestion/.../domain/IngestionExecution.java`(status: running/success/failed、`error_message`、`failure_category`、`failure_advice`、起止时间)。
  - 实时状态 `IngestionRealtimeStatus.java` + `IngestionRealtimeStatusRepository`。
  - 可观测 DTO `IngestionExecutionObservabilityDTO.java`:total/success/failed/running/timeout、successRate、timeoutRate、avgDurationSeconds、**mttrSeconds**、failureTop(失败分类 Top)、trend(按天趋势)。
  - REST 端点 `IngestionTaskResource.java:2559` `GET /api/ingestion/tasks/executions/observability`,另有 `governance-overview`、`trace`、`{id}/realtime-status`、`{id}/incremental-audits`、自动重试 `executions/{eid}/retry`。
  - liquibase 支撑: `20260213_01_ingestion_execution_failure_classification.xml`、`20260309_01_ingestion_execution_auto_retry.xml` 等。
  - 平台事件可观测前端 `dts-platform-webapp/src/pages/ops/PlatformEventObservabilityPage.tsx`(成功/失败/超时/分发状态)。
- **结论**: 采集任务执行监控以 **业务 DB + 聚合 API + 前端页面** 形式完整实现(成功率/超时率/MTTR/失败分类/趋势/重试),覆盖协议"数据采集任务执行情况"。**唯一不足**: 未对接 micrometer 指标 / Prometheus 告警,故无主动阈值告警(失败率超阈自动告警),仍是"看板式被动观测"。

### A5 自定义告警规则 —— 🔴 gap
- **证据**: prometheus.yml 中 `Alertmanager` 仅出现在注释(`dts-platform/.../prometheus/prometheus.yml:8`),**无 `rule_files:`、无 `alerting:` 块、无 alertmanager 服务**(repo 内 grep `rule_files/alertmanager` 仅命中注释行)。
- **误判排除**: `dts-analytics/.../web/rest/AlertResource.java`(`/api/alert` + `AnalyticsAlert`/`AnalyticsAlertSubscription`)是 **Metabase 兼容的 BI 卡片告警**(对保存的 question 结果做订阅提醒),**不是系统/基础设施监控告警规则**,不能满足协议 A5 的"系统监控自定义告警"。
- **缺**: 完全缺少面向运维的"自定义告警规则"能力 —— 无 Prometheus 告警规则文件、无 Alertmanager 路由/抑制/通知渠道、无 UI 配置阈值告警(如采集失败率/超时率/资源水位/错误率超阈触发)。

## 五、B 组 功能及接口日志要素 核验 —— 🟡 partial

`AuditEntry.java` 字段对照协议六要素:

| 协议要素 | 是否齐全 | 字段证据 |
|----------|----------|----------|
| 时间 | ✅ | `occurredAt`(Instant)+ `createdAt` |
| 源IP | ✅ | `clientIp`(INET);解析走 `IpAddressUtils.resolveClientIp`(支持 RFC7239 Forwarded,见多处 `resolveClientIp` 引用 + 项目记忆) |
| 目标IP | 🔴 缺独立字段 | 无 `targetIp`/`serverIp` 列;仅有 `requestUri`+`httpMethod`(可间接定位目标服务,但非协议字面"目标IP") |
| 操作 | ✅ | `operationCode`/`operationName`/`operationKind`/`buttonCode` |
| 异常原因 | 🟡 | 审计有 `result`(SUCCESS/FAILED)+ `summary`/`metadata`/`extraAttributes`,`AuditService` 有 FAIL stage 归一;但无专用"异常原因/错误码"列,失败原因落在自由文本 summary。采集侧另有结构化 `IngestionExecution.errorMessage/failureCategory/failureAdvice` |
| 受影响功能 | ✅ | `moduleKey`/`moduleName`(sprint-34 DB 目录保真分类)+ `targets`(AuditEntryTarget)+ `details` |

- **强项**: sprint-34 后审计目录 DB 化,sourceSystem 保真,模块/操作分类准确,clientIp 经 Forwarded 头收口解析,历史快照不随改名漂移;analytics 侧 `AnalyticsAuditLoggingFilter` 也记录 uri/method。
- **缺**: (1) 无独立"目标IP"字段;(2) "异常原因"在管理/平台审计中无结构化错误码列,依赖 summary 自由文本(采集侧已结构化,可作为模板)。

## 六、综合结论与落地建议

**模块评级: partial**。监控指标采集层(micrometer/actuator/prometheus 端点)与采集任务执行观测、审计日志要素三块较扎实;但**监控可视化仅 JHipster 自带 JVM 仪表盘(开发态脚手架)**,且**完全缺失自定义告警规则(Alertmanager/规则文件)**,日志要素缺"目标IP"与结构化"异常原因"。

### 落地包建议(按优先级)

- **[P0] A5 自定义告警规则(合规硬约束)**: 新增 `prometheus/rules/*.yml` 告警规则(JVM 内存/CPU/错误率/采集失败率/超时率阈值)+ 部署 Alertmanager(路由/抑制/通知渠道:邮件/Webhook),并在 prometheus.yml 补 `rule_files:` 与 `alerting:` 块;或在 ingestion 侧把 `IngestionExecutionObservabilityDTO` 的 successRate/timeoutRate 接入 micrometer Gauge 以便规则可抓取。最好再补一个 UI 配置阈值的"告警规则管理"页。

- **[P1] A1/A2/A3 业务监控仪表盘**: 在 grafana provisioning 增加业务级仪表盘 JSON(采集任务执行、API SLA/错误率、dbt/SQL 执行、连接池/资源水位、metrics 服务),把 `monitoring.yml` 从开发态硬化为生产编排(去除默认 admin 密码与 host 网络,纳入主 compose)。

- **[P1] B 组 异常原因结构化**: 在 `AuditEntry` 增加结构化错误码/异常原因列(参照 ingestion 的 `failureCategory/errorMessage/failureAdvice`),失败审计统一写入。

- **[P2] B 组 目标IP**: 评估是否新增 `server_ip`/`target_ip` 字段以严格满足协议"目标IP"字面要求(当前 requestUri+method 可间接定位)。

- **[P2] A4 主动化**: 将已实现的采集执行观测指标桥接到 Prometheus,使被动看板升级为主动阈值告警,与 A5 协同。
