## 3) 数据标签管理(标签+标签目录 / 预置常用标签 / 自定义 / 对数据资源打标)

**status: 🔴 gap (真缺口,前序即缺,4月以来未补)**

核验:
- **仍未找到任何 DataTag/DataLabel/CatalogTag/AssetTag/TagCatalog/TagDefinition domain 或 service**。`grep -rilE "class.*(DataTag|DataLabel|CatalogTag|AssetTag|TagDefinition|TagCatalog)"` 仅命中无关的 `dts-admin/.../ChangeSnapshotFormatter.java`
- 现状只有 `CatalogDataset.tags`(`domain/catalog/CatalogDataset.java:48` 一个 `@Column(name="tags", length=1024)` 自由文本字段),`CatalogAssetPortalService` 仅对该自由文本做 `like` 模糊查询(`:465`),`CatalogMetadataService` 仅把 `dataset.getTags()` 透传(`:191/:238/:253`)
- 前端无标签管理页: `pages/catalog/` 下无 tag/label 页;`ui/label.tsx` 是通用 UI label,`analytics/.../ClassificationTag.tsx` 是密级标记,均非数据标签管理
- 无标签目录、无预置常用标签库、无标签 CRUD、无"对数据资源打标"的结构化关系表(无 tag-asset 多对多)

结论: **自由文本 tags 字段 ≠ 协议要求的标签管理体系**。前序判断"未找到 DataTag/DataLabel domain"在当前代码仍成立。

缺什么:

- 预置常用标签 seed
- 标签自定义 CRUD + 审计

优先级: **P1**(协议明列子能力,业务价值高且明确;非合规硬约束故非 P0)

落地包建议: 新建 `domain/catalog/CatalogTag` + `CatalogTagCategory` + `CatalogAssetTag`(关联表),`service/catalog/CatalogTagService`(目录/CRUD/打标/seed 预置标签),`web/rest/catalog/CatalogTagResource`,Liquibase changelog 三表 + 唯一约束,前端 `pages/catalog/TagsPage.tsx` + 资产详情打标组件 + 按标签检索接入 `DataSearchPage`。

缺口部分:
- **6 阶段(创建/存储/使用/共享/归档/销毁)审批不完整**: 当前生命周期请求仅支持 `ARCHIVE / DISPOSE / EXTEND_RETENTION` 三种 requestType(`CatalogLifecycleRequestService.java:50-52,346`)。"创建/存储"阶段无独立审批入口;"使用/共享"由另一套 `DatasetDataAccessApprovalService` 承担(链路分散,非统一 6 阶段闭环);只有"归档/销毁/延期"走 `CatalogLifecycleRequest`。**协议要求的"各阶段审批通过后才能执行"未形成统一闭环**。

优先级: **P0**(协议为"通过审批后才能执行"的合规硬约束 + 量化监控要求)

落地包建议:
- 统一生命周期阶段模型: 扩展 `CatalogLifecycleRequest.requestType` 覆盖 创建/存储/使用/共享/归档/销毁,或建立统一编排把 `DatasetDataAccessApprovalService`(使用/共享)纳入同一生命周期视图;每阶段"审批通过后执行"显式 gate。
- 新增资产生命周期监控: `GovernanceOpsMetricsService` 增 lifecycle 维度聚合(按 lifecycleStatus 统计在用/共享/归档/销毁数据量 + trend),前端新增专项仪表盘卡片。

## 6) 数据销毁(临时 + 永久,临时可一键还原)

**status: 🔴 gap**

核验:
- 当前"销毁"= `TYPE_DISPOSE`,审批通过后 `applyApprovedChange`(`CatalogLifecycleRequestService.java:293-301`)仅做: `dataset.setLifecycleStatus("DISPOSED")` + `dataset.setEnabled(false)` —— **纯逻辑软禁用,无物理删除**。
- **无临时 vs 永久销毁的区分**: 只有单一 DISPOSE,无 temp-trash/permanent-hard-delete 两态。
- **无一键还原(沙箱)**: `revertDataset`(`:313`)只在**拒绝一个 pending 请求**时把 dataset 状态回滚,**不是对已销毁数据的一键恢复**;无回收站/trash/soft-delete+restore 机制(`grep softDelete/trash/recycleBin/一键还原/临时销毁` 在 dataset 销毁链路无命中,命中项均为参考码/SQL 执行等无关代码)。
- 永久销毁(物理 drop 表/数据)无实现。

结论: 前序"销毁沙箱(临时trash+还原+永久硬删)"缺口完全成立,4 月以来无任何进展。

缺什么:
- 销毁双态: 临时销毁(进回收站,可还原,带保留期)+ 永久销毁(物理硬删,不可逆,需更高审批)
- 一键还原: 回收站列表 + restore API + 还原审计
- 永久销毁执行器: 审批通过后物理 drop/purge + 不可逆确认 + 审计留痕

优先级: **P0**(销毁/还原是数据合规与可逆性硬约束)

落地包建议: `CatalogDataset` 增 `trashedAt`/`destroyType`(TEMP/PERMANENT)/`purgedAt`;`CatalogLifecycleRequestService` 把 DISPOSE 拆为 `DISPOSE_TEMP`(软删入回收站)+ `DISPOSE_PERMANENT`(经二次审批后物理 purge);新增 `restore` API + 回收站资源 + 前端回收站页;永久销毁执行器对接底层存储 drop,全程审计。
