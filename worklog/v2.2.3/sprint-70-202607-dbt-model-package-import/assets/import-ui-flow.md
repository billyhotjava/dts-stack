# 导入向导 UI 设计

## 1. 入口

### 建模工作台

在当前计划卡片的动作区增加次主按钮“导入已有模型”：

- 与“查看计划详情/下一步”同属当前计划操作，不放在全局导航。
- 未选择计划、计划只读或已归档时禁用，并显示具体原因。
- 点击后固定当前 `planId`，不能在向导中静默切换。

```text
┌──────────────────────── 当前计划 ────────────────────────┐
│ PJM 数据建设计划                    规划中 · 负责人       │
├──────────────────────────────────────────────────────────┤
│ 当前阶段：事实与维度                                     │
│ 首要阻塞：模型尚未建立                                   │
│                                                          │
│ [查看计划详情]  [导入已有模型]        [进入模型中心 →]   │
└──────────────────────────────────────────────────────────┘
```

“进入模型中心”保持当前阶段的主动作；“导入已有模型”是同阶段的替代路径，使用描边次按钮，不能抢占首次用户的主动作。

### 模型中心

在“新建模型”旁增加“导入模型包”次按钮：

- 带 `planId` 进入时锁定计划。
- 无计划上下文时，向导第一步要求明确选择计划。
- 两个入口打开同一组件和同一 API，不维护两套状态。

### 高级 SQL/dbt

保留现有导入和批量导入作为专家兼容入口，并增加指向新模型包向导的说明；不新增一级菜单。

## 2. 四步向导

桌面端使用宽抽屉或独立工作区式弹层，顶部显示步骤，主体显示当前步骤，底部固定“上一步/下一步/确认导入”。不要把四步堆叠在一个长表单里。

```text
┌──────────────── 导入已有模型 ────────────────────────────┐
│ ① 上传模型包 ─ ② 建设上下文 ─ ③ 预检确认 ─ ④ 导入结果 │
├──────────────────────────────────────────────────────────┤
│                                                          │
│                  当前步骤的主要内容                      │
│                                                          │
├──────────────────────────────────────────────────────────┤
│                         [取消] [上一步] [下一步/确认导入] │
└──────────────────────────────────────────────────────────┘
```

### 第一步：上传模型包

- 支持 `.json`，显示 schemaVersion、项目名、生成时间、模型数和 checksum。
- 文件解析失败时不进入下一步。
- 提供“如何从 dbt 项目生成模型包”帮助链接。

### 第二步：确认建设上下文

- 显示并锁定建设计划。
- 按包内稳定 code 映射业务分类。
- 将 dbt source relation 映射到计划内已确认 SourceBinding。
- 缺失项就地显示“前往规划来源/业务分类”，安全返回后刷新，不清空上传结果。

### 第三步：预检矩阵

表格列：

- dbt 节点、DTS 模型名称。
- 模型类型/目标层。
- 转换方式。
- 来源与上游。
- 动作：新增、更新、跳过、冲突、阻断。
- 问题和修复入口。

默认只选 `READY` 候选；`BLOCKED` 不允许勾选。点击行可查看粒度、字段、依赖和 SQL/配置差异。

### 第四步：确认与结果

确认前汇总新增、更新、跳过、阻断数量。提交后显示逐项终态：

- `CREATED / UPDATED / REPLAYED / SKIPPED / FAILED`
- ModelSpec revision、implementation revision。
- “查看模型”“返回当前计划”“仅重试失败项”。

## 3. 交互与文案原则

- 使用业务名称，不要求用户复制 UUID、checksum 或 dbt unique ID。
- “普通模型”和“dbt 实现”同时展示：例如“已创建应用表，SQL 实现由 dbt 管理”。
- 不把预检成功称为导入成功。
- 不通过 toast 代替批次结果页。
- 不提供“清理旧文件”这类与 canonical 导入无关的危险选项。
- 页面刷新或关闭后可通过 runId 恢复预检/结果。

## 4. 响应式与可访问性

- Chrome 95 桌面端完整矩阵；窄屏改为按候选折叠卡片。
- 步骤状态、问题严重度和转换方式不能只靠颜色表达。
- 上传、预检、应用均支持键盘操作和明确 loading/disabled 状态。
- 长模型名、问题信息和 dependency chain 可展开，不横向挤压主要动作。
