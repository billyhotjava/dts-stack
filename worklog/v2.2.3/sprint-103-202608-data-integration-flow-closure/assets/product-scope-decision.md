# ADR-103-01：数据集成流程优先于通用可视化编排

状态：`ACCEPTED`（2026-08-29 补充范围裁决）
日期：2026-08-27；补充裁决：2026-08-29

## 决策

Sprint-103 不建设通用 workflow 编辑器，也不把现有 `graphDsl` 编译为新的执行事实。现有页面收敛为“数据集成流程”：

1. 数据源、目标数据资产、字段映射、调度和可选“接入后质量验证”由类型化表单编辑。
2. `IngestionTask` 草稿与 `IngestionTaskRevision` 是唯一配置事实源。
3. 服务端从指定草稿或版本自动生成只读拓扑投影。
4. 发布、调度和运行继续复用现有 admission、DAG 与 execution owner。
5. 旧 DSL 仅兼容读取/导出，不可发布；自由拖拽编辑从 P0 范围移除。

### 2026-08-29 补充裁决

- “数据集成”是当前版本唯一业务入口，统一承载接入概览、连接管理、任务详情、版本发布、调度和任务级运行记录。
- 独立“任务编排”菜单、列表、编辑器、拓扑画布和运行页全部退役，不再以改名方式保留第二个业务工作台。
- 旧地址 `/explore/etl/orchestration` 仅作兼容跳转：普通访问回到接入概览；携带合法 `taskId` 时回到对应接入任务详情。
- 通用 Airflow 实例仍属于运维域，并通过运维入口按 `AIRFLOW_DAG` 过滤，不作为业务任务入口。
- 已落地的任务版本、准入、调度、执行、质量与资产证据后端契约继续保留。它们是数据集成闭环的基础，也是后续增值版多任务编排可复用的执行边界，不单独对客户暴露编排产品承诺。

## 为什么

- 当前 7 条活跃任务没有证据表明需要分支、汇聚或跨作业依赖。
- 当前库中对象型 DSL 为 0，现有 DSL 也没有执行消费者。
- 接入任务已有真实的配置、版本、准入和运行链路；另建 DSL 编译链会产生双事实源。
- 当前页面暴露 transform/loop/iteration/event/rollback 等没有正式 owner 的能力，会形成产品过度承诺。
- 线性接入任务用表单配置效率更高，拓扑更适合作为理解、校验和诊断投影。

## 能力分层

| 层次 | 本 Sprint 结论 | 进入条件 |
|---|---|---|
| 数据接入 E/L | 建设 | 现有任务、connector、mapping、schedule 契约 |
| 接入后质量验证 | 建设 | 目标必须解析为同一 `dataset:<uuid>`；只在接入 execution 提交成功后触发正式质量 workflow |
| ELT 转换 | 暂缓 | 必须引用已发布、版本化转换制品，禁止内联任意代码 |
| 多任务 DAG | 暂缓 | 真实依赖复杂度证据通过下方门槛 |
| 领域 workflow | 不纳入 | 继续由建模、质量、审批等各自状态机/账本负责 |

## 可编辑 DAG 需求门槛

F0/T01 必须盘点全部活跃任务并收集客户真实流程；只有同时满足以下条件，才允许另立 Feature/Sprint 设计可编辑 DAG：

- 至少 3 条真实流程需要编排多个已发布作业，而不是一个任务内部的源到目标配置。
- 存在表单无法表达的 fan-out、fan-in、条件依赖或跨作业前后置关系。
- 有明确用户角色、调整频率、失败恢复方式和验收样本。
- 节点只引用稳定的已发布任务/制品 ID，各节点已有唯一执行 owner。
- 调度、幂等、重试、取消、变量、凭据、审计和迁移边界可形成完整契约。

若门槛未通过，拓扑保持只读；不能因为画布代码已经存在就继续投资自由编排。

## 接入质量与资产边界

- 数据资产身份在正式质量运行前就必须存在，并统一使用 `CatalogAssetType.DATASET + CatalogAssetKey`；不得为编排页面创建第二套资产 ID。
- 接入过程只执行连接、映射、schema/type、权限、密级与暂存区校验。这些结果决定本次接入能否继续，但不等同于正式资产质量证据。
- 一次 execution 对应的批次/分区/快照提交成功后，才异步触发质量域正式 workflow；质量失败不能反写接入 execution 为失败。
- 当前 `qualityPolicyRef` 的兼容格式是 `dataset:<uuid>`。页面让用户选择目标资产并开启“接入后质量验证”，不提供一个与目标资产无关的任意“策略”选择器。
- 不新增 `TRUSTED`、`VERIFIED` 等资产生命周期枚举。“可信可用”仅在当前 execution 的正式质量证据为 `PASSED` 且消费资格为 `ELIGIBLE` 时派生展示。
- 新 execution 提交成功后，旧批次的 `PASSED` 不能继续冒充当前证据；当前证据必须显式经历 `PENDING/CURRENT/STALE/TRIGGER_FAILED` 等新鲜度状态。

完整契约见 [ADR-103-02](quality-asset-integration-contract.md)。

## 页面策略

- 业务菜单只保留“数据集成”；不再显示“任务编排”或平行的数据集成流程入口。
- 接入概览负责查找和新建任务，任务详情负责配置、校验、发布、调度和任务级运行记录。
- `/explore/etl/orchestration` 只兼容历史书签，不承载新功能，也不透传无关查询参数。
- 运维回填、告警和 Airflow 实例留在运维域；业务操作始终以 `taskId` 为身份，不能用任意 `dagId` 替代。

## 后果

### 正向

- 立即消除 DSL 与实际运行配置漂移的架构风险。
- 复用现有 owner，缩小迁移、测试、安全和运维成本。
- 页面承诺与当前后端能力一致，客户不会看到不可执行节点。
- 后续仍可从版本化任务投影依赖图，不封死演进路径。

### 代价

- Sprint-29 已建拖拽组件及 Sprint-103 独立编排页面代码退役；未来如重新立项，应基于真实多任务依赖重新设计，不能直接恢复旧画布。
- 首版不满足希望自由编排多任务 DAG 的高级用户。
- 必须补齐现有任务配置表单的复用与一致性，而不是只改画布外观。

## 明确不做

- 不把 Airflow Web UI 包装成业务任务编排器。
- 不创建 `workflow_definition/workflow_node` 等平行聚合。
- 不在图节点内存储凭据、规则 JSON、任意 SQL/Python/Spark。
- 不通过前端隐藏替代后端权限、密级与准入控制。
