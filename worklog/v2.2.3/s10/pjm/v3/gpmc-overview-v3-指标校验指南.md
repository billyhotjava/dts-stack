# `gpmc-overview-v3` 指标校验指南

## 1. 先说结论

这次总览屏的核心校验材料，按最容易理解的方式重写成了 2 份：

- `gpmc-overview-v3-指标血缘说明.md`
- `gpmc-overview-v3-指标校验-postgres.sql`

建议使用顺序：

1. 先看血缘说明，知道每个指标从哪张表来的。
2. 再跑最简 SQL，直接核对页面数字。
3. 如果页面值不对，再按血缘往回查 DWS、DWD、ODS。

## 2. 这张屏现在到底走哪一层

`gpmc-overview-v3.json` 当前**没有走 ADS**。

实际链路是：

- 进度：`ODS -> STG -> DWD -> DWS -> 页面`
- 质量：`ODS -> STG -> DWD -> DWS -> 页面`
- 技术状态：`ODS -> STG -> DWD -> DWS -> 页面`
- 风险：`ODS -> STG -> DWD -> DWS -> 页面`

只有甘特图和科室下拉会直接查 DWD。

所以做这张屏的校验时，重点不是 ADS，而是：

- ODS 原始字段有没有进 DWD
- DWD 布尔/日期衍生字段算得对不对
- DWS 月汇总字段有没有按预期聚合
- 页面 SQL 有没有把这些字段用对

## 3. 两份文件分别干什么

### 3.1 `gpmc-overview-v3-指标血缘说明.md`

适合先看这个文件的人：

- 业务
- 测试
- 只懂一般 SQL 的同事
- 需要解释“为什么这个值是这样算出来的”的人

这个文件解决的问题：

- 页面上的每个指标，对应哪张表
- 该字段在上一层是怎么来的
- 如果值错了，先查哪一层

### 3.2 `gpmc-overview-v3-指标校验-postgres.sql`

适合直接跑 SQL 的人。

这个文件的特点：

- 只保留最简单的 SQL
- 不用参数表
- 不用模板语法
- 直接复制到 PostgreSQL 客户端就能执行

你只需要改每段 SQL 里的日期常量，例如：

- `'2025-01'`
- `'2025-12'`

如果要限定单个项目或科室，就把注释的过滤条件打开。

## 4. 最简单的校验方法

拿总览屏来说，建议按下面顺序校验：

1. 先核对顶部/底部数字卡
   - 项目总数
   - 进行中项目
   - 项目完成率
   - 现存质量问题
   - 未整改技术项
   - 高风险总数
2. 再核对 8 张中间图
   - 进度按项目
   - 进度按科室
   - 质量按项目
   - 质量按科室
   - 技术状态按项目
   - 技术状态按科室
   - 风险按项目
   - 风险按科室
3. 最后核对 2 个交互项
   - 甘特图
   - 科室筛选

## 5. 如果页面值不对，怎么回查

### 5.1 数字卡不对

先查 DWS。

例如：

- 项目总数/进行中项目/项目完成率：先查 `biz_dws_progress_monthly_v2`
- 现存质量问题：先查 `biz_dws_quality_monthly_v2`
- 未整改技术项：先查 `biz_dws_tech_state_monthly_v2`
- 高风险总数：先查 `biz_dws_risk_monthly_v2`

如果 DWS 就不对，再往 DWD 查明细。

### 5.2 图表不对

先看图表 SQL 的分组键。

例如：

- 按项目图：`GROUP BY project_no`
- 按科室图：`GROUP BY dept`

很多时候不是数据错，而是：

- 分组键选错
- 空值过滤没处理
- 时间字段用错

### 5.3 甘特图不对

先分成两步：

1. 先查“活跃项目列表”
   - 看哪些 `project_no` 被选进来了
2. 再查某个项目的节点明细
   - 看 `plan_start_date`
   - 看 `plan_date`
   - 看 `actual_start_date`
   - 看 `actual_date`
   - 看 `is_incomplete`

## 6. 这套材料的定位

这套材料的目标不是“100% 复刻页面实现细节”，而是：

- 让普通 SQL 使用者能先看懂
- 让业务和测试能独立校验
- 让排查时知道往哪一层回溯

如果后面确实还需要“页面同构 SQL”，再单独补一份更贴近 JSON 模板的版本，不和最简校验 SQL 混在一起。
