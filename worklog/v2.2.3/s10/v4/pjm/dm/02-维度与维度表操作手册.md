# 维度与维度表操作手册

## 1. 先理解两个对象

- “维度”是业务概念定义，例如“风险等级”。它先形成可确认、可修订的定义。
- “维度表”是该定义的物理/逻辑实现，例如 `dim_risk_level_v2`。它必须绑定一个 CURRENT 维度定义的固定修订。

正确顺序是：

```text
新建维度定义 → 保存草稿 → 确认定义 → 新建/导入维度表 → 绑定固定定义修订 → 字段设计 → 实现与发布
```

不要跳过维度定义直接把字典 SQL 当成维度表发布。

## 2. 当前需要的 8 个业务维度

| 维度中文名 | 建议数据域 | 物理表名 | 稳定主键 | 当前使用方 |
|---|---|---|---|---|
| 节点完成状态 | 研究项目域 | `dim_completion_status_v2` | `completion_status_id` | 项目节点 DWD |
| 节点类型 | 研究项目域 | `dim_node_type_v2` | `node_type_id` | 项目节点 DWD |
| 风险等级 | 研究项目域 | `dim_risk_level_v2` | `risk_level_id` | 项目节点、项目风险 DWD |
| 质量归零状态 | 质量管理域 | `dim_quality_status_v2` | `quality_status_id` | 质量问题 DWD |
| 质量问题原因分类 | 质量管理域 | `dim_quality_category_v2` | `quality_category_id` | 质量问题 DWD |
| 技术更改类别 | 产品技术域 | `dim_change_category_v2` | `change_category_id` | 技术状态 DWD |
| 文件签署状态 | 产品技术域 | `dim_signature_status_v2` | `signature_status_id` | 技术状态 DWD |
| 项目风险分类 | 研究项目域 | `dim_risk_category_v2` | `risk_category_id` | 项目风险 DWD |

当前模型定义的复用范围默认是数据域。风险等级虽然未来也可能服务物料供应域，本批不得跨域硬绑；二期应先决定是建立物料域自己的维度，还是扩展为经批准的跨域复用。

## 3. Step 1：逐个创建并确认维度定义

对上表每个维度重复以下操作：

1. 进入“数据建模 → 模型工作台”。
2. 点击新建，选择“维度”，不是“维度表”。
3. 填写：

| 页面字段 | 填写规则 |
|---|---|
| 数仓分层 | 系统显示“公共层 / 维度层”，不可修改 |
| 数据域 | 按上表选择 |
| 系统编码 | 系统生成，不手工猜测 |
| 中文名称 | 使用上表“维度中文名” |
| 描述 | 必填；写清维度用于统一什么概念、值由谁维护、未知值怎么处理 |

4. 点击“保存”，确认状态仍为 DRAFT。
5. 复核名称、数据域和描述。
6. 点击“确认定义”。确认后该修订成为维度表可绑定的 CURRENT 定义。

描述示例：

> 风险等级用于统一项目风险严重程度的高、中、低分级。标准值由项目风险管理责任人维护，源端别名经映射后进入本维度；未命中值不得自动归为低风险。

## 4. Step 2：准备维度值和字段

所有维度表至少包含：

| 字段 | 角色 | 规则 |
|---|---|---|
| `*_id` | KEY | 稳定 ASCII 标识，非空、唯一；跨表关联使用它 |
| `code` | ATTRIBUTE | 当前 dbt 兼容代码，可能为中文，不作为新跨表主键 |
| `label` | ATTRIBUTE | 中文显示名，非空 |
| `sort_order` 或 `severity_rank` | ATTRIBUTE | 展示/严重度顺序 |
| `is_*` / `cat_*` | ATTRIBUTE | 由 canonical 维度值维护的判断标志 |

## 5. Step 3：登记维度表 ModelSpec

当前 PJM 维度表已有 dbt SQL，推荐走 [06-dbt导入发布与验收手册.md](06-dbt导入发布与验收手册.md) 的逆向建模路径。导入或补录后，对每张维度表检查：

| 页面字段 | 应有值 |
|---|---|
| 数仓分层 | 公共层 / 维度层（DWD） |
| 数据域 | 与维度定义一致 |
| 存储策略 | `table`；加载策略为全量 |
| 实现来源 | 当前静态维度应为已关联 dbt/上游实现；不能显示“待配置”后直接发布 |
| 维度 | 绑定对应 CURRENT 维度定义的固定修订 |
| 表名 | 上表给出的 `dim_*_v2` |
| 表中文名 | 对应维度名 + “维度表” |
| 描述（维度定义） | 必填，与概念定义一致但补充物理维护规则 |
| 字段 | 至少一个 KEY；每个字段有技术名、类型和中文显示名 |

字段类型建议：ID/code/label/适用类别为 `STRING`，布尔标志为 `BOOLEAN`，排序/严重度为 `INT`。

现有页面只为日期维度提供“受控日期维度生成器”。普通维度的新建表单没有物理来源选择器，而物理表名又是必填项，因此仅靠该表单无法从零保存这 8 张普通维度表的完整实现。必须先通过 dbt 逆向导入或已批准的服务端关联流程建立来源/实现及维度定义绑定；不能把“待配置”写成已完成。

## 6. Alias 辅助表的处理

当前 dbt 还有 10 张 alias 表：节点类型、风险等级、风险分类、风险状态、质量分类、质量状态、更改类别、布尔、整改状态、文件签署状态别名表。

它们的职责是把源端写法映射到 canonical code，不是 10 个新的业务维度概念。处理规则：

1. 随 dbt 包作为 DWD 技术辅助模型导入。
2. 不为每张 alias 表创建同名业务维度定义。
3. 映射键通常为 `alias_raw`；文件签署状态还包含 `context`，两者共同决定映射。
4. 未命中值进入数据质量问题，不得静默映射为低风险、已完成等有利状态。
5. alias 表变更后必须重新测试受影响 DWD 模型。

## 7. 维度验收清单

- [ ] 8 个维度定义均为 CURRENT，描述非空。
- [ ] 每张维度表固定绑定正确的维度定义 ID 和修订。
- [ ] `*_id` 为 ASCII、非空、唯一，并标记 KEY。
- [ ] 每个字段都有中文显示名；技术编码仅使用小写字母、数字和下划线。
- [ ] 普通维度有真实来源/上游实现；日期维度才可使用受控生成器。
- [ ] 维度历史策略已明确；当前静态字典按全量 + Type 1 使用，不伪造 Type 2 历史。
- [ ] alias 映射和 canonical 维度职责分离。
- [ ] DWD FACT 引用的是维度模型固定修订，而不是中文文本临时连接。
