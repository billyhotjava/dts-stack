# 二期扩展表设计清单

## 1. 当前状态

以下 5 张表已在 `pm_sources_v2.yml` 注册，但没有 STG、DWD、DWS、ADS SQL：

- `ods_progress_measure_v2`
- `ods_quality_measure_v2`
- `ods_tech_state_measure_v2`
- `ods_risk_measure_v2`
- `ods_material_info_v2`

它们不是本期已完成模型。本文件只给出二期设计和实施顺序，必须在业务键、时间语义和口径确认后再编码、导入和发布。

## 2. 二期统一实施步骤

1. 让源系统提供稳定业务 ID；不要直接把 ODS `serial id` 当成跨批次业务键。
2. 通过样本验证候选粒度唯一性、空值率、重复率和晚到更新方式。
3. 确认业务过程、事实形态和业务时间字段。
4. 补充需要的 canonical 维度与 alias 映射，不在 FACT 中硬编码中文判断。
5. 新建 STG `view`：只做占位符收敛、类型转换、字段改名和来源追溯。
6. 新建 DWD `table`：统一维度键、状态、闭环时长和派生口径。
7. 经业务指标需求确认后再建 DWS/ADS；没有消费需求时停在 DWD，不为“层次齐全”制造空表。
8. 更新 `pm_stg_v2.yml`、`pm_schema_v2.yml` 测试和中文说明。
9. 重新打包，走逆向建模预览、应用、设计检查、构建、测试和发布。

## 3. 项目跟进措施

### 3.1 来源分析

`ods_progress_measure_v2` 有 23 个业务字段：

- 父节点上下文：`project_no`、`subsystem`、`node_task`、`plan_date`、`plan_week`、`completion_status`。
- 措施主体：`measure_category`、`measure_title`、`follow_up_person`、`main_recipient`、`cc_recipient`。
- 跟进/闭环时间：`follow_up_date`、`follow_up_week`、`closure_status`、`final_closure_date`、`final_closure_week`。
- 交付和风险：`closure_deliverable_type`、`closure_deliverable`、`risk_content`、`remark`。
- 更新责任：`last_update_time`、`last_update_week`、`filled_by`。

### 3.2 建议模型

| 项目 | 建议值 |
|---|---|
| 数据域 / 业务过程 | 研究项目域 / 项目跟进闭环 |
| STG | `stg_pm__progress_measure_v2` |
| DWD | `biz_dwd_project_follow_up_v2` |
| 粒度 | 一条独立跟进措施一行 |
| 事实形态 | 累积快照 |
| 时间语义 | 跟进日期、最终闭环日期、最后更新时间 |
| 建议 DWS | `biz_dws_project_follow_up_monthly_v2`，项目×跟进月份 |
| 可选 ADS | `biz_ads_project_follow_up_kpi_v2`，措施数、闭环数、闭环率、平均闭环天数 |

阻断：源表没有 `measure_id`。`project_no + node_task + measure_title + follow_up_date` 只能作为待验证候选键，未证明唯一前不得做增量模型。

### 4.1 来源分析

`ods_quality_measure_v2` 把质量问题上下文和措施字段放在一行：

- 闭环：`follow_up_date/week`、`closure_status`、`final_closure_date/week`、`closure_deliverable_type`、`closure_deliverable`。
- 追溯：`risk_content`、`last_update_time/week`、`remark`、`filled_by`。

### 4.2 建议模型

| 项目 | 建议值 |
|---|---|
| 数据域 / 业务过程 | 质量管理域 / 质量措施闭环 |
| STG | `stg_pm__quality_measure_v2` |
| DWD | `biz_dwd_quality_measure_v2` |
| 粒度 | 一条质量问题跟进措施一行 |
| 事实形态 | 累积快照 |

## 7. 重要物料交付跟踪

### 7.1 来源分析

`ods_material_info_v2` 有 29 个业务字段：

- 物料身份：`project_no`、`subsystem`、`pbs_no`、`pbs_name`、`self_or_outsource`、`supplier_name`、`is_long_cycle`。
- 合同/交付：合同谈判、合同要求到货、实际到货的日期和周数。
- 检验/上装：计划检验、完成检验、上装的日期和周数。
- 责任和进展：`dept_owner`、`control_dept_owner`、`weekly_progress`。
- 风险：`affects_major_node`、`risk_level`、`risk_content`、`delay_impact`。
- 追溯：`last_update_time`、`last_update_week`、`remark`。

### 7.2 建议模型

| 项目 | 建议值 |
|---|---|
| 数据域 / 业务过程 | 物料供应域 / 重要物料交付跟踪 |
| STG | `stg_pm__material_info_v2` |
| DWD | `biz_dwd_material_delivery_v2` |
| 粒度 | 一个项目×PBS 物料一行 |
| 候选 KEY | `project_no + pbs_no`，必须用样本证明唯一 |
| 事实形态 | 累积快照 |
| 时间语义 | 合同要求、实际到货、检验、上装等里程碑日期 |
| 建议 DWS | `biz_dws_material_delivery_monthly_v2`，项目×责任部门×合同到货月份 |
| 可选 ADS | `biz_ads_material_delivery_kpi_v2`，按期到货率、逾期未到货数、长周期高风险数 |

阻断：`pbs_no` 是否项目内唯一、同一物料是否会产生多供应商/多批次记录尚未确认。如果存在批次，粒度和键必须加入采购订单/合同/批次 ID。`last_update_time` 是状态更新时间，不等同每日快照日期。

## 8. 二期维度候选

只有经过数据画像和责任人确认后再建：

- 措施类别、闭环状态、闭环交付物类别；
- 供应商、PBS 物料、自研/外协、长周期标志；
- 项目、组织、人员等公共主数据维度。

新维度继续使用稳定 ASCII `*_id`，中文只作为 label。源端别名放 alias 映射，不把自然语言直接作为事实外键。

## 9. 二期 DoR/DoD

### DoR

- [ ] 每张表有稳定业务 ID 或已证明唯一的自然键。
- [ ] 业务过程、事实形态、时间语义和晚到更新规则已确认。
- [ ] 父事实与措施事实的计数边界清楚，不会重复统计。
- [ ] 枚举值画像完成，canonical/alias 维度责任人明确。
- [ ] DWS/ADS 有真实消费需求和经确认指标口径。

### DoD

- [ ] 5 张 STG 和 DWD SQL、schema 测试、中文字段说明已实现。
- [ ] 依赖规则满足 ODS→STG→DWD→DWS→ADS，没有跨层直读。
- [ ] 模型通过逆向导入、DESIGNED、IMPLEMENTATION_READY 和 RELEASE_READY。
- [ ] 目标环境运行与数据对账通过。
- [ ] 真实账号完成菜单点击、审计和发布验收后，才标记交付。
