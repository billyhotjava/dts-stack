## 一、文档定位

| 项 | 定调 |
|---|---|
| 读者 | 双读者：① 所领导/科室领导（组织、制度、路线图）② 业务操作人员（填报与日常治理动作的操作指引） |
| 主线 | **以项目、财务为双核心数据域的治理**——单个项目金额高，项目与财务是价值密度最高的两块数据，治理资源优先投入这两域；"业财一体化（项目-财务贯通）"仅作为**远期演进方向**表述，不作为承诺目标（现场复杂，客户不一定能做到） |
| 组件表述 | 一律使用通用能力名称（数据集成、主数据管理、元数据管理、数据质量管理等），**不出现**具体产品/组件名；唯一例外：**达梦**（冷备归档库，点名） |
| 现状与目标 | 两段式表述：现状能力如实陈述（Excel 离线填报为主、应用系统建设中），能力缺口全部写入分期路线图，不把规划写成"已具备" |
| 框架对标 | 正文不按 DCMM 逐域展开；DCMM 对标表放附录 |
| 保密 | 研究所保密程度非常高：封面/页眉留密级占位（由客户保密办定级）；安全章节写制度级深度，与所内保密制度做"衔接性引用"而非替代 |
| 业务域范围 | 项目管控（进度/质量/风险/技术状态）、财务（项目财务/项目预算）为双核心，采购、库存为支撑；专利、考勤为辅 |
| 未来源系统 | PLM、ERP（采购/库存/项目财务）、QMS 作为规划接入系统写入蓝图与路线图 |

### 2.2 行文规则

1. 每章开头 1 段"本章导读"（领导可只读导读）；治理域各章末尾附"业务人员须知"框（操作视角摘要，业务语言）。
2. 流程一律给出：角色 × 步骤 × 表单/记录三要素；配泳道图或步骤表。
3. 数据模型细节（DDL、字段映射）不进正文，收进附录索引，正文只引用结论与规则。
4. 质量考核相关表述全部遵循"三步走"节奏（通报→评价参考→正式挂钩），任何章节不得出现一步到位的考核措辞。
5. 页码预算写进各章标题后括号，成文时据此控制篇幅。
6. "业财一体化"措辞管控：全文只在"远期演进方向/蓝图"语境下出现，配"视系统建设与数据成熟度分步推进"限定语；任何章节不得将其写成阶段目标或承诺成果。近期表述统一用"项目、财务两域数据优先治理""财务数据按项目维度可查可算"。

## 三、章节详细提纲（含素材映射）

### 第一篇 总体篇（约 15 页）

**第1章 背景与现状诊断（4页）**
- 1.1 背景：项目型科研院所的数据管理挑战；单项目金额高，项目与财务是价值密度最高、治理优先级最高的两块数据
- 1.2 数据现状盘点：数据源全景（9 类数据源、45 张源表规模——引 v4 文档"数据源全景"），Excel 离线填报占比高、在线系统（PLM/ERP/QMS）建设中
- 1.3 现状问题诊断：口径不一、别名混乱（同一科室/人员/项目多种写法）、填报质量依赖个人、跨域数据（预算-采购-成本）无法按项目贯通、缺少制度与责任体系
- 1.4 治理必要性：先立标准与制度，再接系统——避免"垃圾进垃圾出"
- 素材：`数据管理平台数据模型v4.md`（数据源全景、更新策略）、别名归一化实践（model-governance.md alias dim 清单反推现状问题）

**第2章 治理目标与总体框架（4页）**
- 2.1 总体目标与阶段目标（对应三期路线）
- 2.2 总体框架图：一横一纵——横轴为业务数据域（**项目、财务双核心**，采购/库存/质量/专利/考勤为支撑域），纵轴为治理能力域（标准/模型/主数据/指标/元数据/质量/安全/生命周期/共享）；项目-财务贯通（业财一体化）在图中以虚线标注为远期演进方向
- 2.3 数据架构总览：源系统（现状 Excel + 规划 PLM/ERP/QMS）→ 数据集成 → 分层数据仓库（贴源/结构化/明细/汇总/应用五层，通用化表述）→ 数据服务（看板/接口）
- 2.4 治理原则：源头可追溯、口径唯一真值源、指标定义先于实现、循序渐进
- 素材：v4 文档"分层架构全景"、pjm/finance 两份 model-governance.md 的治理原则章

**第3章 组织与职责（4页）**
- 3.1 三层治理组织：数据治理领导小组（所级，决策）→ 数据管理办公室（归口科室，日常运营）→ 科室数据专员（各业务科室兼职，填报质量与业务口径第一责任人）
- 3.2 角色职责矩阵（RACI）：覆盖标准发布、模型评审、主数据确认、质量整改、共享审批、销毁审批等关键事项
- 3.3 与保密管理体系的衔接：数据定密、涉密数据操作、销毁监督由保密体系主导，数据治理组织配合执行——明确职责边界，不越权
- 3.4 运行机制：月度数据质量例会、季度治理评审
- 素材：客户组织结构（所-科室-职员）；无现成素材，本章为新写

**第4章 制度体系（3页）**
- 4.1 三级制度框架：管理办法（所级发文，1 份）→ 实施细则（各治理域各 1 份，本方案第二篇即蓝本）→ 操作规程/表单（操作级）
- 4.2 制度清单与制定优先级（与三期路线对齐：一期先出标准管理、质量管理、填报规范三份细则）
- 4.3 制度的发布、修订与废止流程
- 素材：新写

### 第二篇 治理域篇（约 40 页）

**第5章 数据标准管理（5页）**
- 5.1 标准体系构成：命名规范、数据类型标准、枚举值域标准、编码规范（四类，直接通用化改写 v4 文档"数据标准体系"节）
- 5.2 关键标准摘编：分层命名规则、枚举值域示例（完成情况/风险等级/闭环状态等 9 类枚举——正文摘要，全量进附录）
- 5.3 标准管理流程：提出→数据管理办公室初审→相关科室会签→领导小组发布→修订归档；标准变更须评估下游影响
- 5.4 业务人员须知：填报时只能使用标准值域（下拉选择），新增值域走申请流程而非自造写法
- 素材：v4 文档"数据标准体系"全节

**第6章 数据架构与模型管理（4页）**
- 6.1 分层架构与各层职责：贴源层只落地不解释、结构化层只做类型收敛不引入业务语义、明细层承载业务解释与口径、汇总层沉淀主题汇总、应用层面向消费——把"STG 宪法"改写为通用的**分层红线规则**（允许做/禁止做清单）
- 6.2 依赖红线：下游禁止越层直读源表；所有业务语义必须经明细层；口径以维表为唯一真值源
- 6.3 模型管理流程：模型设计→评审（数据管理办公室+业务科室）→登记入模型清单→上线→变更评审
- 6.4 血缘可解释性要求：任何看板数字必须能回溯到"源表字段→各层加工→看板"全链路
- 素材：pjm 与 finance 两份 `model-governance.md`（STG 宪法、三段论流水线、依赖规则、血缘要求）

**第7章 主数据管理（6页）**
- 7.1 主数据识别：项目、物料、供应商、人员、科室、会计科目六类；项目主数据是各域数据挂接的地基（财务、采购、质量数据都要靠它关联到项目）
- 7.2 项目主数据多源融合：现状（PMO 台账 + ERP 项目编码）与未来（PLM/ERP/QMS 各有项目标识）的映射模型；统一项目标识 + 映射表 + 人工确认机制（改写 dim_project_master / map_project_name 设计）
- 7.3 别名治理：同一实体多种写法的归一化机制（别名登记表 + 唯一标准值），列举科室/人员/风险等级/节点类型等真实别名案例（脱敏后）
- 7.4 主数据管理流程：新增/变更申请→业务归口科室确认→数据管理办公室登记→分发生效；人工确认（is_verified 机制的流程化表述）
- 7.5 业务人员须知：发现"同一个项目两个名字"如何上报
- 素材：v4 文档 DIM 层设计（dim_project_master、dim_wbs、映射表）、model-governance.md alias dim 清单

**第8章 指标管理（4页）**
- 8.1 指标分类与指标字典：原始指标/二次（派生）指标两级体系；指标登记要素（业务定义、计算公式、统计范围、单位、评价方向、阈值、数据来源、更新频率、历史别名）——直接以 metric-handbook 的指标卡片结构为模板
- 8.2 口径管理：口径冻结机制（冻结日期、权威出处）、历史别名归档（解决"同一指标多个叫法"）
- 8.3 指标全生命周期流程：提出→定义评审→发布→变更（须重新评审并通知消费方）→下线
- 8.4 指标现状规模：已治理 77 个项目管控域指标、财务域看板指标（作为一期成果案例写入）
- 8.5 业务人员须知：对看板数字有疑问时如何查口径（指标说明入口）、如何提口径异议
- 素材：`pjm/metric-handbook.md`、`pjm/metric-registry.json`（77 指标、fieldDictionary）、`finance/finance-screen-metric-audit.md`、v3/metrics 指标大表（溯源出处）

**第9章 元数据与血缘管理（3页）**
- 9.1 元数据范围：技术元数据（表/字段/加工逻辑）、业务元数据（业务含义、归口科室）、管理元数据（密级、责任人、更新频率）
- 9.2 数据资产目录：按业务域组织的资产清单，覆盖率要求
- 9.3 血缘管理：端到端血缘链路（填报模板字段→贴源层→各层→看板指标）；来源追溯字段规范（批次号、来源文件、导入时间等——改写 STG 元数据字段规范）
- 9.4 元数据维护责任：技术元数据随模型上线自动登记，业务元数据由科室数据专员补录
- 素材：model-governance.md 第 6 节（来源元数据字段）、v4 文档 STG 层字段收敛标准

**第10章 数据质量管理（7页，治理域篇最重章）**
- 10.1 质量维度与规则体系：完整性/准确性/唯一性/及时性/一致性五维；从现有 6 条规则扩展为分域规则清单（正文给规则框架与示例，全量规则清单进附录）——含映射完整率≥95%、人员匹配率≥90%、枚举命中 100%、主键唯一 100%、月度导入及时性等既有规则
- 10.2 源头质量控制：填报模板管控（下拉选择、格式约束、必填项）、入湖校验（格式/值域拦截）——针对"Excel 离线多"的现状重点写
- 10.3 质量监控与告警：规则自动执行、质量报告（月度）、问题分级（阻断/严重/一般）
- 10.4 整改闭环：问题登记→定责（按血缘定位到填报科室或加工环节）→整改→复验→销号；整改单表单设计
- 10.5 质量评价三步走：**一期**只做月度质量通报（不排名不考核）→ **二期**质量分纳入科室数据工作评价参考 → **三期**与考核挂钩（需所级发文）；明确每步的进入条件
- 10.6 业务人员须知：常见填报错误清单（日期格式、自造枚举、空值占位符）与正确做法
- 素材：v4 文档"数据质量规则"节、model-governance.md（占位符归 NULL、safe 转换宏反推常见质量问题）、质量考核节奏为用户定调

**第11章 数据安全管理（4页）**
- 11.1 分级分类：数据分类（按业务域）× 分级（公开/内部/秘密/机密，定级由保密部门主导，数据平台落实标识与管控）
- 11.2 访问控制：最小授权、按科室/角色的权限矩阵、高敏数据（项目财务、预算）单独审批
- 11.3 传输与存储安全：离线文件导入的加密与落地保护、涉密数据全程受控（能力表述通用化，不写实现组件）
- 11.4 操作审计：谁在何时访问/导出了什么数据，审计日志留存要求
- 11.5 与保密制度的衔接：引用所内保密管理规定作为上位依据；数据平台安全措施是保密要求在数据环节的落实
- 素材：sprint-36（数据安全/机密级合规）、sprint-37（入湖加密）成果的通用化表述；审计 IP/留痕实践

**第12章 数据生命周期管理（4页）**
- 12.1 全生命周期阶段：产生（填报/接入）→使用→归档→销毁
- 12.2 保留与归档策略：贴源层 3 年在线、每年归档；明细/汇总/维度层保留策略（改写 v4 文档生命周期表）；**归档目标库：达梦数据库**（点名），归档流程与恢复验证要求
- 12.3 数据销毁流程：销毁申请（含数据清单与密级）→数据管理办公室审核→保密部门审批→执行销毁（在线库+达梦归档库+备份介质同步处置）→双人监销→销毁台账登记；涉密数据销毁从严
- 12.4 表单：归档申请单、销毁审批单、销毁台账（模板进附录）
- 素材：v4 文档"数据生命周期管理"节 + 达梦/销毁为用户定调，销毁流程新写

**第13章 数据共享与服务管理（3页）**
- 13.1 共享原则：最小必要、按需审批、全程留痕
- 13.2 共享方式与规范：看板授权、数据接口、离线提取三类，各自的申请与审批流程（离线提取从严：审批+水印/台账）
- 13.3 服务口径一致性：所有共享出口必须消费应用层统一口径，禁止绕过口径层直接取数
- 13.4 对外（所外）提供数据：叠加保密审查
- 素材：治理原则延伸 + sprint-38 接口化实践的通用表述；大部分新写

### 第三篇 实施篇（约 18 页）

**第14章 系统接入与数据流规划（6页）**
- 14.1 接入现状与目标：现状以 Excel 模板月度/周度填报为主；目标分批接入 PLM（设计/技术状态）、ERP（采购/库存/项目财务/预算）、QMS（质量）
- 14.2 接入次序建议与判定标准：数据价值 × 系统成熟度 × 标准就绪度三维评估；ERP 采购库存已有同步基础可先行，PLM/QMS 随系统建设跟进
- 14.3 项目、财务两域数据流详解（本章核心）：项目域数据流（计划/进度/质量/风险/技术状态的填报与接入路径）+ 财务域数据流（预算三本账、项目经费、成本归集的取数与按项目维度对齐）；近期目标是"财务数据按项目维度可查可算"
- 14.4 项目-财务贯通蓝图（远期演进方向，非阶段承诺）：五段数据流——预算编制→采购执行→库存与领用→成本归集→项目决算，及跨段勾稽关系（预算 vs 已执行、采购 vs 入库、领用 vs 成本）；明确以 ERP 等系统建设与数据成熟度为前提、分步推进
- 14.4 新系统接入的治理前置件：接入前必须完成的标准对齐、主数据映射、质量规则定义清单（防止"先接入后返工"）
- 素材：v4 文档 ERP 采购/库存/成本/财务各层设计、预算域"三本账"口径（已执行=预付+账面+应付）、pjm-v4 预算域实践

**第15章 分期实施路线图（5页）**
- 15.1 一期（治标准、治填报，约 6 个月）：发布三份核心制度；填报模板标准化；主数据与别名清理；指标字典发布；质量月度通报机制启动。退出标准：映射完整率/枚举命中率达标
- 15.2 二期（接系统、闭环质量，约 12 个月）：ERP 深度接入，财务数据按项目维度关联分析落地；PLM/QMS 按建设进度接入；质量整改闭环上线；元数据目录覆盖主要业务域；质量分纳入评价参考
