# T01: 血缘治理闭环端到端集成测试

**优先级**: P0
**状态**: BLOCKED_INPUT
**依赖**: F1/T01、F1/T02、F2/T01、F2/T02、F2/T03、F3/T01、F3/T02 全部 DONE；G0 的 B1（实例/账号）、B2（样本链路）

## 目标

在运行实例上证明血缘治理闭环成立，而不只是单测绿。

## 技术设计

### 端到端脚本（对应 IT-01 ~ IT-05）

**场景 A：正确性（IT-01）**

1. 对样本链路的下游数据集调 `impact?withColumns=true` → 记录 `columnLineages` 条数 N1
2. 直接查库 `select count(*) from catalog_column_lineage where dataset_lineage_id in (...)` → 记录 N2
3. 若库中存在已失效行，断言 `N1 < N2` 且差值 == 已失效行数（**这就是修复的证据**）
4. 带 `at=<某历史时刻>` 再查 → 断言 `snapshotAt == columnLineageSnapshotAt`

**场景 B：导入可诊断（IT-02）**

1. 上传一个**故意含未匹配模型**的 manifest
2. 断言响应 `skippedReasons` 四类计数合计 == `skipped`
3. 在采集运营台「未匹配明细」中能看到这些模型及原因
4. 修正 schema 后重传 → 未匹配数下降

**场景 C：补录闭环（IT-03）**

1. 影响分析记录当前边数 N
2. 「登记血缘」补一条 → 边数 N+1，新边 `MANUAL` + `DECLARED`
3. 「失效」→ 边数回 N
4. 设 `at` 为失效前 → 边重新出现（**软失效语义证据**）
5. 审计库查 `CATALOG_LINEAGE_CREATE` / `CATALOG_LINEAGE_DELETE` 各一条

**场景 D：核验不被覆盖（IT-04）**

1. 对一条 `ADDAX` 边执行核验 → `VERIFIED`，记录 `lastVerifiedBy`
2. 触发 Addax 血缘同步（运营台「立即同步」）
3. 重查该边 → 断言仍为 `VERIFIED`、`lastVerifiedBy` 保留、`lastObservedAt` 已刷新（**ADR-90-04 证据**）
4. 对一条**未核验**的边同样操作 → 断言其状态按采集结论更新（守卫未过度拦截）

**场景 E：运营台可诊断（IT-05）**

1. 运营台四路采集源状态与库中 `relation_type` 分布一致
2. 待核验计数与 `pending-verification` 的 `statusCounts` 一致
3. 「去核验 →」跳转后影响分析确实只显示对应状态的边
