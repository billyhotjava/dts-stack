# Sprint-102：数据质量自动化工作流闭环

**时间盒**：2026-08-24 ～ 2026-09-11  
**状态**：IN_PROGRESS  
**Owner / Reviewer**：xiezm  
**目标**：把规则、运行策略、模型质量阶段、数据接入后验证、规则执行、问题处置和发布门禁收敛为同一条可追踪、可重试、可审计的数据质量工作流；用户不再靠多个页面手工拼接执行结果。

## 背景与现状

平台已经具备规则、规则版本、资产绑定、单次运行、周期巡检、模型候选质量证据和问题单，但当前是多条相邻能力，不是统一工作流：

- `QualityRunService` 是正式规则执行引擎，人工、调度、入湖和模型发布入口对它的调用方式不同。
- `gov_quality_task` 能按固定分钟周期调度，但没有工作流实例、聚合状态、重试策略、并发策略和稳定的来源关联。
- `gov_quality_run.job_id` 已存在却未使用，前端只能看到分散的规则运行。
- 模型候选进入质量阶段后仍需逐条创建治理运行；文件暂存预检查与数据接入后的正式资产验证边界不清晰。
- 实测 1 条运行策略产生 244 次规则运行，其中 239 次调度失败；失败形成 240 张未关闭的 `QUALITY_RUN` 问题单，说明当前按单次运行建问题会造成告警风暴。

## 产品边界

1. 数据治理中的“质量规则”仍是规则定义与资产绑定的唯一入口；建模页面只选择/查看规则和工作流证据，不复制规则编辑器。
2. `QualityRunService` 仍是唯一规则执行引擎；新增 `QualityWorkflowOrchestrator` 只负责编排、幂等、聚合和关联。
3. `gov_quality_task` 演进为“运行策略”，不新建第二套调度定义。
4. 工作流失败只阻断未发布候选、登记问题并允许重试；不自动回滚已经发布的生产模型。
5. 不做拖拽式流程画布，不新增顶级菜单，不引入 Lakehouse 语义。
6. 权限沿用现有治理 maintainer guard 与数据资产可见性：所级数据管理员可管理全局策略，部门数据管理员只能处理所属部门可见资产。

## 端到端契约链

```text
规则定义/绑定
    ↓
运行策略 或 业务事件（模型质量阶段、数据接入完成、人工立即验证）
    ↓
QualityWorkflowOrchestrator（幂等、并发、来源关联）
    ↓
QualityRunService（唯一规则执行引擎）
    ↓
工作流聚合状态 + 规则运行明细 + 审计
    ↓
失败：同一问题持续追加证据 → 重试 → 恢复
通过：模型发布门禁继续；数据接入完成后的资产质量状态从正式运行事实派生
```

## 架构决策

| ADR | 决策 | 理由 |
|---|---|---|
| ADR-102-01 | 新增工作流实例账本，复用 `gov_quality_run.job_id` 关联子运行 | 保留单次运行事实，同时补齐聚合控制面 |
| ADR-102-02 | `QualityRunService` 为唯一执行引擎 | 防止调度、建模和入湖产生口径不同的结果账本 |
| ADR-102-03 | `gov_quality_task` 更名为产品语义“运行策略”，表名/API 保持兼容 | 开发期收敛 UI，不破坏已部署契约 |
| ADR-102-04 | 调度幂等键为“策略 + 时间槽”；业务事件幂等键由来源实体与版本生成 | 防止调度重入和消息重投产生重复工作流 |
| ADR-102-05 | 工作流状态为 `QUEUED/RUNNING/PASSED/FAILED/BLOCKED/CANCELLED` | 区分质量不通过、系统阻断和人为取消 |
| ADR-102-06 | 问题身份按“资产 + 规则绑定 + 错误类别”聚合 | 避免每次失败创建新问题单；恢复后保留证据 |
| ADR-102-07 | 发布模型失败不自动回滚 | 已发布事实不可由异步质量波动静默改写 |
| ADR-102-08 | 完成全部 Feature 后集中做一次 E2E | 遵守当前测试约定，开发阶段只跑聚焦测试/构建 |
| ADR-102-09 | 模型候选进入 `QUALITY_RUNNING` 时自动分发钉定规则 | 保留“构建 → 质量检查”的显式状态机，不在构建完成时暗中跨阶段 |
| ADR-102-10 | 文件暂存预检查不写正式工作流；接入成功后按冻结策略启动正式工作流 | 预检查面向待提交暂存数据，正式工作流面向已落地数据资产，二者证据不可混用 |
| ADR-102-11 | 首版并发固定 `SKIP`、重试由授权用户显式发起 | `REPLACE` 需要可靠取消在途规则；自动重试需要稳定故障分类，未具备前不制造重复运行 |
| ADR-102-12 | 规则列表“执行”与旧 `/quality/runs` 人工入口统一进入 `QualityWorkflowOrchestrator` | 保留旧响应兼容，但任何正式人工运行都必须具备 workflow identity |
| ADR-102-13 | 活动工作流默认 30 分钟超时转 `BLOCKED`，授权用户可显式取消等待 | 防止失联子运行永久占用策略 `SKIP` 唯一约束；取消不伪装成质量失败 |
| ADR-102-14 | 模型候选一次质量命令聚合其全部钉定规则，并在重试时保持规则版本与绑定不变 | 发布证据不能因规则新版本而漂移，也不能拆成无法聚合的多个工作流 |
| ADR-102-15 | 接入后质量触发失败必须持久化并有限次自动补偿，接入成功事实保持不变 | “不回写接入失败”不等于允许质量链路静默断开 |
| ADR-102-16 | 所级与部门级数据管理员共用治理维护入口，部门角色继续受资产可见性约束 | 对齐已确认权限口径；删除策略不能绕过对象级访问校验 |

## Review 收口契约（2026-08-22）

| 缺口 | 收口契约 | Task |
|---|---|---|
| 规则列表正式执行仍产生 legacy run | `POST /api/governance/quality/workflows/trigger` 返回 `QualityWorkflowRunDto`；旧 `/quality/runs` 人工路径兼容返回 runs，但内部调用同一编排命令 | F2/T04、F5/T04 |
| `QUEUED/RUNNING` 可永久卡住 | 超时转 `BLOCKED/WORKFLOW_TIMEOUT`；`POST /workflows/{id}/cancel` 转 `CANCELLED` 并释放策略活动约束 | F1/T04、F5/T04 |
| 模型钉定证据重试漂移、一次命令拆成多个工作流 | 一个 candidate command 对应一个 workflow；`contextJson` 保存全部 `{ruleId, ruleVersionId, bindingId}`，重试复用原快照 | F3/T04、F4/T04 |
| 模型已进入质量阶段但自动启动失败静默 | 返回稳定错误码并保留可重试入口，UI 明确提示失败，不再只写服务端日志 | F3/T04、F5/T04 |
| 接入后触发失败没有补偿 | execution 成功事务先登记 `PENDING`，提交后进入 `TRIGGERING`；失败转 `RETRY_WAIT`、第三次转 `EXHAUSTED`，成功转 `TRIGGERED`，始终使用原 execution identity 幂等补偿 | F3/T04 |
| 所级数据管理员不能删除策略 | 前后端复用治理 maintainer 角色集合；服务层删除前执行资产可见性校验 | F2/T04 |

## 完成标准

- 每次人工、周期、模型或入湖触发都有唯一工作流编号，并能查到所有规则运行。
- 重复调度/事件投递不会创建重复工作流；同一策略并发行为可解释。
- UI 能配置运行策略、立即验证、查看工作流时间线、规则明细、失败原因和重试结果。
- 模型质量门禁读取工作流最终状态；数据接入后的正式验证不再绕过工作流账本。
- 同一根因的连续失败只维护一个开放问题，恢复后追加恢复证据。
- 新动作进入审计资源字典，关键日志包含 workflowId、taskId、datasetId、triggerType、triggerRef。
- 聚焦测试、模块构建、迁移检查通过；全部 Feature 完成后再执行真实 Chrome E2E。
