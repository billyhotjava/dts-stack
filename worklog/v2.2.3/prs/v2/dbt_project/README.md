# 花卉租赁数据模型 v2

版本：2.0.0。用途：在 DTS「数据建模 → 逆向建模」上传 ZIP，完成环境映射后导入模型，再按依赖顺序物化。

## 文件

- `prs-flower-dbt-models-v2.zip`：页面上传入口，包含一个完整 dbt 项目、31 个模型和 `target/manifest.json`。
- `dbt_project/`：同一模型包的可编辑源文件。模型和字段中文说明位于 `models/*_schema.yml`，来源契约位于 `models/sources.yml`。
- `model-catalog.md`：模型名称、业务粒度、依赖和物化顺序。
- ZIP 的 `.sha256` 文件用于核对文件内容。

## 来源与版本范围

参考旧目录 `/opt/prod/prs/source/dts-stack/worklog/prs/v1/xycyl-finance-dbt-models-v1.zip`。旧包为月结和收款两条财务链，共 7 个模型。v2 保留其核心业务用途，扩展租赁、摆放、变更、回收和养护链。

v2 只写入 `/opt/prod/s10/v2.2.3/worklog/v2.2.3/prs/v2`，旧目录未修改。

本地来源为 PostgreSQL `biadmin.public`，19 张表均使用当前接入前缀 `ods_prs`，例如 `ods_prsp_project`、`ods_prsa_month_accounting`，前缀与原表名之间不额外加下划线。字段来自 2026-09-13 的实际 ODS 结构，不沿用旧包的全字符串假设。

模型名统一使用 `prs_v2_`；dbt 项目名 `prs_flower_v2`，项目版本 `2.0.0`。输出采用全量 `table`，SQL 方言为 PostgreSQL。包内不含连接凭据、外部依赖包、自定义宏、数据库辅助函数或测试节点。业务 SQL 直接通过 `source()` 读取 ODS，DWS/ADS 用 `ref()` 依赖上游模型。

## 逆向建模导入

1. 上传 `prs-flower-dbt-models-v2.zip`，保留全部 31 个业务模型。包中为 DWD 17 个（其中维度 5 个）、DWS 5 个、ADS 9 个。
2. 选择数据域 `DATA_PRS`（花卉数据管理）。`PRS` 是业务分类，不是本包的数据域编码。
3. 将 19 个 `prs_ods` 来源映射到实际接入资产；物理位置见 `models/sources.yml`。不要选择旧的 `ods_ptr_mysql_*` 资产。
4. 在需要业务过程的模型上选择现有 `prs_mgmt`（花卉租赁管理业务）。
5. 为 ADS 选择实际的花卉数据集市和主题域。可使用名称“花卉租赁数据集市”和“花卉租赁经营分析主题域”；代码可采用 `DM_PRS`、`PRS_OPERATIONS`。导入时已创建并发布上述对象；包内不硬编码环境 UUID。
6. 导入后按平台现有流程物化，包含相应上游依赖。全量顺序见 `model-catalog.md`。以接入同步完成后的 ODS 作为首次物化输入。

维度携带稳定 `dimensionDefinitionCode`、内嵌定义及字段映射。后续修改同一维度应继续复用这些编码。复杂 SQL 预计作为平台的 dbt 托管模型导入，不要求全部转成可视化设计器 SQL。

包内 manifest 由离线静态解析生成，来源数据库为 `biadmin`，示例输出 schema 为 `prs_v2`；实际物化输出以平台选择的目标连接和命名规则为准。`sources.yml` 不写死数据库名。直接通过 dbt 使用时，需在包外提供 `prs_flower_v2` profile，选择同一个 PostgreSQL 仓库的目标 schema。

## v1 → v2 的口径改进

| 问题 | v2 处理 |
| --- | --- |
| 旧来源名称、全字符串转换和辅助宏 | 对接实际 `ods_prs*` 表，使用原生数值与时间类型；SQL 无自定义宏依赖 |
| 月結表每项目每月只有一行的假设 | DWD 以月结 `id` 为粒度，保留合同、部门及源年月；DWS 再按租户、项目、月份汇总 |
| `net_receipt_total_amount` 被解释为现金实收 | 改为“月结实时租金”；`folding_after_total_amount` 为折后应收；账面实收单独保留 `total_amount` |
| 当月收款替代账期实收，再推导欠款和回款率 | 月结应收、月结账面实收、按 `pay_time` 统计的现金收入分别展示；不输出未经账单归属确认的欠款及回款率 |
| 未区分有效收款 | 租摆现金汇总仅纳入 `status=2` 且 `income_type=1`；收款明细保留全部收入类型和状态 |
| 收款明细被当作直接关联月结 | `a_collection_item.biz_type=1` 指发票、`2` 指销售账单；只保留真实关联，不直接连接月结 ID |
| 名称充当项目或客户关联键 | 使用业务 ID；项目经合同关联客户；DWS 聚合保留租户键，名称只用于显示 |
| 单头与明细连接重复计算金额 | 单头、明细分别建 DWD；养护工作量从单头汇总；收款分摊先按收款单聚合再连接 |
| 减花租金重复取负 | 保留 `biz_total_rent` 原符号，作为业务变动额，绝不称为月租收入 |
| 不合法年月与缺失金额被静默填成有效值 | 年月验证后生成月首日，不合法值保留 NULL；关键汇总保留缺失金额记录数 |

## 统计约定

- 五个维度为当前 Type 1 全量维度；历史事实按当前合同关系归属客户，不表示客户归属的历史快照。
- 源主键作为单一花卉源系统中的稳定业务键。无租户字段的子表从单头或项目继承租户；无法关联的事实保留，不以姓名或项目名猜测 ID。需要通过缺失关联明细定位源数据问题。
- DWD 保留删除标记、状态和 6 个 `_dts_*` 接入血缘字段。维度保留已删除对象，供历史事实关联；业务汇总按明确有效状态筛选。
- 报花有效单为未删除且状态 1–5；已结束为状态 5。`business_time` 优先使用起租时间，其次申请时间。月度租金变动和成本仅汇总已结束单。明细 `item_type` 与单头 `order_type` 是不同的类型集合，不混用。
- 月结汇总纳入状态 2–5，排除待确认月结；实际原始记录仍完整保留在 DWD。
- 当前摆放采用未删除且状态 1。按源 `total_number × rent/cost` 统计实摆租金和成本，并将绿植、花盆、盆架数量分开；该租金不是财务月结应收，当前快照也不用于还原历史月末存量。
- 收款金额使用真实源字段 `pay_amoney`。收款分摊只代表登记的关联金额；未分摊金额允许负数以暴露超分摊，不用 `greatest(...,0)` 隐藏差异。若有缺失分摊金额，需结合缺失数量解读。
- ADS 收款、租赁、变更、回收明细保留源状态，查询时根据用途筛选。租赁明细的租金和成本为源值，不随意乘数量或合计父子组合明细。
- 汇总里的 NULL 金额保持可见。金额求和遵循 SQL 忽略 NULL 的规则，同时提供关键缺失记录数；仅“该侧完全没有记录”时补 0。不能把含缺失记录的部分合计作为完整金额。
- 未覆盖采购、库存流水、工作流、聊天、系统日志和完整发票到月结核销链；这些不影响本版已定义的租赁经营与财务并列分析范围。

## 生成检查范围

已执行 dbt 静态 parse、字段引用/契约检查、依赖闭合及无环检查、维度定义映射检查和 ZIP 内容核对。静态解析使用无数据库连接的占位 profile，只生成 manifest；未执行 dbt compile/run/test、SQL 查询测试、页面导入、真实数据对账、部署或物化。因此这里交付的是已完成静态检查的模型包，不宣称页面导入和物化已经通过。

业务口径参考旧 v1 包，并核对花卉源码中的 `MonthAccounting`、`CollectionRecord`、`CollectionItem`、`FlowerBizInfo`、`FlowerBizItem`、`ProjectGreen` 及其查询映射。ODS 结构依据当前本地数据库。

## 2026-09-13 导入适配

- 显式配置 31 个模型的物理 `alias`，业务名称可用中文。
- 项目和摆放位置维度直接关联 ODS，保留原连接键、租户条件和客户归属口径，适配维度不得依赖模型的导入约束。
- 补全直接及间接 ODS 的 `sourceRefs.layer=ODS`，保留其他层间模型依赖。
- 导入来源应选择数仓 PostgreSQL 的已采集资产；当前接入写出的同名原 MySQL 连接目录记录缺少采集状态，不能作为建模来源。
- 本次仅重新执行静态 parse 生成 manifest 和页面导入预览，不执行 dbt compile/run/test 或物化。

## 构建字段命名适配

2026-09-13：DWD 追溯字段输出统一采用 `dts_*`，读取 ODS 时仍使用原 `_dts_*` 字段。保持追溯内容，适配非贴源模型技术字段必须以小写字母开头的规则。

## 当前运行器来源适配

本包的 dbt 来源名采用 `public.ods_prs原表名`，与平台按已确认 ODS 绑定生成的来源定义一致。SQL 的实际输入表、租户连接条件和业务口径不变。月度结算采用周期快照/统计周期；报花单头采用累积快照/业务、申请、完成里程碑日期。
