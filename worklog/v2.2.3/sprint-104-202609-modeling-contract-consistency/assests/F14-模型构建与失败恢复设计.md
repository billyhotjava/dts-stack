# F14 模型构建与失败恢复设计

状态：DRAFT，2026-09-23；初审基线`a7f54ef1e`，增量核对`20400602b`。依赖[F13/F14联合设计](F13-F14-联合设计与实施顺序.md)。本文件是拟实施设计，不表示当前支持分阶段续跑。

## 1. 用户场景与范围

用户在既有工作台发起构建，应在执行前得到明确检查结果；执行后知道失败阶段、已有结果和下一步。SQL成功但核验/回写失败时，在证据完整且当前授权有效的情况下，只恢复后续步骤，避免重复加工。证据不完整则明确禁止自动续跑，保留事实并由用户选择新构建。

覆盖首建、同版本重复请求、同版本再次构建、修改后新构建及旧模型兼容。复用既有`ModelBuildIntentService`、`ModelMaterializationStartService`、派发仓储/服务、runtime-spec、sync-probe/finalize和Airflow DAG。已发布模型的日常运行仍走`PlanOperationalRunService`，本期仅回归共享代码，不改其业务生命周期。

不重写建模编辑器、SQL解析器、质量规则引擎；不承诺数据库DDL/DML跨引擎回滚；不删除用户目标表、历史运行或发布记录；不因恢复放宽权限、密级、来源版本及目标检查。

## 3. 构建阶段与不变量

| 技术阶段 | 业务显示 | 完成证据 | 失败后动作 |
|---|---|---|---|
| PRECHECK | 构建前检查 | 当前模型/实现/来源版本、目标配置与必要字段通过 | 留在原配置；说明具体修复入口，不启动Airflow |
| PREPARE_RUNTIME | 准备执行环境 | 当前批次取得有效运行包和凭据租约 | 重试准备或明确新构建；不能假设SQL执行过 |
| DBT_BUILD | 执行数据加工 | 同批次manifest/run_results、invocationId与各输出实际结果 | 无证明或部分SQL失败不能走“只恢复后续步骤” |
| SYNC_PROBE | 核对目标表与字段 | 文件完整、当前范围一致、目标关系核验通过 | SQL成功且证据可重读时允许受控继续核验 |
| FINALIZE | 保存构建结果 | 执行记录、候选状态和已核验结果一致 | 允许幂等补写；返回丢失不重复执行SQL |

资源清理独立记结果：失败应提示并由已有清理机制恢复，不能覆盖SQL首发错误；凭据泄漏或仍在运行的进程必须阻止不安全的后续操作。所有阶段完成才算构建成功，DBT_BUILD成功仅说明执行证据；SCHEMA_ONLY显示“表结构已创建”，不声称有业务数据。

## 4. 构建前检查与运行快照

复用既有阶段校验、来源解析和目标解析，将可静态发现的字段角色、业务过程、来源分层识别、目标ID不存在等错误前置到构建入口；不得为前置校验再维护一份规则。检查不创建目标表、不执行用户SQL。

构建入口锁定模型/实现、来源版本、环境/目标ID、包校验和及必要运行配置版本。runtime-spec消费时再次确认这些绑定仍有效；展示与执行读取同一生效配置。凭据轮换可按既有安全配置获取当前凭据，但不能把同名不同ID当同一目标。检查和执行之间发生真实变化应明确拒绝并保留原运行记录。

## 5. 首发错误与阶段证据

拟在既有构建详情读接口增加`materializationProgress`：runGroupId、attempt、buildMode、stages[]、primaryFailure、cleanupFailure、allowedRecoveryActions。阶段项含name/status/startedAt/finishedAt/correlationId，status取WAITING/RUNNING/SUCCEEDED/FAILED/UNKNOWN/SKIPPED；SKIPPED仅表示无需执行或被前序阻止，不能算该阶段成功。错误沿用联合设计的结构化字段。详细DTO由M0与F13一起冻结，字段缺失兼容旧客户端。

执行阶段结果必须可跨进程重启读取。优先在既有派发/运行记录上增加阶段详情及证据引用，保存有界的元数据，SQL与文件内容不塞入JSON。修改通过版本比较，历史首发失败保留；若现有行不能承载并发与追加历史，T01说明依据后采用附属记录表，不能两套存储同时作为真相。

恢复成功后当前阻断清除，但原始失败和恢复操作历史保留；页面区分“当前结果已恢复”与历史失败，不能继续把旧primaryFailure当当前阻断。

只接受受认证的当前批次回调；字段必须校验运行目的、批次/尝试、包校验和、模型/实现范围和artifact invocationId。Java响应→Python读取→平台持久化有跨语言测试，HTTP失败内容不是自由文本猜码。外部内容脱敏并限制长度，首发阶段真实错误优先，兜底通用码只在原始证据不存在时使用。

## 6. 分阶段恢复与终态规则

| 当前情况 | 行为 | SQL是否重跑 |
|---|---|---|
| 回调成功但响应丢失 | 相同业务键重放返回已有结果 | 否 |
| SQL全成功，核验未完成，证据及版本齐全 | 创建“继续核验”恢复操作 | 否 |
| 核验已成功，仅完成回写丢失 | 创建“补写构建结果”恢复操作 | 否 |
| SQL失败、部分输出失败、执行结果未知 | 提示查看原因；用户通过既有入口明确新尝试 | 不自动重跑；新构建可能执行SQL |
| 运行文件丢失、invocationId不符、目标或来源已改变 | 拒绝续跑，提示重新确认配置后新构建 | 否 |
| 当前候选STALE/CANCELLED、已被替代，或已有更新尝试 | 拒绝旧结果和恢复命令 | 否 |
| 已发布模型需再次加工 | 使用既有日常运行入口 | 不借恢复命令重开发布流程 |

所有续跑先重新鉴权，确认旧SQL进程终止、最新尝试未变化及必要证据仍可读取。复用既有租约服务申请新凭据，不复用已消费token或过期lease；恢复过程必须同样释放资源。证据保留期覆盖可恢复窗口，过期后按钮禁用并解释，具体期限由M0核对磁盘预算后冻结。

**终态不能直接回写成功**：当前代码可能已把sync-probe/finalize失败记为BUILD_FAILED及运行失败。T01必须列出服务/仓储允许转换；拟通过带原因、版本检查和审计的`RECOVER_BUILD`操作恢复到受控BUILDING过程，恢复模式只允许SYNC_PROBE/FINALIZE，禁止重新派发SQL。若不满足证明条件拒绝该转换；不得通过SQL手改状态或绕过原终态拒绝。对原始失败尝试保留记录，恢复操作关联它，不能伪造全程无失败。BUILD_FAILED→BUILDING的恢复分支与普通新尝试分支必须有明确模式，M0冻结后才能实施。

## 7. 恢复命令与持久化

拟新增`POST /api/modeling/plans/{planId}/release-candidates/{candidateId}/recover-build`：If-Match、Idempotency-Key；body={pipelineRunGroupId,expectedAttempt,action,reason}，action只允许RESUME_VERIFICATION或FINALIZE_RESULT。服务端独立计算可执行动作，不信任客户端指定阶段。合法请求返回202及operationId、candidateId、pipelineRunGroupId；查询使用扩展后的既有工作台GET。

拟新增附属恢复操作记录`modeling_materialization_recovery_operation`：tenant/candidate/group/attempt、action、请求幂等键与参数摘要、请求人与执行身份引用、状态、版本、领取令牌/过期、起止时间、错误与证据引用。唯一约束确保同一执行批次最多一个活动恢复操作；同键不同参数拒绝，同键相同参数重放。DDL、外键类型、生命周期及迁移编号M0冻结；不新增独立运行台账。

执行接入现有派发服务的恢复分支；先短事务领取，事务外核验与调用，短事务按版本提交。租期过后旧worker不能写结果。新构建/放弃与恢复竞争必须争用同一当前尝试判定，最多一方生效；迟到回调不得覆盖新尝试。提交到外部后的结果未知先查询确认，不默认重发有副作用操作。

## 8. 页面、预算与兼容

沿用构建页面/发布面板，显示准备→加工→核验→结果四个步骤；失败行显示已完成步骤、具体原因及操作。可恢复时显示“继续核验”或“补写构建结果”；仅在实际需要且已允许时显示“重新构建”，提示将再次执行加工。点击后防重，失败保留输入；刷新仅GET。纯读失败显示“状态读取失败”，不清空上一次结果或显示成功。

拟定工程预算：本地身份/版本/配置预检p95≤3秒，外部连接检查有显式超时；异步恢复受理p95≤2秒，30秒内被可用worker领取；同批次活动恢复≤1；单次批处理上限沿用现有20，单条失败不阻塞队列。现有派发总超时继续沿用配置，不因本次统一缩短。预算在M0以固定夹具测量后冻结，不是生产性能承诺。Chrome95和1366×768/窄屏回归。

老客户端回调没有阶段字段时按已有证据判断；缺证明显示未知，不从旧FAILED猜测SQL成功。新恢复入口可关闭：关闭后拒绝新恢复请求，查询与普通构建仍兼容。新阶段/操作记录仅向前增加，旧版不会误领取恢复工作须经回退测试证明。存在尚未结束的恢复操作时不得降级到不识别恢复模式的旧版；必须由服务正常完成或受控终止并回到旧版可识别状态，不能手改库。发布时Java服务与Airflow脚本/运行包作为同批制品验证，不能只更新后端而漏掉DAG。
