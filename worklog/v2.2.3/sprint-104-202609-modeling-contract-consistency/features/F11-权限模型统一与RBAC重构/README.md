# F11-权限模型统一与 RBAC 重构

**状态**：SURVEY（现状已冻结，重构方案待确认）
**登记日期**：2026-09-19
**基线提交**：`9bc3ec27a`
**契约文档**：[F11 权限现状梳理与重构方案](../../assests/F11-permission-model-survey-20260919.md)

## 背景

F9 落地部门建模权限后，2026-09-16 现场出现"当前账号无权访问该建模数据"：拥有研究所数据管理员角色的账号在 `/api/modeling/**` 全部 403。根因是数据角色只存在 DTS 库、不在 Keycloak，而 F9 的身份解析只读 Keycloak。`9bc3ec27a` 已修复该点，但暴露出的是权限模型本身的结构问题，不是单点缺陷。

用户提出的两项判断，经梳理均已确认：

1. dts-admin 有自己的用户表、角色表、部门表，与 Keycloak 的打通有缺陷（对应 S1–S5）。
2. 角色权限仅与菜单绑定，不具备 RBAC 能力（对应 S6–S10）。

## 目标

- 冻结 dts-admin 与 dts-platform 的三员权限与普通用户权限现状，给出可核对的证据。
- 提出重构方案，明确事实源、权限点模型、统一决策点和清理范围。
- 方案确认后再进入实施；本 Feature 当前只完成梳理与方案。

## 范围

**包含**：角色事实源与身份解析、三员职责边界、普通用户（员工）权限、菜单与权限的关系、对象级授权机制、密级与部门范围控制。

**不包含**：跨部门授权审核的具体实现（F9 已定仅保留入口）、前端按钮级显隐的逐页核对、Ranger 的存废结论。
