## 背景与本次范围

原报告记录 F9 建模目录未合并 DTS 数据角色引起 403，9bc3ec27a 修复了该点。当前根本问题是身份来源与解析分散、权限点配置不统一、领域策略的组合和迁移规则不明确。现有代码已经有硬编码 RBAC、权限目录与菜单权限码写入，本 Feature 在这些能力上收口。

用户本轮要求把人员/部门职责划分落盘并继续完善架构；不包含代码实现、数据库变更或部署。原 T01 的“已全部冻结”结论因源码反证和现场证据缺口改为 IN_PROGRESS，保留原调查历史；T02–T09 均为 DRAFT。

包含：人员/组织字段所有权、账号绑定、当前身份、三员/数据角色、权限点/带范围授权、菜单服务协议、对象/列表/批量/后台决策、迁移和验收。前端只改造既有页面/按钮与反馈，不新建权限门户。跨部门共享审批、Ranger 替换、密级业务政策制定、多账号人事模型不在本次默认范围；相关依赖按架构 §11 记录。

## 核心设计

1. MDM 负责人事与组织，DTS 负责本地有效目录及业务授权，Keycloak 负责认证账号；每类字段只有一个权威维护方，禁止整行双向覆盖。
2. 保留 organization_node；将 admin_keycloak_user 演进为唯一在用人员目录与当前账号绑定，支持待开户；person_profile 核验后退出全部运行读取并只读归档。
3. 人员与账号分开识别，授权用稳定账号 ID，用户名不作为身份回退。MDM 原始状态、DTS 准入状态与 Keycloak enabled 分开；当前 mdm_enabled 不直接等于离职。
4. admin 提供唯一当前身份解析，platform 的认证/会话/建模/worker 接入同一上下文。继承 F9 的当前复核，不能跨请求缓存允许。
5. 权限按资源+业务动作定义，授权范围随绑定保留。统一决策入口选择领域策略，明确拒绝优先、强制条件、异常与审计，保留 F9 编辑/消费/审核分离。
6. 同步改造 platform→admin 的菜单服务委托协议；菜单只作导航，接口仍独立判权。按扩展、核验回填、对比、切换、收缩发布，清理任务放最后。

## 使用场景与验收结果

| 场景 | 必须观察到的结果 | 验收 |
|---|---|---|
| MDM 更新部门，Keycloak 投影暂时失败 | 当前目录变更不被旧投影回灌，后续范围使用新部门；同步有状态可重试 | IT-68/69 |
| 撤角色、停用、调岗后保留旧门户会话 | 下一授权判定使用新值；目录失败不沿用旧允许 | IT-70/71 |
| 同名账号重建/历史授权迁移 | 新账号不继承旧授权；无法证明历史主体时隔离 | IT-70/76 |
| 员工/部门管理员从菜单进入并直接请求 API | 当前主体一致；只读与维护分离；对象不足时允许页面可见但动作禁用 | IT-72/73 |
| 模型编辑、数据导出、混合批量/worker | EDITOR 不产生消费/审核权，任一目标不足整批无副作用，后台重新授权 | IT-74/75 |
| 旧版升级与安全恢复 | 每项权限差异可解释；不恢复已撤权或把匿名菜单作为回退 | IT-76/77 |
