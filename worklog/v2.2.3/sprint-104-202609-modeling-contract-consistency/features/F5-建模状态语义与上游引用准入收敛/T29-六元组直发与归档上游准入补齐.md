# T29-六元组直发与归档上游准入补齐

**优先级**：P1  **状态**：DRAFT
**依赖**：T27（消费结构化准入结果）。

## 目标

前端按数据库约束的完整形状提交上游输入，后端不再依赖保存期补齐锁定；已归档上游不再静默通过发布预检。

## 输入、输出与数据流

### 1. 契约漂移收口

数据库 CHECK 约束要求上游输入为六字段齐全的对象（`20260724_08_upstream_model_pin_contract.xml`，逐字段校验 modelSpecId、revision、checksum、implementationRevision、implementationChecksum、dbtUniqueId）。前端 `buildImplementationInputs` 在 `modelWorkbenchService.ts`:1120–1137 的回退分支只构造三字段 `{modelSpecId, revision, checksum}`，缺三个实现字段，依赖后端 `ModelImplementationInputPolicy.pinCurrentUpstreamImplementations`:85 在保存期补齐。

这是 2026-09-09 那次 409 的结构性来源（见 [上游锁定取证](../../assests/upstream-pin-stale-root-cause-20260909.md)）。`e711880ef` 起后端已实现首次锁定补齐，症状已消除，契约漂移本身仍在：前端发出的载荷不满足库层约束，仅因中途补齐而侥幸通过。

**变更**：前端在有可用性投影（T26 返回 `implementationRevision`、`dbtUniqueId`）时直接构造六字段；投影不可用时保持现有三字段回退，由后端补齐兜底。后端 `pinCurrentUpstreamImplementations` **保留**，作为旧客户端与降级路径的兼容层，不删除。已锁定输入不得隐式升级的现有规则（`:83` 注释所述）继续有效。

### 2. 归档上游准入补齐

`ModelReleaseCandidatePreflightService.validateEdges`:305 只在依赖修订漂移分支内检查上游状态（`:323`）。若下游钉住的正是上游当前修订且该修订快照为 `ARCHIVED`，边状态为 `CURRENT`，预检不做任何状态判定即放行。前端候选列表已过滤 ARCHIVED（`modelWorkbenchService.ts`:583），因此该路径只在历史引用上出现，属真实但低频的缺口。

**变更**：在 `validateEdges` 增加一个与修订漂移无关的分支，被钉修订快照为 `ARCHIVED` 时阻断，错误码沿用现有命名风格并携带 modelSpecId 与 pinnedRevision。不改动现有 STALE 分支的判定条件，避免影响已发布模型的可重现性。

需先确认现网是否存在指向已归档上游的活跃引用。若存在，本变更会阻断其发布，须在 Sprint README 记录影响面与处理方式，不得直接上线。

## 技术设计

两项变更相互独立，可分别提交。第 1 项属前端契约对齐，第 2 项属后端准入补洞。第 2 项开工前对 `ModelReleaseCandidatePreflightService.validateEdges` 跑 `gitnexus_impact` 并记录结果。

## UI交互与错误路径

第 1 项对用户无可见变化，成功路径与现状一致。第 2 项的阻断在发布预检既有阻断列表中展示，沿用 T28 的 reason 文案机制，说明上游已归档及可选动作。

## 影响范围

`modelWorkbenchService.ts`:1120–1137；`ModelReleaseCandidatePreflightService.java`:305–352；对应 Vitest 与 Java 测试。无迁移。
