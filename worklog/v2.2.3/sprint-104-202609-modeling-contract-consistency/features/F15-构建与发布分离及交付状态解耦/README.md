**优先级**：P0（大版本入版）

**依据**：本轮用户要求重建 F15；延续 [F3 建模与数据模块边界](../F3-全层建模与数据模块边界简化/README.md)。源码核对基线为 `dc06a6277`，本轮合并文档基线为 `0bc4fde6a`。本次仅重建文档，没有撤回或修改业务代码；旧 F15 的需求、任务及实施记录从 Git 历史追溯，不能计作新版完成证据。本轮未取得 Image #7 原图，以用户描述及当前源码为依据。

## 1. 为什么重建

上一版把建模、构建、资产登记、工程验证、治理质量、发布、上线放进同一个弹窗的 7 个步骤（旧文档已删除，源码替换方案由 T01 核对）。问题有三点：

- 一个页面 7 个过程，每个过程都带详细内容，操作者找不到自己该做什么。
- 这些环节归属不同的模块和负责人，生命周期也不同，硬串成一条线不合理。
- 串成一条线后，任何一个下游环节出错，看起来都像整个建模失败。例如上线后某一次定时计算失败，也显示成「第 7 步需处理」。

## 2. 目标

建模人员可以独立保存模型设计、完成实现配置和构建：**构建满足本次模式要求并确认结果后，建模就完成了**。保存草稿只表示设计已保存；结构构建只表示表结构完成，不表示已有业务数据。

发布是构建成功之后一个独立、按需发起的动作。资产登记、数据质量、资产治理、上线与定时运行在各自功能中处理。模型上只显示相关摘要与处理入口，任何下游事项出错都不会抹掉已确认的建模结果。各功能仍检查真正需要的前置条件，不能以“解耦”为由绕过版本、来源、审批、权限或密级要求。

| 需求 | 可观察结果 | 验收 |
|---|---|---|
| R1 独立入口 | 模型页面不展开其他业务的完整表单 | IT-01/02/11 |
| R2 独立结果 | 已保存、构建完成、质量未通过、未发布可以同时存在 | IT-02/04/09 |
| R3 按实际依赖检查 | 保存不要求质量合格，发布才检查本次发布所需条件 | IT-01/05/06 |
| R4 就地恢复 | 哪项失败恢复哪项，不重跑已完成 SQL | IT-03–07 |
| R5 可结束与返回 | 完成构建可返回列表，往返其他功能不丢上下文 | IT-02/08/11 |
| R6 原约束有效 | 版本、来源、权限、密级、审批与策略仍由服务端检查 | IT-05/06/09/10 |

## 3. 设计原则（ADR）

| # | 决定 | 理由 |
|---|------|------|
| A1 | 设计保存、构建结果分别记录；构建所必需的目标核验和结果回写决定构建是否完成 | SQL 成功但结果尚未确认不能假报成功；后续登记、治理和发布失败不能反向改变构建事实 |
| A2 | 资产登记、质量、治理、发布、上线与运行各自维护结果，失败在所属功能恢复 | 复用现有分项状态和业务对象；接口分项返回不等于后台事务已解耦，T01 必须核对 |
| A3 | 发布独立办理，提交时检查所选版本的必要条件；面板只呈现检查摘要、处理链接和合法动作 | 清单是信息分组，不是只有四种拒绝原因；审批、版本/来源一致性、工程/资产证据及安全约束继续由服务端检查。ADVISORY 不把质量问题伪装成合格，BLOCKING 可阻止发布但不改变构建结果 |
| A4 | 上线后的定时运行不属于发布流程：发布成功就是发布完成 | 某次运行失败是运维问题，显示在运行监控里，模型列表上只有一个「运行」标记 |
| A5 | 不新增页面或菜单（领域规约 B1） | 构建、发布两个弹窗占用原来「发布与构建」弹窗的位置；登记、质量、运行复用现有页面 |
| A6 | 单文件不超过 800 行（领域规约 B5） | 拆开现有 `ModelPublishDialog.tsx` 的职责，构建和发布各用一个组件；开工时复核行数 |

## 4. 实施前核对

- **D1 工程检查归属**：T01/T05 将现有检查逐项分成“构建必要核验”和“发布工程检查”。必要核验随构建执行；发布工程检查独立记录、可查看/恢复，并由发布消费。不得直接把可能包含治理质量的现有命令整体自动接到构建后面。能否复用同一命令、如何拆开副作用，由源码和接口证据决定。
- **D2 旧实现替换**：本轮删除旧需求已经获得用户授权，不要求再次确认。代码尚未实施；T01 核对旧组件和调用方，设计定向替换方案，不把整提交 `git revert` 当作重建文档或编码的前提，不撤掉可复用的权限、错误处理和质量策略修复。
- **D3 后台失败隔离**：已确认一处持久层耦合——`QUALITY_RUNNING` 对账同时执行登记与治理评估（证据见 T01「已核对事实」）；拆分由 F13-T02 在原服务落地。其余核对项：核对独立构建是否依赖发布候选、构建结果与登记/质量的事务交接、状态写入者及真实恢复入口。页面折叠或前端改色不能替代这些检查；未知项仅阻止对应开发任务，不阻止当前设计核对。

## 5. 界面

模型行操作：`[构建]` `[发布]`，模型详情保留保存设计入口。未具备有效构建证据时不能提交发布；仍可查看已有发布记录和具体缺项。必要原因以可见文字/键盘可访问提示表达，不只依赖鼠标悬停。

**构建弹窗**（一屏以内，只和构建有关）

```
┌ 构建 · biz_ads_budget_derived_v2 r3 ──────────────────── ✕ ┐
│ ● 构建失败：目标数仓不可用                  [查看详情 ▸]     │
│ 构建范围  本模型 + 2 个缺失上游          [查看依赖计划 ▸]    │
│ 执行环境  开发环境 ▾        [高级设置 ▸ 依赖策略]            │
│ 最近结果  09-24 14:02 · 3/3 张表完成 · 工程检查通过          │
│                                     [关闭] [重新构建]        │
└────────────────────────────────────────────────────────────┘
```

- 展示未构建、构建中、已完成、失败，以及证据不完整时的待核验/待确认；读取失败是单独的页面状态，不推断业务失败。放弃、继续核验、补写结果、重新构建仅在服务端允许时出现。
- 依赖计划、逐表明细默认折叠。
- 尚未发起任务即被占用时显示“暂不能构建”，不伪造一次构建失败。只有服务端授权时才可关闭对应占用发布单，保留确认；不得自动关闭他人操作。
- 构建完成后可以返回列表或关闭；“查看数据资产”是按需入口，不强制登记、质量、治理、发布或上线。关闭页面不取消后台任务，重开读取同一运行。

**发布弹窗**（可查看记录与缺项，提交要求有效构建证据）

```
┌ 发布 · biz_ads_budget_derived_v2 r3 ──────────────────── ✕ ┐
│ 发布前检查                                                   │
│ ✓ 构建结果    r3 · 09-24 14:02 构建成功                      │
│ ✓ 工程检查    通过                                           │
│ ✓ 资产登记    已登记                                         │
│ ! 数据质量    缺少质量规则（提示，不影响发布）   [去配置]      │
│ ✓ 审批        无需评审（数据管理员自助发布）                  │
│ ✓ 权限与密级  通过                                           │
│ 发布说明 [                                  ]                │
│                                          [取消] [发布]       │
└────────────────────────────────────────────────────────────┘
```

- 每一项只显示结论摘要和处理入口；缺项跳到所属功能办理，不在发布窗口展开质量规则、治理字段或运行配置。打开/刷新不自动构建、登记、检查质量或上线。
- 需要评审时，「发布」按钮换成「提交评审」；评审人打开同一个弹窗，看到的是「通过 / 驳回」。
- 已发布后显示发布信息及服务端允许的动作；回滚按权限和实际状态提供。上线状态与运行详情在运行入口处理，失败不能自动回滚已发布版本。

**模型列表**：分别表达构建、发布、登记、质量、运行状态；它们是可筛选/查看的独立摘要，不再排列成流程进度。优先显示构建和发布，其余通过既有列配置/详情查看，窄屏不强塞所有列。沿用 `ModelDeliveryStatusCell`；目录登记和分析准备仍是不同事实，不能合并后让分析故障变成登记失败。

**通用状态与导航**：加载、空、读取失败、成功分别呈现；读取失败保留上次结果并标记未刷新，依赖最新状态的写操作不擅自放行。往返保留模型、版本、环境、运行/资产标识及返回位置；资产未登记时仍可按模型/运行定位登记处置。嵌入向导、旧深链和批量入口同样取消强制后续流程，不能保留另一套七过程入口。

### 6.1 业务职责与失败范围

| 业务 / 入口 | 当前操作的前置条件与完成事实 | 失败后的保留和恢复 |
|---|---|---|
| 建模设计 / 模型详情 | 当前保存所需身份、结构和版本校验；定义持久化 | 保留输入和旧版本，不要求登记、质量或发布完成 |
| 构建 / 构建弹窗 | 当前版本、可执行来源/目标与安全条件；模式所需核验及构建结果回写完成 | 保留模型；SQL成功但核验未完成时由 F14 安全续跑，不假报完成 |
| 工程验证 / 构建记录或独立验证操作 | 按 D1 区分必要构建核验与发布检查；证据绑定版本和目标 | 发布检查失败保留已确认构建，阻止需要该证据的发布；只恢复相应检查 |
| 登记 / 数据资产管理 | 可确认的目标和统一资产身份；同一对象登记成功 | 登记失败不影响构建；只重试登记，不重跑 SQL、不产生重复资产 |
| 质量 / 规则与报告页 | 所需资产、规则、数据与权限；执行结果和业务结论分别记录 | 缺规则、数据不合格、执行故障分别处置；只恢复质量任务 |
| 治理 / 资产详情 | 所选治理事项自身规则；保存成功 | 普通信息维护失败保留输入，不触发构建；密级等安全字段独立检查 |
| 发布 / 发布弹窗 | 当前版本/范围的构建、工程、资产、策略、审批与安全条件；发布记录成功 | 只恢复发布，保留原构建/质量记录；不隐式发起上线 |
| 上线与运行 / 既有运行入口 | 对应发布版本及合法执行关联/配置；上线生效、每次运行分别记录 | 上线或运行失败不改写发布和建模完成；只恢复对应事项 |

条件只在发起对应操作时检查。数据质量与普通治理可分别办理，不要求填完所有治理资料才检查质量。既有后台登记/对账可继续工作，但必须独立记录和恢复，不参与已完成构建的回滚。

版本、来源、SQL或目标变化只失效相关的当前资格，历史证据保留但不能给新版本放行；普通治理字段修改不触发 SQL 重跑。重复、响应丢失、重启与迟到回调须按原操作标识恢复，不能覆盖当前版本或生成重复副作用。批量中的独立对象保留成功，有真实依赖的对象明确等待/拒绝。
