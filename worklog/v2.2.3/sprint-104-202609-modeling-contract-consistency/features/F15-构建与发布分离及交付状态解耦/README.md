# F15：构建与发布分离及交付状态解耦

**优先级**：P0（大版本入版）
**状态**：DRAFT（2026-09-24 重建；待用户确认 §4 决策后转 READY）
**依赖**：F13（发布前检查、质量策略）、F14（构建与失败恢复）

## 1. 为什么重建

上一版把建模、构建、资产登记、工程验证、治理质量、发布、上线放进同一个弹窗的 7 个步骤（已撤回，见 T01）。问题有三点：

- 一个页面 7 个过程，每个过程都带详细内容，操作者找不到自己该做什么。
- 这些环节归属不同的模块和负责人，生命周期也不同，硬串成一条线不合理。
- 串成一条线后，任何一个下游环节出错，看起来都像整个建模失败。例如上线后某一次定时计算失败，也显示成「第 7 步需处理」。

## 2. 目标

建模人员只对「构建」负责：**构建成功，建模就完成了**。

发布是构建成功之后一个独立、可选的动作。资产登记、治理质量、定时运行在各自的模块里处理。模型上只显示这些环节各自的状态标记，任何一个出错都不会把模型标成失败。

## 3. 设计原则（ADR）

| # | 决定 | 理由 |
|---|------|------|
| A1 | 模型的成功或失败，只由构建决定（构建自带的工程检查也算构建的一部分） | 建模人员能控制、也该负责的只有构建 |
| A2 | 资产登记、治理质量、发布、运行各自是一个独立的状态维度，失败只显示在自己那一项，处理入口在各自模块，从模型出发最多跳转一次 | 后端 `delivery-status` 已经按 materialization / quality / publication / catalog / analysis 分项返回，不需要新建模型 |
| A3 | 发布是独立动作，只在构建成功后可用。发布弹窗只有一张检查清单和发布按钮 | 发布的阻断条件只有 4 项：构建结果有效、资产已登记、阻断（BLOCKING）策略下质量通过、权限与密级通过。提示（ADVISORY）策略下，质量只是清单中的一条提示 |
| A4 | 上线后的定时运行不属于发布流程：发布成功就是发布完成 | 某次运行失败是运维问题，显示在运行监控里，模型列表上只有一个「运行」标记 |
| A5 | 不新增页面或菜单（领域规约 B1） | 构建、发布两个弹窗占用原来「发布与构建」弹窗的位置；登记、质量、运行复用现有页面 |
| A6 | 单文件不超过 800 行（领域规约 B5） | 拆开现有 `ModelPublishDialog.tsx`（当前 1020 行），构建和发布各用一个组件 |

## 5. 界面

模型行操作：`[构建]` `[发布]`。构建成功之前「发布」置灰，鼠标悬停时提示原因。

**构建弹窗**（一屏以内，只和构建有关）

```
┌ 构建 · biz_ads_budget_derived_v2 r3 ──────────────────── ✕ ┐
│ ● 构建失败：目标数仓不可用                  [查看详情 ▸]     │
│ 构建范围  本模型 + 2 个缺失上游          [查看依赖计划 ▸]    │
│ 执行环境  开发环境 ▾        [高级设置 ▸ 依赖策略]            │
│ 最近结果  09-24 14:02 · 3/3 张表完成 · 工程检查通过          │
│                                     [关闭] [重新构建]        │
└────────────────────────────────────────────────────────────┘
```

- 状态只有 4 种：未构建、构建中（有进度，可放弃）、构建成功、构建失败（显示原因和处理办法，错误码放在「查看详情」里）。
- 依赖计划、逐表明细默认折叠。
- 所选模型被其他发布单占用时，作为构建失败的原因展示，处理按钮是「关闭占用发布单」。

**发布弹窗**（构建成功后可打开）

```
┌ 发布 · biz_ads_budget_derived_v2 r3 ──────────────────── ✕ ┐
│ 发布前检查                                                   │
│ ✓ 构建结果    r3 · 09-24 14:02 构建成功                      │
│ ✓ 资产登记    已登记                                         │
│ ! 数据质量    缺少质量规则（提示，不影响发布）   [去配置]      │
│ ✓ 权限与密级  通过                                           │
│ 发布说明 [                                  ]                │
│                                          [取消] [发布]       │
└────────────────────────────────────────────────────────────┘
```

- 每一行只显示一个状态和一个处理入口；处理入口跳到对应模块，比如「去配置」跳到数据质量模块。
- 需要评审时，「发布」按钮换成「提交评审」；评审人打开同一个弹窗，看到的是「通过 / 驳回」。
- 已发布后，弹窗只显示发布信息和「回滚」，不显示运行状态。

**模型列表**：状态列按维度拆开，分别是 构建 | 发布 | 资产 | 质量 | 运行。每一列是一个独立标记，点击跳到对应模块。沿用 `ModelDeliveryStatusCell`，现有「构建状态 / 目录登记 / 分析准备」三列并入这个模式。

## 6. 契约

| 数据 | 来源（已有） | 用于 |
|------|--------------|------|
| 构建 | `delivery-status.steps[materialization]` + 发布单工作台的 `entryEvidence` / `primaryBlocker` | 构建弹窗、列表「构建」列 |
| 资产 | `steps[catalog]`、`steps[analysis]` | 发布清单、列表「资产」列 |
| 质量 | `steps[quality]` + `governanceQuality`（`required` 表示阻断策略） | 发布清单、列表「质量」列 |
| 发布 | `steps[publication]` + 发布单工作台的 `allowedActions` | 发布弹窗、列表「发布」列 |
| 运行 | `getPlanExecutionWorkspace` 返回的 `binding` | 列表「运行」列（只读，点击进运行监控） |

只有 D1 需要改后端：构建成功后自动执行工程检查，结果写回同一个发布单。其余都只读取已有接口。
