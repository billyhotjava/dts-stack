# F13-T07：存量卡单治愈与可运维性

**优先级**：P1
**状态**：DRAFT
**依赖**：T02、T03
**估算**：1 人日

## 目标

部署后两套环境中的存量卡单全部被识别并处理；运维人员有一份可照做的 runbook、一条可查询的巡检 SQL 和明确的告警阈值。

## 技术设计

- **存量处置**：不写数据修复脚本。部署后首轮对账会为每张 `QUALITY_RUNNING` 单生成状态行：
  - 因登记问题卡住的（本机 `d0af4a93…`）→ T02 生效后应自动推进或转为 USER_ACTION；
  - 因治理 MISSING/EXPIRED 卡住的（openEuler）→ 转为 ACTION_REQUIRED，由数据管理员按 T06 处理；
  - 其余 → 按目录归类，SYSTEM 类逐条排查并在 runbook 记录。
  - `BUILT` 状态的存量单（本机 3 张、openEuler 5 张）不在对账范围，只在 runbook 列出并说明它们在等待用户点“发布”，不做处理。
- **巡检 SQL**（写入 runbook）：
  ```sql
  select c.id, c.status, s.phase, s.blocker_code, s.owner_role,
         now() - s.first_seen_at as blocked_for, s.attempt_count, s.next_attempt_at
    from modeling_model_release_candidate c
    left join modeling_release_quality_reconcile_state s
      on s.tenant_id = c.tenant_id and s.candidate_id = c.id and s.candidate_version = c.version
   where c.status = 'QUALITY_RUNNING'
   order by s.first_seen_at nulls first;
  ```
- **告警**：`dts_release_quality_blocked{category="SYSTEM"} > 0` 持续 30 分钟 → 平台告警；`dts_release_quality_blocked_age_seconds{category="USER_ACTION"} > 3 天` → 周报提醒数据管理员。现有告警渠道由 T01 确认；若项目尚无指标抓取，本 task 只交付日志关键字告警（`event=model_publication_quality_system_blocked_escalated`）。
- **Runbook**：`assests/F13-runbook.md`，包含：阶段/类别含义、巡检 SQL、各 SYSTEM 码的排查步骤、如何让某张单立即重试（调用 refresh，而不是改库）、何时建议“取消并创建替代发布单”。
