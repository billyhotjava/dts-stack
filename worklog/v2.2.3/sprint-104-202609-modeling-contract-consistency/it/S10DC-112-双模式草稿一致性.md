# S10DC-112：可视化与代码模式切换丢失配置

## 根因与重构判断

工单截图为“风险明细”r4。当前代码明确存在丢失路径：useModelAuthoringSession.persist 在 codeDirty 时不发送 visualImplementation；modelDraftFromAuthoringSnapshot 对版本化但缺少此字段的结果从空加工配置重建表单。原单测甚至断言产出表名为空，说明这不是单个控件缺陷，而是把“不能继续用原配置生成 SQL”误设计成“删除原配置”。另一个风险是模式按钮仅改 URL，可视化尚未保存的修改未先生成对应代码。

需要范围受控的重构：调整同一模型草稿中可执行加工配置与历史只读参考的区分，统一模式切换时的保存顺序。保留现有草稿服务、版本检查、代码校验和发布流程；不新建 SQL 解析器，不重写建模模块，不承诺任意 SQL 都能双向还原。

## 已确认的业务规则

用户已确认：SQL 无法完整还原时，以代码为当前加工逻辑，上次可视化配置保留为只读参考，明确提示未同步。模型名称、说明、粒度、字段等模型定义独立保留。已有代码修改不得被参考配置重新生成的 SQL 覆盖。

## 详细修复边界

- 草稿中区分 codeAuthoritative、visualReference 与仍可执行的 visualImplementation。参考信息存入现有 JSON 草稿，不新增数据库表或手工修改任务。
- 服务端根据代码文件变化判定代码接管，保留之前的可视化配置，拒绝将只读参考当作可视化保存；未知 SQL 保留原文。
- 提交加工配置后，将参考信息随已有加工记录保存；重新打开/创建后续草稿仍能看到参考信息。
- 前端恢复表单时读取参考信息、保留当前模型定义，并明确只读状态；只有代码模式可继续修改加工逻辑。
- 模式切换前保存当前修改；保存失败留在原模式，避免出现旧代码和新表单混用。
- 不对已丢失且无可信历史记录的配置自动猜测恢复。

## 验证要求

1. 可视化修改后进入代码，保存先于导航，生成代码反映修改；保存失败不切换。
2. 修改 SQL 后返回可视化，原产出名、字段映射及加工参数保留且只读，代码原文保留。
3. 二次保存、关闭重开、提交后重开仍保持代码接管与参考配置。
4. 模型定义修改不丢失，不把只读参考重新变成可执行配置。
5. 旧格式和纯代码模型仍可读取；版本冲突继续拒绝，不覆盖他人修改。
6. 在 /data/dts-stack 同步已推送 SHA 后执行前后端针对性测试和构建，真实页面及现场镜像验收独立记录。
