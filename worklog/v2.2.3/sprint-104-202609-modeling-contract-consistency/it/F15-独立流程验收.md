# F15 独立流程验收

**状态**：NOT_RUN；**依据**：[F15 需求与设计](../features/F15-构建与发布分离及交付状态解耦/README.md) R1–R6。
**本轮仅测试设计**：受测 SHA、镜像/包、环境、执行者、执行日期待实际执行填写。旧 F15 统一阶段用例和历史 PASS 不作为新版证据。

## 数据、观察与责任

使用隔离计划下的两类模型：结构构建模型 S、数据构建模型 D；保留 v1 成功结果和 v2 修改版本，另准备已发布版本、在途任务、批量独立对象及存在真实上游依赖的对象。角色采用实际有权/无权账号，不能只用管理员覆盖所有路径。

测试前后记录模型版本、目标/环境、构建运行、登记资产标识、验证/质量记录、发布记录、执行关联，以及 SQL、登记、质量、发布、部署命令调用次数。跨服务或事务行为需真实持久化/集成证据，组件 mock 只证明展示和消费行为。故障只在受控夹具注入，执行后恢复夹具与配置。

开发承担单元/组件和集成验证；测试承担功能/异常/回归与缺陷确认；业务/运维承担实际使用验收，人员待指定。组件测试验证独立状态与动作映射，系统测试关注下表可观察结果，避免每一层重复同一整链流程。

1. T01 后细化实际输入/输出及夹具；先执行 IT-01/02 的最小切片，再接 IT-03–10；IT-11 随可用页面执行，IT-12 在正式制品就绪后执行。
2. 编译/转换测试、构建、打包均在 `/data/dts-stack`，先从已提交推送的开发分支 `git pull --ff-only` 并核对 SHA；部署：本机测试环境的构建与运行同在 `/data/dts-stack`（Compose 项目 `dts-stack`），按 compose 定向更新服务；历史正式运行目录 `/opt/dts/release/dts-stack`（F6/F9 记录）在本机已不存在，其他环境按其实际部署目录与正式交付配置执行并记录路径。
3. 每项追加版本、环境、真实执行者、命令/步骤、实际结果、截图/日志/状态引用、缺陷和修复确认；本次不创建占位成功证据。
4. PASS、FAIL、BLOCKED、NOT_RUN 分别统计；mock、静态检查、正式服务和客户验收分别标明。测试执行完成而业务要求未满足时，Feature 保持未完成。
