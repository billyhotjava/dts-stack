## 三、后续需要完善的内容

以下顺序取自 `sprint-70-82-architecture-review-20260802.md` 的执行顺序，并补充各 Sprint 自身欠条。

### P0-1：硬化旧 ETL / Airflow 兼容面（第一批已编码，待部署验收）

真实风险不是"绕过 pairwise token 的旁路"（旧 DAG 回调不带 token，当前过滤器实际会拒绝），而是**回调失败被 `|| true` 吞掉、`sync_models` 使用 `all_done`，造成执行状态与资产同步状态不一致**；且 trigger / dbt 文件写入 / Git 变更此前只要求登录、没有动作级维护者权限。

第一批整改已完成编码、30 个聚焦回归通过，内容包括：回调改用 `DTS_AIRFLOW_TO_PLATFORM_TOKEN`（缺失即失败）、移除 `|| true`、`sync_models` 仅在 dbt 成功后执行、Airflow 只获准 `POST /api/etl/dbt/models/sync` 精确路径、写/触发类动作统一要求 `INFRA_MAINTAINERS`。

**待办**：部署并在真实 Airflow / dbt / Platform 联动下完成验收。

### P0-2：接通 canonical 最小建模闭环

后端能力存在，但 `src/pages/data-modeling/` 未消费 canonical API，**前端仅有静态交互壳，客户无法完成真实建模**（新 UI 的失败关闭是有意的安全边界，不是隐性旁路）。

**待办**：不再扩大设计面，先接通最小闭环——至少覆盖规划、ModelSpec CRUD、stage gate，并在目标环境完成浏览器验收。同时必须在文档中严格区分四种状态：**源码存在 / 自动化测试通过 / 已部署 / 浏览器人工验收**。

Sprint 76 / 77 / 79 / 81 / 82 的终验欠条尚未全部关闭。准确表述是"局部真实验证存在，但缺少统一目标环境下**部署 → 登录 → 建模 → 物化 → 资产登记 → 审计落账**的完整证据链"。
