## 一、目录结构约定

每篇文档一个目录，目录内固定三类内容：

```
spec/
├── README.md                     本文件：总览、工作量评估、构建说明
├── _template/                    统一样式模板与构建脚本
├── 01-需求规格说明书/
│   ├── outline.md                目录框架（当前阶段产出）
│   ├── 正文.md                    Markdown 正文（中间产物）
│   ├── assets/                   图表、截图、表格源文件
│   └── dist/                     最终交付物 .docx / .pdf
├── 02-设计方案/
├── 03-测试报告/
├── 04-集成接口说明/
├── 05-安装部署手册/
├── 06-用户使用手册/
├── 07-三员操作及系统维护手册/
└── 08-培训计划和培训材料/
```

`assets/` 与 `dist/` 已预建为空目录，正文撰写阶段直接落文件。

## 二、构建工具链（已验证可用，无需新装依赖）

| 环节 | 工具 | 位置 / 状态 |
|---|---|---|
| Markdown → Word | `build-docx.py` | `worklog/v2.2.3/s10/v4/governance/build-docx.py`，复用参考 docx 的 styles/theme/fonts，仅重写 `document.xml` |
| 样式模板 | 参考 docx | 现用 `s10/v4/数据管理平台数据模型v4.docx`；建议本套件统一到 `_template/` 下自建模板 |
| Word → PDF | `libreoffice` / `soffice` | 已安装（`/usr/bin/libreoffice`），`soffice --convert-to pdf` |

已确认**未安装**：`pandoc`、`python-docx`。现有链路不依赖它们，不必引入。

建议流程：

```bash
# 1. 撰写 正文.md
# 2. 生成 docx（脚本需参数化改造，见下方风险 R3）
python3 _template/build-docx.py --src 01-需求规格说明书/正文.md \
    --ref _template/style-ref.docx --out 01-需求规格说明书/dist/xxx.docx
# 3. 转 PDF
soffice --headless --convert-to pdf --outdir 01-需求规格说明书/dist/ \
    01-需求规格说明书/dist/xxx.docx
```

## 四、关键风险

| ID | 风险 | 说明 | 应对 |
|---|---|---|---|
| **R1** | **测试报告缺真实验收证据** | 截至 2026-08-03，Sprint-71～83 共 13 个仅 3 个形成闭环，多数停在"源码完成 / 自动化测试通过"，缺"部署 → 登录 → 建模 → 物化 → 资产登记 → 审计落账"的统一环境证据链 | 03 必须区分「自动化测试结果」与「系统测试/验收结果」两章分别陈述；不得以 mock、source-contract 冒充真实验收 |
| **R2** | **需求规格与协议差距不一致** | 技术协议对照现网仍有 P0/P1 缺口；若 SRS 声称的能力大于已交付能力，验收时会形成硬伤 | 01 设「需求实现状态矩阵」，逐条标注 已实现 / 部分实现 / 未实现，并与 `protocol-gap-plan.xlsx` 双向对齐 |
| **R3** | **构建脚本为一次性硬编码** | `build-docx.py` 顶部把源文件、模板、输出路径写死为治理方案专用，不支持多文档 | 先做参数化改造（约 0.5 人日），迁入 `_template/` |
| **R4** | **测试基线本身不干净** | 现有 node:test 基线存在 52 项失败（`analytics/*`、`menuTree` 等）；且 `.source-contract.test.ts` 用 `node:test` 而非 vitest，直接跑 `vitest run` 会误报 234 文件失败 | 03 需先固化"正确的测试执行方式"并给出基线失败清单与定性，避免报告数字失真 |
| **R5** | **三员职责需与现场保密要求核对** | 三员（系统管理员 / 安全保密管理员 / 安全审计员）职责划分与权限矩阵须匹配客户现场的保密管理制度，不能只按产品现状写 | 07 撰写前先取得客户方保密管理规定，形成职责映射表再落笔 |
| **R6** | **截图随 UI 变更失效** | 本次已删除各页面内嵌说明文字，`docs/user-guide/assets/screenshots/` 中含旧版界面的截图将与现网不符 | 06 更新前重新采集截图；建立截图登记表（`screenshot-register.md` 已有此机制，沿用） |
