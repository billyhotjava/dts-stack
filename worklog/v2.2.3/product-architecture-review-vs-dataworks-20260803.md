# DTS 产品业务架构复核 · 对标 DataWorks

日期：2026-08-03
范围：DTS 当前**业务结构**（产品域、能力边界、用户旅程），不含技术架构。
对标对象：阿里云 DataWorks，重点参照《数据集成 - 配置数据同步方案》。
证据基线：`portal-menu-seed.json` 菜单树、`dts-ingestion` / `dts-platform` 源码实测、Sprint-71～83 worklog。

---

## 一、结论摘要

DTS 的业务结构**不是 DataWorks 的残缺版，而是另一条产品路线**：DataWorks 是"公有云多租户数据开发 PaaS"，DTS 是"私有化交付的数据治理平台"。因此有一部分 DataWorks 能力（资源组计费、Serverless、多租户配额）不构成差距，不应盲目补齐。

在**真正可比的产品域**上，判断如下：

| 判断 | 内容 |
|---|---|
| **明显强于对标** | 数据建模域（规划→标准→维度→指标→关系图，且有 StageGate/ReleaseCandidate 发布门禁与 dbt 双向往返）；密级全生命周期不可降级传播；共享交换/数据推送；内置 BI + 数据大屏 |
| **基本对齐** | 数据地图与资产台账、血缘与影响分析、质量管控、元数据管理、数据服务 API |
| **存在实质差距** | ①缺工作空间与开发/生产环境隔离 ②数据集成只有 T+1 批量，无实时同步与整库方案 ③运维中心缺 SLA 基线与智能诊断 ④缺治理健康分闭环 ⑤缺敏感数据自动识别 ⑥开发链与建模链治理强度不对等 |

**最重要的一句话**：DTS 当前的头号问题**不是功能缺口，而是交付闭环**。上一份周报已确认 Sprint-71～83 中 13 个只有 3 个真正闭环，多数停在"源码完成、未验收"。在补齐下面任何一个产品域之前，先把现有能力打通到客户可用，否则只是把未验收的面积再扩大一倍。

## 三、差距明细

### Gap-1（P0）缺"工作空间/项目"组织单元与开发-生产环境隔离

**现状证据**：`grep -rn 'devEnvironment|prodEnvironment|环境隔离|DEV_PROD' --include='*.java'` **零命中**；`workspace` 关键字仅出现在建模上下文（建模空间），不是租户级项目边界。

DataWorks 的一切都挂在 Workspace 之下：Workspace 绑定计算引擎、成员角色、以及**开发态/生产态双环境**。这带来三件 DTS 现在做不到的事：

1. 多团队/多业务线在同一平台上互不干扰地工作；
2. "在开发环境改完 → 发布到生产"这一基本安全动作；
3. 权限以项目为边界，而不是只能靠全局角色。

**影响**：这是结构性缺口，不是功能缺口。它会同时限制交付（一套环境只能服务一个团队）、安全（改动直接作用于生产）和商业模式（无法按项目售卖）。

**已有进展**：`worklog/prototype/` 的统一 ELT 重构原型已引入"项目/工作空间 + 阶段向导"，方向正确，但目前仍是前端原型，未进入主产品。回植版本决策为 v2.2.4。

---

### Gap-2（P0）数据集成只有 T+1 批量，无实时同步，也无"整库同步方案"抽象

这是用户给出的对标文档的正面命题，也是差距最集中的地方。

**逐项核实**：

| DataWorks 能力 | DTS 实际 | 证据 |
|---|---|---|
| 整库实时同步（秒级～分钟级） | **未交付** | `ConnectorCapabilityService`：实际在用的 `addax` 连接器 `supportsCdc=false`；声明支持 CDC 的 `airbyte` 连接器 version 字段写的是 **`"future"`**，即预留位 |
| 整库全增量（T+1） | 部分 | `IncrementalSyncService` 是**水位列轮询**（`column > watermark`），属单表级 T+1 增量，非整库方案 |
| 整库选表 / 正则选表 / 分库分表合并 | **无** | `grep 'wholeDatabase|整库|分库分表|shardingTable'` **零命中** |
| 自动捕获源端新增表 | 无 | `IngestionTask.tableMapping` 是显式枚举的 `[{source,target}]` 数组，选库不会自动带出新表 |
| DDL 变更四策略（正常处理/忽略/出错/告警） | **无** | 仅 `TargetTableProvisioner` 的非破坏性 schema reconcile，是系统行为，不是用户可配策略 |
| 断点续传 / 位点重置 | 无 | 无位点概念（水位列不等于 binlog 位点） |
| 历史回灌 backfill | 声明未实现 | `addax` 的 `backfill.enabled=false` |
| 字段赋值（常量/变量/函数、分区动态创建） | 未见 | — |
| 同步任务级监控告警（延迟/Failover/资源利用率） | 部分 | 有 `lastExecutionStatus`、告警记录，无延迟与 Failover 维度 |

**产品含义**：DTS 目前的数据集成是**"逐个任务配置"的粒度**，DataWorks 是**"一个方案覆盖整库"的粒度**。当客户有 200 张表要接入时，DTS 需要建 200 次任务（或维护一个 200 项的 tableMapping 数组），DataWorks 是选库 + 正则一次搞定，且源端加表能自动跟进。这是**规模化交付时最先暴露的差距**。

**另注**：`IngestionTask.graphDsl` 字段注释明写 *"可视化编排 DSL（仅持久化，执行链路暂不消费）"* —— 可视化编排目前是壳，与 Sprint-80/83 前端已部署但未接后端是同一类问题。

**建议顺序**（不必一步到位追实时）：
1. **先做"同步方案"这一层抽象**（选库 → 规则选表 → 批量生成任务 → 统一运维），这一步只用现有 Addax 批量引擎就能做，收益最大、风险最低；
2. 补 DDL 变更策略与源端新增表捕获；
3. 实时 CDC 单独立项评估——它需要引入流式引擎（Airbyte/Flink CDC），是引擎级投入，不应与①②混在一起，且要先确认客户是否真有秒级时效诉求。

### Gap-3（P1）运维中心缺 SLA 基线管理与智能诊断

**现状**：运维中心有运行概览、任务实例监控、告警记录、补数管理——都是"看得到"。
**缺**：DataWorks 的**基线管理**（承诺关键任务的产出时间，自动倒推链路上所有上游、提前预警可能破线）与**智能诊断**（自动定位慢节点、卡点、资源争抢）。`grep SLA|基线|智能诊断` 无实质命中。

**产品含义**："看得到"和"保得住"的区别。客户关心的不是"任务失败了给我告警"，而是"早上 8 点的报表能不能按时出来"。基线是把运维从被动响应转为主动保障的关键抽象。

---

### Gap-4（P1）缺"数据治理中心"——没有治理健康分闭环

**现状**：DTS 有资产台账、质量报告、分级分类、血缘覆盖——但这些是**彼此独立的检查点**，没有汇总为一个可量化、可排名、可下钻、可指派整改的治理总分。

DataWorks 治理中心把存储/计算/质量/规范/安全/研发六类治理项打分，形成健康分排行，并推送具体优化建议驱动持续改进。

**可复用资产**：DTS 已有 `HealthScoreCard`、`RiskAttributionView`、`OverviewTrendView`——但它们在 `analytics/project-cockpit`（**项目管理大屏**，服务于 pjm 项目域），不在数据治理域。这套健康分/风险归因的产品模式可以直接平移到数据治理，实现成本远低于从零设计。

**产品含义**：治理类产品的续费理由往往不是"我帮你管了数据"，而是"我能证明你的数据在变好"。没有健康分就没有这条证据链。

---

### Gap-5（P2）数据安全：脱敏已真实生效，但缺敏感数据自动识别

**先澄清一个容易误判的点**：DTS 的脱敏**是真的**，不是空壳——`CatalogMaskingService` 在 `AssetResource`（采样预览）和 `ExploreExecResource`（即席查询）中实际调用，有 `resolveContext` / `applyMasking` / `toMaskingMetadata` 完整链路，前端 `data-security.tsx` 有规则管理页。

**真正缺的是识别**：`grep 'sensitiveDiscovery|autoClassif|敏感识别|identifySensitive|scanSensitive'` **零命中**。即：脱敏规则要靠人工登记到具体字段上。

DataWorks 数据保护伞支持内置 + 自定义识别规则**扫描全量表自动打标**。DTS 现在的模式在几十张表时可行，到几千张表时打标覆盖率必然成为瓶颈——而覆盖率不足的分级分类，在合规审查时等于没有。

**注**：Sprint-71 标签体系与 Sprint-72 密级沿血缘传播能部分缓解（传播 ≠ 识别，它解决的是"已知密级如何扩散"，不解决"未知字段是不是身份证号"）。两者互补，都需要。

---

### Gap-6（P2）开发链与建模链的治理强度严重不对等

这是个内部一致性问题，比对标更值得关注。

- **建模链**：有 StageGate 门禁、ReleaseCandidate 发布候选、独立审核人/发布人职责分离、回滚、审计落账——治理强度**高于** DataWorks。
- **开发链**（Data Studio 的脚本/编排/即席）：没有等价的版本、评审、发布包、跨环境发布治理。

**后果**：同一个平台上，改一个维度模型要过五道门禁，改一个 Python 脚本可以直接生效。这条不对等的路径会成为治理体系的旁路——用户会自然地绕开重的那条。DataWorks 在两条链上是**同一套**发布流程。

---

### Gap-7（P3）缺迁移助手与开放平台

- **迁移助手**：DataWorks 支持跨项目/跨环境的导入导出与迁移。DTS 有建模域的 imports/exports，但没有产品级迁移能力。**对私有化交付型产品这个价值反而更高**——现场环境搬迁、多客户方案复制、POC 成果转生产，现在都只能靠人工。
- **开放平台（OpenAPI / OpenEvent）**：DTS 没有面向客户的开放 API 体系与治理事件外发，客户无法自建自动化，也无法把 DTS 的治理事件接入自己的工单/监控系统。

---

### Gap-8（P3）无资源隔离视角

`grep 'resourceGroup|资源组'` **零命中**。

私有化部署下**计费**不重要，但**隔离**重要：一个大表全量同步不应该拖垮整个平台的调度与查询。DataWorks 用独享/公共资源组解决，DTS 目前无任何抽象。这条优先级低，但在客户数据量上来后会变成稳定性事故的根因。

## 四、DTS 的差异化优势（不应因对标而丢失）

对标的风险是照着竞品清单补功能，把自己的独特价值稀释掉。以下是 DTS 明显强于 DataWorks 的部分，应继续加固而非平均用力：

1. **密级全生命周期与不可降级传播**（Sprint-72）——沿血缘自动传播最高密级、只升不降、七类生命周期动作可审批可审计。这是信创/涉密场景的刚需，DataWorks 的数据保护伞没有等价能力。**这是护城河。**
2. **建模域深度**——数仓规划（业务分类/分层/数据域/业务过程/数据集市/主题域）→ 数据标准（字段标准/标准代码/词根/命名词典/标准映射）→ 维度建模 → 指标体系（原子/派生/复合/修饰词/时间周期）→ 关系图，配合发布门禁与 dbt 双向往返（Sprint-83）。这条链比 DataWorks 智能数据建模更完整。
3. **共享交换与数据推送**——政务数据交换场景的专有能力。
4. **一体化 BI 与数据大屏**——DataWorks 需要外接 QuickBI/DataV，DTS 内置。
5. **国产化适配**——达梦等国产数据库的深度支持。

## 五、建议

### 优先级排序

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | 先关闭现有交付闭环，不新增产品域 | 13 个 Sprint 仅 3 个闭环；再铺新面积只会放大未验收债 |
| **P0** | Gap-1 工作空间与开发/生产环境隔离 | 结构性缺口，同时卡住交付、安全和商业模式；原型已就绪，是回植而非新建 |
| **P0** | Gap-2 第①步：数据集成"同步方案"抽象 | 规模化交付第一个撞墙点；用现有 Addax 引擎即可实现，不需引擎级投入 |
| **P1** | Gap-4 治理健康分 | 可从 project-cockpit 平移，成本低；是治理产品的续费证据链 |
| **P1** | Gap-3 SLA 基线管理 | 把运维从被动响应转为主动保障 |
| **P2** | Gap-5 敏感数据自动识别 | 规模化后合规覆盖率的前提 |
| **P2** | Gap-6 开发链发布治理对齐建模链 | 修补治理旁路，属内部一致性 |
| **P2** | Gap-2 第③步：实时 CDC | 需引擎级投入，先确认客户真实时效诉求再立项 |
| **P3** | Gap-7 迁移助手 / Gap-8 资源隔离 | 迁移助手对私有化交付价值被低估，可提前 |

### 三条判断原则

1. **不要照抄 DataWorks 的功能清单**。资源组计费、Serverless、多租户配额是公有云商业模式的产物，私有化交付不需要。要对标的是**用户旅程的完整度**，不是功能数量。
2. **抽象层级的差距 > 单点功能的差距**。Gap-1（工作空间）和 Gap-2（同步方案）本质都是"少了一层抽象"，补上后下面的功能会自然长出来；反过来堆单点功能填不平抽象层的坑。
3. **先把强项做到无可替代**。密级传播和建模深度是 DataWorks 短期补不上的，把这两块做透形成的差异化，比追平数据集成的实时能力更能决定竞标结果。
