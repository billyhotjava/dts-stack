# T02: 实测编译产物与 canonical bundle 可行性

**优先级**: P0
**状态**: IN_PROGRESS
**依赖**: 无（可与 T01 并行；必须早于 F2 全部 Task）

## 目标

用可回收 E2E 样本确证 DESIGNER 的 3 文件预览能补齐为可静态校验、可冻结、可恢复、可编译的 4 文件 canonical dbt project。在它关闭前，接管生产代码不得开工。

## 为什么必须先做

复核结论 A 与账本 #24/#25 目前只有读码证据。若直接冻结 3 文件，缺少 `dbt_project.yml` 会在静态校验或草稿恢复阶段失败；若 implementation 字段不满足 import seam，制品导入会在事务中失败。

## 技术设计 (Contract-first)

本 Task 不改生产代码，只产出事实。

### 探针 A：DESIGNER 编译产物的真实类型集合（验证结论 A）

仅使用 T01 新建的 `E2E_S91_DESIGNER_*`，禁止触碰业务模型：

1. 调既有 `POST /{id}/lifecycle/compile`，或直接在测试中调用 `CanonicalModelLifecycleCompilerAdapter.compile(...)`；
2. 记录返回 `ArtifactWrite` 的 **`artifactType` 去重集合**与 `path` 列表；
3. 查库确认落地类型：

   ```sql
   select artifact_type, node_kind, path
   from modeling_dbt_artifact
   where model_spec_id = :id and revision = :rev
   order by artifact_type, path;
   ```

4. 证据只记录 path、artifact type、node kind、byte size 与 checksum；SQL 正文仅存在测试内存，不进入 worklog、日志或审计 payload。

**判定**：
- 编译器输出类型集合必须为 `{STG_SQL,SQL,SCHEMA,TEST}`，文件必须恰为 3 个；不满足则保持 G1 GAP 并修订契约。

### 探针 B：4 文件 canonical project 的静态校验与冻结

1. 使用系统派生 project identity 生成确定性 `dbt_project.yml`，与探针 A 的 3 文件组成 4 文件 project；project-file 生成规则必须复用或从 `DbtCanonicalProjectReconstructor` 最小抽取，禁止复制第二份。
2. 调 `AdvancedDbtDraftStaticValidator.validate(files)`，再调 `DbtProjectBundleManifest.freeze(...)` 与 `restore(...)`。
3. 断言 projectKey、projectChecksum、bundleChecksum 稳定，恢复文件恰为 4 个，且每个 path/content checksum 与输入一致。

### 探针 C：接管后编译门禁的直接验证

在测试中模拟：把探针 A 的制品按**修订后契约**（只取被拥有节点的 SQL/SCHEMA + 整包 CONFIG）写入一个 DBT_MANAGED implementation，然后调 `compile`：

- 断言不抛 `MODEL_DBT_IMPORT_REQUIRED`；
- 断言 `CONFIG` bundle 内可检出 `dbt_project.yml` 与 `stg_*.sql`，文件数为 4；
- 断言 `dbtUniqueId` 与 `ExecutionPlan.selector` 与接管前一致。
- 断言 implementation 满足 `ACTIVE + DBT_MANAGED + GENERATED + 单一 DBT generator config`，否则 import fail closed。

这三条断言应当直接演进为 F2/T02 的阻断测试，不要写完就丢。
