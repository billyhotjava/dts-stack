# Sprint-68：DTS 标准内容库与通用基线产品化

**时间**：2026-07  
**状态**：READY  
**类型**：Content Platform / Data Governance / Safe Upgrade / Offline Delivery  
**目标**：把 Sprint-57 已有标准包管道升级为可版本化、可追溯、可安全升级的 DTS 标准内容库，使新部署客户可直接安装通用基线并只做少量本地调整；PJM/dbt 资产仅在通过严格准入后进入可选项目管理扩展包。

## 1. 背景

Sprint-57 已完成标准包 `preview → apply → rollback`、内置包安装、导入历史和页面入口，但当前内置内容仍是验证级规模：

- 3 条业务术语、15 条常用数据元；
- 性别、学历、行政区划省级 3 张公共码表；
- 内置资源位于 dts-platform classpath，内容升级依赖后端镜像重建；
- 同编码重装会直接更新现有术语、数据元和码表，尚不能证明客户本地修改不会被覆盖；
- 标准包只覆盖术语、数据元、码表目录、码值和映射，尚未纳入计量单位；
- 通用数据元使用 `source_system` 表达来源系统，但缺少标准来源、版本、许可证和本地覆盖等独立溯源字段。

新部署需要的是“可编辑的高覆盖基线”，不是把未经审核的行业报表字段、测试数据或标准全文批量塞入生产库。

## 2. 方案比较与决策

| 方案 | 结论 | 原因 |
|---|---|---|
| A. 继续向 classpath CSV 追加大量数据 | 不采用 | 上线快，但内容升级需要重建镜像，无法独立发布，也不能保护客户修改 |
| B. 建立版本化内容仓库、离线签名包和客户覆盖层 | **采用** | 复用现有导入管道，同时获得来源治理、独立升级、冲突预览和现场离线交付能力 |
| C. 部署后在线抓取国家/行业标准 | 不采用 | 现场常为离线环境；来源许可、格式漂移、可重复构建和审计均不可控 |

## 3. 产品主线

```text
授权/公开结构化来源 + 已有 DTS/PJM 候选资产
  → 来源登记与许可审查
  → 结构化抽取
  → 通用性/血缘/重复/命名/质量/客户适用性六道准入
  → 内容包构建、校验、签名
  → DTS 离线包目录
  → 部署画像选择并预检安装
  → DTS 基线 / 客户扩展 / 本地改写三层生效视图
  → 后续内容升级三方 diff、冲突确认、审计与回滚
```

## 4. PJM/dbt 引用边界

候选来源：`worklog/v2.2.3/s10/v4/pjm/dbt_model`。

当前预审结论：

1. `models.tsv` 中模型治理状态仍为 `DRAFT`，不能因“第一阶段实现完成”而自动晋升为 DTS 基线；
2. `pm_schema_v2.yml` 的关键唯一性、非空和 accepted-values 测试多为 `severity: warn`，准入前必须升级为阻断门禁并得到真实 `dbt test` 通过证据；
3. Canonical dim 可作为候选，但风险等级、节点类型、质量归零、技术状态等属于项目管理语境，默认进入可选 `pjm-project-management-reference` 包，不进入通用核心包；
4. Alias dim 是来源值归一化映射，不是公共码表；只能在保留 `source_system=PJM_V4` 和上下文的情况下转为码表映射；
5. `dim_boolean_alias` 的“已完成→是”和 `dim_risk_category_alias` 的“供应链/管理/资源→进度”存在上下文或信息损失，禁止进入通用基线；
6. ODS 原始行、测试 CSV/XLSX、`target/`、`logs/`、看板 JSON、截图、ZIP、`.bak` 和生成 SQL 均不是标准内容来源；
7. DWS/ADS 指标及公式归指标注册表所有，不得伪装成业务术语、数据元或公共码表导入标准模块。

详细判定见 [PJM 候选准入矩阵](assets/pjm-candidate-admission-matrix.md)。

## 5. 全局约束

1. 复用 Sprint-57 的标准包预检、应用、历史和回滚管道，不建立第二套数据库种子机制。
2. 客户本地修改不得被包升级静默覆盖；存在冲突时必须 fail closed。
3. `source_system` 与“标准内容来源”分离，后者必须保存包、版本、记录键、来源和许可证。
4. 内置业务术语默认是 `REFERENCE` 或 `DRAFT`，不得无条件强制为客户正式 `ACTIVE` 术语。
5. 计量单位进入包契约时使用稳定 `base_unit_code`，入库阶段再解析 UUID 引用。
6. DTS 通用基线不出现 PJM、具体客户、报表编号、研究室、军工或其他行业专属核心字段。
7. 国家标准全文公开不等于允许商业再分发；没有明确授权或合法来源登记的内容不得构建进发布包。
8. 行政区划默认最多到县级；不把不再公开或无授权的乡镇、村级统计代码作为交付目标。
9. 内容包必须可离线安装，远程目录只能作为可选更新源，不能成为现场部署前置条件。
10. Chrome 95、权限、租户隔离、CAS/ETag、审计、失败恢复和窄屏属于完成标准。

## 8. 完成标准

- [ ] 新部署可通过“通用企业版”画像离线安装 DTS 通用基线，不需要逐条创建术语、数据元、码表和计量单位。
- [ ] 标准内容至少形成 10 个可独立安装、可追溯、可校验的包；每个包均有版本、来源、许可证结论、校验和和依赖。
- [ ] 术语、数据元、码表、映射和计量单位使用一条包级 preview/apply/rollback 管道。
- [ ] DTS 基线、客户扩展、本地改写三层可区分；升级不会静默覆盖本地修改。
- [ ] 内容升级可展示新增、上游变更、本地变更、冲突、弃用和替代关系，并支持显式确认与回滚。
- [ ] PJM/dbt 候选形成逐项 ACCEPT/CONDITIONAL/REJECT 报告；拒绝项和理由可审计。
- [ ] PJM 扩展包不包含 ODS 行、测试数据、target/logs、看板制品或有损通用别名映射。
- [ ] 真实 PostgreSQL 证明首次安装、重复安装、内容升级、本地覆盖、冲突、弃用和回滚。
- [ ] 后端定向测试、前端 source-contract、production build、内容 CI、Chrome 95 桌面/窄屏和 GitNexus 变更审计均留存证据。
- [ ] 最终发布评审分别给出代码、测试、内容、部署和浏览器五层结论，不用工作日志状态代替真实证据。

## 9. 明确不做

- 不复制、汇编或内置未经授权的国家/行业标准全文。
- 不追求把所有行业内容默认安装到每个客户环境。
- 不把客户现场数据、PJM 测试数据或报表样例作为 DTS 基线。
- 不把 dbt DWS/ADS 指标当作标准模块的业务术语或数据元正文。
- 不在没有本地覆盖保护前扩充并推送大规模内置内容。
- 不以 classpath 大 CSV 作为长期内容发布和升级边界。
