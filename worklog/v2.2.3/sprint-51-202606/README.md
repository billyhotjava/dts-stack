# Sprint-51: 现有页面横切职责域重构

**时间**: 2026-06  
**状态**: IN_PROGRESS  
**类型**: Frontend-first Refactor Planning / Existing Pages Only  
**目标**: 参考 v2.2.4 Sprint-2 的“字典 / 血缘 / 治理 / 元数据 / 全局状态”横切职责域思想，在 v2.2.3 **现有页面**上做界面重构规划；先不新增 `/v2` 命名空间、不回植新 IA 骨架、不改代码，后续实施以现有页面和真实接口缺口为第一约束。

## 背景

v2.2.4 Sprint-2 的核心价值不是某个新目录或新 UI 壳，而是把接入、集成、资产、指标之间散落的基础能力收敛为横切职责域：

- 字典域：系统类型、参考码、业务术语、连接器等统一消费。
- 血缘域：DataSource -> Dataset -> Metric 链路不再由页面各自猜。
- 治理域：质量、授权、发布门禁等能力跨资产和指标复用。
- 元数据与标签：OpenMetadata 中的 owner、domain、tags、profile 进入资产详情。
- 状态编排：部门、页面筛选、详情抽屉、联动刷新需要有明确边界。

v2.2.3 已经有大量客户可见页面和菜单闭环（Sprint-45~50），因此本 sprint 不复制 v2.2.4 的 `/src/v2` 新骨架，而是在现有页面上完成重构规划，优先保证客户可见路径连续、Chrome 95 可验收、后端 API 只补真实缺口。

## 重构边界

| 规则 | 决策 |
|------|------|
| 页面来源 | 以 v2.2.3 现有页面为第一事实源 |
| 菜单策略 | 默认不新增菜单，不新增 `/v2` 命名空间 |
| 实施顺序 | 先页面矩阵和交互闭环，再抽服务/补 API |
| 后端策略 | 现有 API 能承载就不补；缺口必须从页面验收项倒推 |
| 兼容策略 | 保持 Sprint-45~50 已完成路由、工作台和 Chrome95 约束 |
| 验收策略 | source-contract / 页面 smoke / API 缺口登记必须同步 |

## 执行顺序

```
F0 页面事实源
  -> F1 字典域收敛
  -> F2 血缘与元数据详情
  -> F3 治理域复用
  -> F4 工作台主链路
  -> F5 API缺口与验收证据
```

F0 是所有编码前置 gate；F5 贯穿所有 Feature，任何后端新增必须先登记页面缺口、字段契约和验证方式。
