# Demo 验收清单

## 1. 验收原则

以下证据层级必须区分：

```text
UI 草稿保存
≠ 配置已生效
≠ 编译通过
≠ 测试通过
≠ 物理表已生成
≠ 调度运行成功
≠ 权限和业务消费验收通过
```

每个结论必须附实际 ID、revision、run ID、时间和证据路径。不得仅使用 Mock、静态页面或文档设计作为运行证据。

## 5. G3 标准与主数据

- [ ] 业务术语有稳定编码、定义、owner 和版本。
- [ ] 数据元有稳定 ID/版本、类型和约束。
- [ ] 复用了已有 COUNT、PERCENT、CNY 单位，或记录了新建理由。
- [ ] 任务状态和风险等级码表使用 ASCII `standard_code`。
- [ ] 项目健康状态使用 `PH-GREEN`/`PH-AMBER`/`PH-RED` 稳定码。
- [ ] 所有已知中文值和 H/M/L 别名能映射。
- [ ] 未识别码值进入 UNKNOWN/质量失败，不进入 OTHER。
- [ ] 组织和项目业务编码通过非空、唯一测试。
- [ ] 组织更名不会生成新的业务组织编码或重复当前组织。
- [ ] 密级词汇未写入业务标签或公共码表。

建议证据：`evidence/03-standards-master-data.md`。

## 6. G4 模型设计和版本关系

- [ ] 3 个业务维度定义均为 CURRENT。
- [ ] 概念维度不维护属性/主键；主键与维度属性编码在维度表字段层声明（重构后契约）。
- [ ] 日期维度使用受控 DATE_DIMENSION 生成器（若当前 UI 未暴露，需在数据实现侧确认）。
- [ ] 组织维度为 TYPE1，周期历史由任务快照事实承担。
- [ ] 项目维度为 TYPE1。
- [ ] FACT 粒度是任务＋快照日期。
- [ ] FACT 粒度键唯一命中 `task_snapshot_id` KEY 字段。
- [ ] `snapshot_date` 是 TIME 字段。
- [ ] FACT 事实形态和时间语义是 PERIODIC_SNAPSHOT/SNAPSHOT_DATE。
- [ ] SUMMARY 只引用锁定 revision 的上游模型。
- [ ] APPLICATION 填写消费场景并只引用锁定上游模型。
- [ ] 字段技术编码全部为小写英文、数字和下划线。
- [ ] 所有字段有中文业务名称和公开密级。
- [ ] KEY/MEASURE 字段标准覆盖率为 100%。
- [ ] 每个直接映射字段保留来源字段引用。
- [ ] 不存在自引用、循环依赖或目标表作为自身输入。

建议证据：`evidence/04-model-design.md`。

## 10. G8 资产、血缘、权限和消费

### 10.1 资产与血缘

- [ ] 6 个模型物理资产具有唯一资产身份。
- [ ] owner、密级、标签、生命周期齐全。
- [ ] `GOVERNED` 只加在已通过门禁的资产上。
- [ ] 表级血缘覆盖 source→ODS→DWD→DWS→ADS。
- [ ] 至少验证 5 条关键字段血缘。
- [ ] 血缘影响分析能定位 ADS、BI、API 和数据产品。

### 10.2 权限

- [ ] 已授权业务查看者可查看 ADS、指标、BI、API 和数据产品。
- [ ] 无授权用户在五个入口均不可消费数据。
- [ ] API 无权限请求返回拒绝，不返回部分数据。
- [ ] BI 和数据产品不使用独立的本地权限绕过平台策略。
- [ ] read/write/export 权限事实和审计记录一致。

### 10.3 消费

- [ ] BI 看板使用 ADS，不直接查询 ODS/STG。
- [ ] BI 包含指标卡、项目明细和日期/组织筛选。
- [ ] API 只返回业务字段，不泄漏 SQL、dbt 路径或凭据。
- [ ] 数据产品关联 ADS、指标、BI 和 API。
- [ ] 数据产品有 owner、刷新频率和使用说明。

建议证据：`evidence/08-consumption-permission-lineage.md`。

## 11. G9 运行、审计和可恢复性

- [ ] 基线成功、质量失败、修复成功三次运行均有 run ID。
- [ ] 实例页可查看状态、开始/结束时间和日志。
- [ ] 失败记录包含原因、受影响资产和修复动作。
- [ ] 修复后重跑与原失败记录可关联。
- [ ] 数据源、标准、模型、指标、权限和发布动作有审计记录。
- [ ] 审计记录包含操作者、租户、对象、动作、结果和时间。
- [ ] 未分类审计动作单独记录为产品缺口。
- [ ] 证据文件不包含数据库密码、token、Cookie 或真实客户数据。

建议证据：`evidence/09-ops-audit.md`。

## 12. 最终 GO/NO-GO

### GO 条件

- G1～G9 全部通过。
- 物化租约契约已在实际部署中修复并验证。
- 模型、质量、指标、资产、权限、血缘和消费都引用同一批当前 revision。
- 无客户 ODS 变更。
- 证据包可以由第三方依据 ID 和时间复核。

### NO-GO 条件

任一情况存在即不能宣称完整 Demo 打通：

- 只创建 UI 草稿，没有真实物理表。
- dbt build 未启动或 profile lease 消费后失败。
- 质量执行错误被展示为通过。
- 标准、密级、owner 或权限门禁缺失。
- 血缘只有手工文档，没有运行/制品证据。
- BI/API 直接消费 ODS 绕过治理资产。
- 无授权用户可以从任一消费入口看到数据。
- 客户 ODS 被修改。
- 验收证据依赖 Mock 或无法对应实际对象 revision。

```text
签认：数据管理岗 / 业务验收人 / 技术支持方
```
