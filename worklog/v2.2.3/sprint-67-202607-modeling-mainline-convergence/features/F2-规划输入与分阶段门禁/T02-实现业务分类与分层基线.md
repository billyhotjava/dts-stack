# T02：实现业务分类与分层基线

**优先级**：P0
**状态**：DONE
**依赖**：F2-T01

## 目标与用户结果

用户在计划详情直接确认“管什么业务、数据放哪”，保存后立即得到新的基线和下一步，不再被送往一个混合概念页面完成隐式状态。

## 范围与不做

- 范围：独立业务分类编辑单元、分层/命名/历史策略、分类实时解析、版本并发、保存和安全返回。
- 不做：不复制分类正文，不在计划页创建第二套 catalog domain；不复用会整组覆盖分类/活动/指标的旧 `saveBusinessScope` 写路径；不在本 Task 重算九阶段下一步。

## 输入契约

| 输入 | 必填阶段 | 校验 | 缺失行为 |
|---|---|---|---|
| planId | 页面进入 | 存在且可编辑 | 404/403 状态页 |
| domainBindings | 进入模型设计前 | 至少一个 CONFIRMED、无重复、可访问 | `CATEGORY_SCOPE_INCOMPLETE` |
| layerScheme | 进入模型设计前 | 支持的经典分层枚举 | `PLANNING_POLICY_INCOMPLETE` |
| namingPolicy | 进入实现前 | 前后缀/大小写规则有效 | 可保存草稿，阻止实现 |
| historyPolicy | 进入实现前 | SCD/保留策略有效 | 可保存草稿，阻止实现 |
| defaultTimeZone | 否 | 非空时必须是 IANA ZoneId | 不默认写死行业/地域时区 |
| If-Match/version | 每次保存 | 等于当前编辑单元版本 | 409 并发冲突 |

## 输出产物

- `CategoryScopeView`：domain binding、实时名称/编码、AVAILABLE/MISSING/ARCHIVED/FORBIDDEN、readiness、issues、lastValidatedAt；
- `VersionedValue<CategoryScopeView>`：响应体携带 version，HTTP 同时返回 `category-scope:{version}` ETag；
- `PlanningPolicyView`：策略正文、MODEL_DESIGN_READY/IMPLEMENTATION_READY、issues；
- `VersionedValue<PlanningPolicyView>`：响应体 version 与 `policy:{version}` ETag；
- 更新后的 PlanningBaseline/StageProjection；
- 审计事件和 lastValidatedAt。

## 详细设计

1. 新增 `EditUnit.CATEGORY_SCOPE("category-scope")`。它和兼容 `BUSINESS_SCOPE` 共用数据库 `business_scope_version` 做 CAS，但新 API 只读写 `modeling_warehouse_plan_domain`；旧、新入口互改必须冲突，禁止静默覆盖。
2. 新增 `GET/PUT /api/modeling/warehouse-plans/{planId}/baseline/categories`。PUT 只接收 `domainId/confirmationStatus`，不得接收 `processId/objectId`、分类名称或正文。
3. 分类 PUT 先验证全部输入与解析结果，再 CAS，再只替换 domain binding；不得删除或重写 process/metric 行。
4. 新增 `CatalogDomainResolutionPort`，计划服务只依赖端口，不直接拥有 Catalog 正文。生产适配器必须真实区分 AVAILABLE/MISSING/ARCHIVED/FORBIDDEN；若 Catalog 尚无生命周期/访问事实，必须用 additive schema/adapter 补齐并单独评审，不能以“查到=AVAILABLE、查不到=MISSING”冒充完成。
5. 分类 READY：至少一个 `CONFIRMED + AVAILABLE`；CANDIDATE 不 READY；EXCLUDED 不计有效分类；任一非排除绑定 MISSING/ARCHIVED/FORBIDDEN 时 BLOCKED。业务活动和旧指标需求均不参与该判断。
6. 分类 binding 只持有 ID、确认状态和校验时间；名称/编码由 Catalog projection 实时返回。失权时不得泄露名称、描述或负责人。
7. 新增 `GET /baseline/policy`；GET/PUT 都在响应体返回 version，不能只依赖会被共享前端拦截器丢弃的响应头。
8. 分层策略采用两级 readiness：有效 `CLASSIC_ODS_DWD_DWS_ADS` 即 `MODEL_DESIGN_READY`；命名与历史策略也有效才是 `IMPLEMENTATION_READY`。
9. 初始通用枚举冻结为 `CLASSIC_LOWER_SNAKE/CLASSIC_UPPER_SNAKE` 和 `PRESERVE_BUSINESS_HISTORY/LATEST_STATE_ONLY`；拒绝任意字符串。defaultTimeZone 可空，非空按 `ZoneId` 校验。
10. `PlanningBaseline.PLANNING_POLICY_INCOMPLETE` 只表示缺少有效 layerScheme，不因实现阶段的命名/历史策略尚未填写而阻止模型设计。
11. 用新的 forward-only Liquibase changeset 增加分类校验时间和策略草稿所需的 nullable 变更；禁止修改 `20260718_01`。Catalog lifecycle/ACL 如需扩展，必须是单独、可回滚的 additive 提交。
12. 计划详情 baseline 使用“业务分类 / 数仓分层 / 来源盘点”三个 Tab；前两个是真实表单，各自只有一个主按钮。页面不出现业务过程或业务对象。
13. “管理业务分类”是次级操作，带白名单 `returnTo` 和 planId；返回后重新读取 API，不读取 session/localStorage 作为真值。
14. 保存成功后重新读取 category/policy、PlanningBaseline 和 StageProjection；前端不本地推导生命周期或下一步。409 保留脏表单并显示响应体 currentVersion。
15. 分类正文新增/编辑继续由 `/api/catalog/domains` 原主负责；计划只保存稳定引用，禁止“读 catalog、写 semantic”双真值。

### Catalog 解析事实的独立提交边界

- `catalog_domain` 增加可审计的 `ACTIVE/ARCHIVED` 生命周期和 `PUBLIC/RESTRICTED` 可见性；历史记录显式回填 `ACTIVE + PUBLIC`，不由适配器猜默认值。
- RESTRICTED 分类复用现有 `AssetOwnership/AssetGrant/AssetPermissionService`，资产类型为 `CATALOG_DOMAIN`；不新建第二套 ACL。
- 解析顺序优先保护信息：无记录为 MISSING；RESTRICTED 且无权为 FORBIDDEN 并清空名称/编码/负责人/描述；有权后再区分 ARCHIVED/AVAILABLE。
- Catalog 的 list/tree/stats 读取面必须消费同一可见性规则；分页在查询前应用 `PUBLIC OR authorized IDs` 谓词，不得先 page 后过滤而通过 total 泄露隐藏分类。
- Catalog 事实、resolver 与回归测试作为独立 HIGH-risk commit；通过后 category-scope 才得接入，避免和计划 CAS 改动混杂评审。

## 异常、权限与恢复

- 分类归档/无权：显示具体绑定并要求替换，不把其当已确认。
- 409：响应体返回 editUnit/currentVersion，展示重新加载/保留草稿选项。
- 返回分类页后丢失 planId：通过白名单 returnTo 回计划，不写 session 真值。
- 分类失权：只显示“不可访问分类”和修复动作，不泄露 Catalog 正文。
- 计划 PUBLISHED/ARCHIVED：分类和策略写入均返回生命周期冲突，不产生部分写入。

## 实施与测试设计

1. Contract RED：分类 DRAFT/READY/BLOCKED、无 process 仍 READY、分层两级 readiness、枚举与 ZoneId。
2. Service IT RED：category 保存只改 domain 行；旧 business-scope 与 category 共列 CAS；category/policy 版本隔离；过期版本零写入；租户/生命周期隔离。
3. Resolver RED：AVAILABLE/MISSING/ARCHIVED/FORBIDDEN、失权不泄露、分类正文不复制；任何缺失状态能力必须先补真实 adapter。
4. Resource RED：GET/PUT body version + ETag、428/409/403、409 body currentVersion、canonical payload 无 process/object。
5. Frontend RED：三个 Tab、真实表单、响应体版本、409 保留草稿、保存后四项刷新、安全 returnTo、无退役词。
6. 用两个浏览器会话验证并发、分类管理返回、Chrome 95 与窄屏；记录 API/DB 证据。

## 实施结果（2026-07-19）

- category/policy 已使用独立 edit-unit CAS、响应体版本与强 ETag；真实旧 `category-scope:1` 写入在版本 2 时返回 `409 WAREHOUSE_PLAN_EDIT_UNIT_VERSION_CONFLICT`。
- Catalog adapter 真实区分 AVAILABLE/MISSING/ARCHIVED/FORBIDDEN，分类正文仍由 Catalog 持有；计划只保存 domainId 与确认状态。
- 真实 Chrome95 保存 `项目管理域` 与经典分层/命名/历史/时区后，数据库 `business_scope_version=2`、`policy_version=2`，策略 readiness 为 `IMPLEMENTATION_READY`。
