# T01：明确双起点计划创建输入

**优先级**：P0
**状态**：DONE
**依赖**：F1-T03

## 目标与用户结果

用户从业务目标或现有资产开始，都能用最少字段创建一个真实计划，并在刷新或跨页面后恢复同一 planId。

## 范围与不做

- 范围：创建计划表单、DTO、服务端技术编码、幂等、初始来源原子写入、返回路径和指定计划恢复。
- 不做：创建时不要求分类、过程、业务对象、完整来源盘点、分层策略或指标；不在本 Task 建资产选择器和负责人转派 ACL。

## 输入契约

| 字段 | 必填 | 规则 | 默认/缺失行为 |
|---|---|---|---|
| name | 是 | trim 后 1-128 字符；允许重名 | 空或超长返回字段错误 |
| objective | BUSINESS_FIRST 是，ASSET_FIRST 可后补 | trim 后的客户语言建设目标 | 资产起点后补时工作台显示缺口 |
| scope | 否 | 初始边界说明 | 缺失保持 null，不伪造 |
| onboardingMode | 是 | BUSINESS_FIRST/ASSET_FIRST，创建后不可修改 | 根据入口默认，提交前可切换 |
| ownerId | 否（服务端解析后必有） | 仅允许等于当前认证用户 | 缺失默认当前用户；伪造他人返回 `WAREHOUSE_PLAN_OWNER_FORBIDDEN` |
| ownerDepartmentId | 否 | 仅允许当前认证上下文中的部门 | 无部门保持 null，不伪造 |
| initialSourceRefs | ASSET_FIRST 至少一个 | `sourceType/sourceId/sourceVersion?`；按 type+id 去重 | BUSINESS_FIRST 为空合法；服务端生成 bindingId，初始为 CANDIDATE |
| idempotencyKey | 是 | trim 后 1-128 字符；同租户同 key 同请求返回同一计划 | 弹窗打开时生成，失败重试复用，取消或成功后清除 |

请求体不接收 `code`、`planId`、domain/process/object、完整策略或指标。技术 `code` 由服务端先生成 plan UUID，再固定派生为 `wp_<uuidhex>`；禁止前端 `Date.now()`、数据库时间或随机业务文案生成编码。

## 输出产物

- `CreateWarehousePlanResult`：`planId/plan/version/etag/initialSourceBindings/nextAction/replayed`；
- HTTP `201 + Location + ETag`（重放可返回同一聚合，响应体 `replayed=true`）；
- `nextAction=/modeling/plans/{planId}/baseline`，页面默认 Tab 根据 onboardingMode 决定；
- 初始 source binding 作为计划版本 1 的 CANDIDATE，不额外递增 sourcesVersion。

## 详细设计

1. 创建 API 在一个事务内写计划头和初始来源；任一来源失败，计划头一并回滚。
2. 新增 nullable `idempotency_key varchar(128)`、`idempotency_request_hash varchar(64)`、`idempotency_response_snapshot jsonb` 和 `(tenant_id,idempotency_key)` 唯一约束；存量记录保持 null，使用新的 forward-only changeset，禁止修改旧 changeset。
3. 请求 hash 使用 SHA-256，覆盖规范化后的 name/objective/scope/mode/有效 owner/department 与排序后的来源引用；不包含 key、服务端 code 或生成 ID。
4. PostgreSQL 通过 `INSERT ... ON CONFLICT (tenant_id,idempotency_key) DO NOTHING` 处理并发；不能捕获唯一异常后在 aborted transaction 中继续查询。
5. 首次创建在同一事务中持久不可变创建响应快照；同租户同 key 同 hash 始终返回创建时的 version 1 plan 和初始来源，不被后续改名或来源替换污染；同 key 不同 hash 返回 `409 WAREHOUSE_PLAN_IDEMPOTENCY_CONFLICT`；不同租户可复用 key。
6. 当前认证 login/userId 和 dept 是负责人真值；前端显示只读创建上下文，不提供自由文本负责人。最终授权仍由后端 `@PreAuthorize` 和字段校验执行。
7. 前端弹窗每次打开生成一个密码学随机 key（`crypto.randomUUID()`，Chrome 95 兼容路径使用 `crypto.getRandomValues()`）；请求超时和字段修正继续复用。
8. 前端只消费响应体中的 planId/etag/nextAction，不自行计算 code、版本、完成度或成功路由。
9. URL 指定 planId 时直接 GET 该计划；404/403 清除无效提示并显示恢复说明，禁止静默切到列表第一条。
10. 最近计划只可作为 UI 偏好；计划内容、来源、版本和 StageProjection 始终来自 API。
11. 工作台计划、阶段投影与详情页证据请求使用递增 request sequence；当用户从计划 A 切换到 B 时，A 的迟到响应不得覆盖 B。

## 异常与权限

- 无创建权限：按钮禁用并解释，不发送 API。
- 当前认证身份缺失：返回认证/权限错误，不创建 anonymous/system 计划。
- owner/department 与认证上下文不符：返回字段级错误，不回退为默认管理员，也不扩大为任意负责人转派。
- 网络超时：保持表单和 idempotencyKey，可安全重试。
- 同 key 不同请求：409，保留表单并要求生成新 key 后显式重试。
- 来源引用重复/空白：创建前字段校验失败；来源持久化异常时整个事务回滚。

## 实施与测试设计

1. Contract RED：请求无 code；name/key 长度；BUSINESS_FIRST 缺 objective；ASSET_FIRST 缺来源；重复来源；owner 约束。
2. Service IT RED：同 key 同请求重放、同 key 异请求冲突、跨租户、两个并发请求、来源失败整体回滚、来源不重复。
3. Resource RED：服务端 actor、无 code 请求、聚合响应、Location/ETag/nextAction/replayed、稳定 400/409/403。
4. Liquibase RED：两个 nullable 列、租户幂等唯一约束、master include、无 drop/rename/旧 changeset 修改。
5. Frontend RED：创建类型无 code；key 生命周期；双模式条件字段；负责人只读；无权限不 POST；成功只消费后端 nextAction。
6. Recovery RED：指定 plan 直接 GET；404/403 不回退首条；无显式 Tab 时按 onboardingMode 定位业务范围/来源；deferred A/B 响应验证迟到 A 不覆盖 B。
7. 实现最小 DTO/API/UI 与纯 create-flow helper，运行定向测试、相邻 IT、Chrome 95 构建。
8. 浏览器验证连续点击、网络重试、刷新、返回、无权限与两种起点。
