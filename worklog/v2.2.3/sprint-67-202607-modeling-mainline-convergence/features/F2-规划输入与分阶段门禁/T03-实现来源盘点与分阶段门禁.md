# T03：实现来源盘点与分阶段门禁

**优先级**：P0
**状态**：DONE
**依赖**：F2-T02；候选确认阶段另依赖 F3-T01

## 目标与用户结果

来源盘点只回答“数据从哪里来”，模型门禁按表类型在需要时校验来源，不再要求来源先映射到业务对象或过程。

## 范围与不做

- 范围 A（先实施）：source binding、确认/排除、权限/版本解析、CURRENT/STALE/UNKNOWN、真实来源 Tab、移除 source-business mapping 基线前置。
- 范围 B（F3-T01 后实施）：无持久候选台账的模型候选预览/确认、概念设计例外、四类表分阶段来源规则。
- 不做：不复制数据源连接正文，不用表名自动确认业务事实。

## 输入契约

| 输入 | 来源 | 必填阶段 | 校验 |
|---|---|---|---|
| sourceType/sourceId/version | 连接、目录、文件、dbt | 资产起点创建时或实现前 | 引用可访问且版本存在 |
| confirmationStatus | 用户 | 基线确认 | CONFIRMED/EXCLUDED |
| exclusionReason | 用户 | EXCLUDED 时 | 非空、可审计 |
| conceptualDesignAllowed | policy | 仅 DIMENSION 草稿 | 不得绕过实现/发布来源门禁 |
| sourceRefs | ModelSpec | FACT 保存、其他类型实现前 | 无重复、层级和依赖有效 |

## 输出产物

- `SourceInventoryView`：响应体 version/etag/readiness/checkedAt 与服务端解析后的 bindings；
- WarehousePlan source bindings（bindingId 服务端生成，客户端不得伪造 resolvedVersion/freshness）；
- 来源清单的 CURRENT/STALE/UNKNOWN 状态与不泄露的修复动作；
- 按 modelType 计算的保存/实现/发布 blocker；
- 删除 `SourceBusinessMapping` 必经依赖的迁移计划。

## 详细设计

1. 新增 `GET/PUT /api/modeling/warehouse-plans/{planId}/baseline/sources` 聚合契约。响应体必须返回 version/etag；PUT 不相信客户端展示名、resolvedVersion、freshness 或权限结论。
2. 新来源由服务端生成 bindingId，按 `(sourceType,sourceId)` 幂等；EXCLUDED 必须有原因。保存和刷新时后端重新校验租户、权限、存在性和真实版本。
3. 基线确认要求所有入选来源 CONFIRMED 或 EXCLUDED，且至少一个 CONFIRMED + CURRENT；不再读取 `SourceBusinessMapping`，也不要求 domain/process 映射。
4. BUSINESS_FIRST 无来源时返回 `NOT_REQUIRED_YET`，不能显示“来源盘点完成”；只有 policy 明确允许时可登记概念 DIMENSION 草稿，一旦生成/实现仍需来源或 generationStrategy。
5. 来源失权、删除或 provider 失败分别投影为 UNKNOWN/STALE，保留稳定引用和修复入口；不得自动排除、自动换同名表或泄露名称/字段。
6. 来源解析通过窄 `SourceReferenceResolver` 端口接 Catalog/File/dbt/Connection 原主；不修改共享资产列表主契约，也不把 `lastSyncedAt` 伪装成 schema version。
7. 来源 Tab 抽为独立组件，加载真实 GET、用响应体 version 做 If-Match；409 保留草稿，成功后刷新来源、baseline、projection。
8. 阶段 B 在 F3-T01 后提供 preview/confirm：preview 按 `planId + source versions + inferenceVersion` 生成稳定 candidateId，不落候选表；confirm 重新读取来源并校验 candidateId，漂移返回 `MODEL_CANDIDATE_STALE`。
9. confirm 必须由用户确认 modelType、name/purpose；DIMENSION 确认 keys/generationStrategy，FACT 确认 grain/time semantics，SUMMARY/APPLICATION 确认 dependsOn/用途；多分类计划必须选择已确认 domainId。
10. confirm 使用 idempotencyKey 并调用 canonical objectless ModelSpec create。不得调用仍写 `LEGACY_READONLY` artifact 的旧 dbt import 持久化路径，也不得新增候选模型事实表。
11. FACT 保存至少一个 CURRENT sourceRef；SUMMARY/APPLICATION 以有效 dependsOn 为主；DIMENSION 可用 CURRENT 来源或 generationStrategy。业务活动仅 FACT 可选说明，不参与来源门禁。
12. 旧 source mapping 表/API 只保留兼容读取与后续 F5 冻结审计；本 Task 不 drop/rename 历史结构。

## 异常、权限与恢复

- 引用无权：只显示“不可访问来源”，不泄露名称/字段。
- 来源删除：保留引用和修复入口，不自动切换到同名表。
- 重复导入：按稳定 source ref 幂等去重。

## 实施与测试设计

1. A-Contract RED：确认/排除/原因、重复引用、CURRENT/STALE/UNKNOWN、BUSINESS_FIRST NOT_REQUIRED_YET、baseline 不读取 mapping。
2. A-Service/API RED：GET body version/etag、服务端 bindingId、If-Match、来源失权/删除/provider 失败、跨租户、不可伪造解析字段。
3. A-Frontend RED：真实 sources Tab、响应体版本、409 保留、失权通用显示、无业务对象/必填过程、Chrome 95。
4. B-Contract RED（F3-T01 后）：四类表三阶段来源门禁、preview 稳定、漂移失败、confirm 幂等、objectId/processId 不出现。
5. 回归 Catalog、File、dbt、Connection adapters；旧 mapping 可读但不参与 canonical baseline。

## 实施结果（2026-07-19）

- Phase A 已完成：真实来源 Tab、GET/PUT 版本契约、服务端 binding 身份/版本解析、失权脱敏、来源失效诊断与 409 草稿恢复、BUSINESS_FIRST 无来源延迟以及 canonical baseline 脱离 source-business mapping。
- Phase B 已完成：`model-candidates/preview|confirm` 只从 CONFIRMED + CURRENT + AVAILABLE 来源生成稳定 SHA-256 candidateId，不持久化候选台账；confirm 重新预览，漂移返回 `MODEL_CANDIDATE_STALE`，并由服务端重建 sourceRef 后只调用 canonical ModelSpec create。
- F3 三阶段门禁分别覆盖 DIMENSION、FACT、SUMMARY、APPLICATION 的来源或上游依赖规则；概念设计不再绕过 IMPLEMENTATION_READY/RELEASE_READY。
- 证据：`it/evidence/api/model-candidate-preview-confirm.txt`、`it/evidence/backend-contract/source-stage-gates.txt`。
