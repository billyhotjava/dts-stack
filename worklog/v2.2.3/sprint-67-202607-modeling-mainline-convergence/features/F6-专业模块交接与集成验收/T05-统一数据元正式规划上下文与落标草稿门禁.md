# T05：统一数据元正式规划上下文与落标草稿门禁

**优先级**：P0
**状态**：IN_PROGRESS
**依赖**：F2-T02、F4-T02、F4-T03、F4-T04、F6-T01

## 目标与用户结果

用户可以直接浏览和维护全局数据元、业务分类等专业目录；从模型字段或建设规划进入专业页面时，页面只保留经过白名单校验的 `planId/modelSpecId/revision/returnTo`。字段标准由当前 ModelSpec 保存稳定 ID 和版本，不再由数据元页生成一份与正式模型脱节的浏览器草稿。

## 问题来源

2026-07-21 人工测试发现：数据元页以旧 `sessionStorage` 数仓规划为整页门禁，因此即使业务分类目录已有多个业务域，仍显示“缺少数仓规划上下文”。同时，业务分类页会用时间戳生成 `warehouse-plan-*` 会话记录，使“全局业务分类”“正式 WarehousePlan 分类基线”和“浏览器规划草稿”成为三套互相矛盾的上下文。

业务分类存在只说明全局目录有可复用分类，不等于任何建设规划已经选择并确认该分类。原页面把这两个事实混为一谈，属于需求边界缺失，不只是提示文案错误。

## 决策与范围

1. 数据元和业务分类是全局 owner，可直接浏览；缺少 `planId` 不得阻断列表、搜索、详情和有权限的维护动作。
2. 某分类是否纳入建设范围、是否已确认、数仓分层策略，只由 canonical WarehousePlan 基线持有。
3. 正式字段落标只由模型详情“字段标准”页签保存，绑定稳定 `standardElementId/version`；数据元页不再创建 page-wide `standard-binding-draft`。
4. 删除 Elements/SubjectAreas 对 legacy `warehousePlanningContext` 的生产消费，以及后端失败时回退浏览器草稿的路径。
5. Elements → 标准包 → Elements → 模型字段/计划基线只传递白名单上下文；外站、跨模型、跨计划和带额外参数的 `returnTo` 必须拒绝。
6. 兼容 SQL 页可继续只读识别历史 `standardDraftId`，但新页面不得继续生产该上下文。

## 输出产物

- 全局数据元 owner 的无规划可用态、独立加载失败态和安全返回提示；
- 数据元与标准包往返的 canonical 上下文构造器；
- 模型字段 owner 打开数据元时传递真实 `planId`；
- 业务分类页移除会话规划、STG 会话配置和临时计划生成，返回正式规划基线；
- source-contract/纯函数测试、production build、Chrome 95 和真实 API 人工验收证据；
- 更新后的操作手册、页面矩阵、IT 索引和增量 Go/No-Go。

## 验证矩阵

| 场景 | 预期 |
|---|---|
| 菜单直接进入数据元 | 无规划红色阻断；列表、搜索、详情及有权维护可用 |
| 全局已有业务分类但无计划 | 分类目录正常；进入模型动作引导先创建/选择建设规划，不伪造 planId |
| 从计划管理业务分类 | 返回同一 `planId` 的 baseline/categories，不改变分类正文所有权 |
| 从模型字段进入数据元 | 显示当前模型返回提示；维护/导入标准包后返回同一模型 standards 页签 |
| 恶意或漂移 returnTo | 外站、跨模型、跨计划、未知参数均被拒绝 |
| 数据元 API 失败 | 显示失败与重试，不伪装为“暂无数据元” |
| 字段落标 | 只在 ModelSpec 字段标准页签保存稳定 ID/版本，无 session 草稿 fallback |
| 伪造/错配 planId | 非 UUID、重复值、跨计划 returnTo 和路径穿越均清空上下文并返回规划台账 |
| Chrome 95 / 390px | 按钮可换行、提示和返回动作可见，无横向溢出 |
