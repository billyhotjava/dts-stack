# Sprint-11 安全 Review 记录

**范围**：SQL IDE 重构涉及的查询执行、结果导出、二次查询、跨设备 Tab 恢复与审计补点。

**结论**：未发现阻塞 Sprint-11 GA 的高危安全缺口；上线依赖的主要控制点已经具备，但仍需在运行期继续监控导出频控与二次查询隔离。

## 已确认控制项

1. **SQL 安全重写仍复用平台基线**
   - 继续以 `SecuritySqlRewriter` 作为查询改写与权限注入的统一入口。
   - 文档设计没有引入绕开该入口的“新执行通道”。

2. **原始 SQL 与重写后 SQL 均进入审计**
   - 满足“谁执行了什么”和“系统最终下发了什么”两层追踪。
   - 对导出、分页、复制、二次查询、EXPLAIN 等动作点都要求审计补齐。

3. **导出能力受频控约束**
   - 文档明确要求按用户做导出频控，避免大结果集被无限次批量拉取。

4. **二次查询隔离有显式边界**
   - 结果集即临时视图的设计要求按用户隔离。
   - DuckDB 仅作为受控的结果再利用层，不承担跨用户共享语义。

5. **回滚路径明确**
   - 通过 Feature Flag 切回旧页面，不需要破坏式数据回滚。
   - 这降低了发现安全/稳定性问题后的处置成本。

## 运行期重点观测

1. **导出频控命中率**
   - 观察是否存在单用户短时间高频导出未被拦截的情况。

2. **二次查询临时视图隔离**
   - 重点验证跨用户、跨会话不会读到彼此的结果快照。

3. **审计完整性**
   - 对“执行、导出、复制、二次查询、EXPLAIN”抽样核对审计落表与字段完整度。

## 残余风险

1. **DuckDB JNI 与临时视图隔离的组合风险**
   - 功能上可行，但仍需靠灰度和压测验证稳定性与清理策略。

2. **大结果集导出对资源的压力**
   - 已有频控与流式导出设计，但仍需结合容量与并发实测持续观察。

## 结论口径

Sprint-11 可以按既定范围关闭；后续若出现安全相关问题，优先通过 Feature Flag 回滚并保留审计样本做复盘。
