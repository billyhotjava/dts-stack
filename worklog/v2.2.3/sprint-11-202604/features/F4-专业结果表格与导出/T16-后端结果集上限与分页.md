# T16: 后端结果集上限提升 + 分页接口改造

**优先级**: P0
**状态**: READY
**依赖**: F1

## 目标

把现有 5000 行硬限制提升到 100k，同时保持现有 JSONB 存储方式对老接口的兼容。分页接口走新的 `/api/sql/v2/*`，老接口 `/api/sql/result-page/{id}` 不动。

## 技术设计

### 当前实现问题

- `SqlExecutionService` 执行时 `stmt.setMaxRows(5000)`，结果全量 `List<Map>` → 序列化为 JSONB 存 `ResultSet.previewColumns`
- 超过 5000 行无法展示
- JSONB 单行若存 100k 行可能达几十 MB，单行读写慢

### 改造方案

**两级存储**：
- `query_execution.preview_json`（保留）：头 5000 行 JSONB，供兼容展示
- `query_execution_chunk`（新增表）：分块存储完整结果
  ```sql
  CREATE TABLE query_execution_chunk (
      execution_id UUID NOT NULL,
      chunk_index  INT NOT NULL,
      rows_json    JSONB NOT NULL,            -- 每块 2000 行
      row_start    BIGINT NOT NULL,
      row_end      BIGINT NOT NULL,
      PRIMARY KEY (execution_id, chunk_index)
  );
  CREATE INDEX idx_qec_exec ON query_execution_chunk(execution_id);
  ```

**JDBC 流式写入**：
- `stmt.setFetchSize(2000)` + `resultSet.next()` 循环
- 每 2000 行写一个 chunk，不加载全量到 JVM
- 100k 行硬上限，超过标记 `truncated=true` 并记日志

**新分页接口**：

| 方法 | 路径 | 功能 |
|---|---|---|
| `GET` | `/api/sql/v2/executions/{id}/page?page=&size=` | 按页拉取，size 上限 500 |
| `GET` | `/api/sql/v2/executions/{id}/stream?from=&to=` | 流式范围拉取（导出用） |
| `GET` | `/api/sql/v2/executions/{id}/meta` | 元信息（总行数、列 schema、状态） |

### 清理策略

- `query_execution_chunk` 按 `created_at` 30 天后清理（新增定时任务）
- 也可以在结果不再被任何 Tab 引用时立即清理（通过 `last_execution_id` 反查）

## 影响范围

- 新增表 `query_execution_chunk` + Liquibase
- `SqlExecutionService` 写入逻辑改造（只改内部实现，对外 API 不变）
- 新增 3 个 `/api/sql/v2/executions/{id}/*` 端点
- 新增定时任务 `QueryExecutionChunkCleaner`
