# MDM 现场同步失败排障指南

适用现象：现场同步失败，怀疑配置不生效或外部 JSON 文件解析异常。优先检查已落盘文件与同批次日志，再检查配置和网络。

审查日期：2026-09-09。源码基线：`980010339591e96e62c2e344fc6891c2a4af3803`。本指南基于静态代码及配置审查；尚未获得现场原始文件、日志、镜像版本，以下风险不能直接认定为现场根因。仓库目录实际拼写为 `docs/intergration/mdm`。

## 1 先定位失败阶段

正式服务链路：发起上游 POST 请求 → 院方回调 `/api/mdm/receive` → 读取 UTF-8 文件 → 尝试解析 JSON → 保存文件 → 提交异步任务 → 校验必填字段 → 同步组织 → 导入人员 → 推送 Keycloak 组织树。

**HTTP 200、握手成功、文件已保存都不等于导入成功。** 正式服务异步处理，响应中的记录数和导入数不是最终结果。Demo 仅落盘校验，不入库。

| 现场证据 | 判断 | 下一步 |
| --- | --- | --- |
| 没有 `mdm.pull.response`，有连接或上游错误 | 握手未完成 | 核对地址、路径、鉴权及上游返回 |
| 握手成功，没有 `mdm.callback.saved` | 回调未到、鉴权失败、仅准备通知，或落盘失败 | 查回调日志、请求类型及目录权限 |
| `mdm.callback.parse-object failed` | JSON 解码或语法解析失败 | 按第 3 节检查原始文件 |
| 已保存，`parsed ... users=0 depts=0` | 结构不受支持、空集合，或解析失败后被当作空数据 | 查顶层结构和此前解析告警 |
| `mdm.callback.validation partial invalidUsers=... invalidDepts=...` | 部分记录缺必填字段；这些记录被剔除，其余完整记录照常导入 | 按 `mdm.callback.user.skipped` / `mdm.callback.dept.skipped` 的序号定位，修正源数据；人员的剔除原因同时记入导入批次失败明细 |
| `mdm.callback.async.failed` | 异步阶段异常 | 保留完整异常栈，区分组织同步、数据库和人员导入问题 |
| `mdm.callback.import.users ... failed>0` | 人员部分导入失败 | 查看人员导入批次失败明细 |
| `mdm.callback.push-keycloak failed` | 组织树推送 Keycloak 失败 | 检查 Keycloak 配置和可用性，勿判定为 JSON 解析失败 |

## 2 保留现场证据

在实际部署目录执行。先查服务所属 Compose 项目和配置文件，不要从开发目录启动容器。以下 `<...>` 均须替换。日志与 JSON 可能含人员信息，只在现场保存，外发前脱敏。

```bash
docker ps -a --filter name=dts-admin --format 'table {{.ID}}\t{{.Names}}\t{{.Image}}\t{{.Status}}'
docker inspect <容器ID> --format '{{json .Config.Labels}}'
docker inspect <容器ID> --format 'image={{.Image}} workdir={{.Config.WorkingDir}}'
docker inspect <容器ID> --format '{{json .Mounts}}'
docker port <容器ID>
docker logs --since 30m --timestamps <容器ID> > /tmp/mdm-admin-incident.log 2>&1
rg -n -C 4 'mdm\.(pull|callback)|mdm upstream pull failed|Exception|Caused by' /tmp/mdm-admin-incident.log
```

日志默认文件为容器 `/logs/dts-admin/mdm-gateway.log`，标准 Compose 对应宿主 `./logs/dts-admin/mdm-gateway.log`。若控制台没有 MDM 记录，应按实际挂载和配置读专用日志，不能据此判定未收到请求。

按 `mdm.callback.saved file=...` 找到宿主机挂载中的原始文件；默认 `/data/mdm` 对应部署目录 `./data/mdm`。在现场证据目录保存只读副本并记录 SHA-256、大小、接收时间与日志，不覆盖原件，不重复触发全量同步取证。

注意：文件名可能来自 `desp.sendTime` 或首个人员的 `updateTime`；同一天相同派生文件名会被 `TRUNCATE_EXISTING` 覆盖。重复推送前先留存原件，文件名不保证每批唯一。

## 3 检查外部 JSON

### 3.1 文件编码和语法

在有 Python 3 的现场机器执行以下只读检查，不输出人员字段值。将路径换成保存的原始文件；不需要联网安装依赖。

```bash
python3 - /现场证据/失败原始文件.json <<'PYJSON'
import sys, json, hashlib
from pathlib import Path
raw = Path(sys.argv[1]).read_bytes()
print('bytes=', len(raw), 'sha256=', hashlib.sha256(raw).hexdigest())
print('utf8_bom=', raw.startswith(b'\xef\xbb\xbf'))
try:
    text = raw.decode('utf-8')
except UnicodeDecodeError as e:
    print('UTF8_ERROR byte_offset=', e.start)
    raise SystemExit(1)
try:
    obj = json.loads(text)
except json.JSONDecodeError as e:
    print('JSON_ERROR=', e.msg, 'line=', e.lineno, 'column=', e.colno)
    raise SystemExit(2)
print('top_type=', type(obj).__name__)
if isinstance(obj, dict):
    print('top_keys=', list(obj))

def inspect_group(names, required, top_array=False):
    if isinstance(obj, list) and top_array:
        key, value = '<top_array_as_users>', obj
    elif isinstance(obj, dict):
        key = next((k for k in names if obj.get(k) is not None), None)
        value = obj.get(key) if key is not None else None
    else:
        key, value = None, None
    print('group=', names[0], 'selected_key=', key,
          'type=', type(value).__name__,
          'items=', len(value) if isinstance(value, list) else 0)
    if not isinstance(value, list):
        return
    invalid = [i for i, row in enumerate(value, 1) if not isinstance(row, dict)]
    missing = [(i, [k for k in required if row.get(k) is None or
                   not str(row[k]).strip()])
               for i, row in enumerate(value, 1) if isinstance(row, dict)]
    missing = [(i, keys) for i, keys in missing if keys]
    print('non_object_rows=', len(invalid), 'first20=', invalid[:20])
    print('missing_rows=', len(missing), 'first20=', missing[:20])

# 如现场 required.users/depts 已调整，同步替换以下字段列表。
inspect_group(['users', 'user'], ['userCode', 'userName', 'deptCode'], True)
inspect_group(['depts', 'orgId', 'orgIds', 'orgs', 'orgIt'], ['deptCode', 'deptName'])
PYJSON
```

该脚本是严格 JSON 与结构预检，不替代 Java/Jackson 运行验收。重点检查空文件、UTF-16/GBK、UTF-8 BOM、HTML 错误页、转义后的 JSON 字符串、尾逗号、注释、多段 JSON、`---` 分隔内容。正式服务不会执行 Mock 的多文档合并逻辑。编码或语法修正应由源端完成，保留修正前后证据。

### 3.2 当前正式服务支持的结构

推荐单个 JSON 对象，集合内每条记录是对象：

```json
{
  "users": [{"userCode": "U001", "userName": "联调人员", "deptCode": "D001", "status": "1"}],
  "depts": [{"deptCode": "D001", "deptName": "联调部门", "parentCode": "90", "status": "1"}]
}
```

此例仅说明结构，不能直接向生产提交测试人员。组织父节点和业务编码须按现场数据约定确认。

- 人员按 `users`、`user` 顺序取第一个非 null 字段。
- 组织按 `depts`、`orgId`、`orgIds`、`orgs`、`orgIt` 顺序取第一个非 null 字段。
- **空数组也会优先命中**：`users: []` 会遮住后面的有效 `user`；字段是字符串或对象也不会继续寻找下一个候选字段。
- 不会自动解包 `data`、`result` 等外层对象，也不会对字符串内容进行第二次 JSON 解析。
- 顶层数组一律作为人员集合；组织数组即使带 `type=depts` 也不会变成组织集合。
- 数组内非对象元素被忽略；必填检查不等于完整字段类型校验。
- 默认人员必填 `userCode,userName,deptCode`，组织必填 `deptCode,deptName`。缺字段的记录逐条剔除：组织写 `mdm.callback.dept.skipped` 日志；人员写 `mdm.callback.user.skipped` 日志（仅前 20 条）并作为 FAILED 明细记入本次导入批次，原因含序号与缺失字段。其余完整记录照常导入，不会整批停止。仅修改 `required-fields` 不影响此处实际使用的 `required.users/depts`。
- 组织先于人员导入。组织同步异常可阻止随后人员导入；Keycloak 推送失败则有单独告警。

### 3.3 HTTP 接收格式

正式入口是 `POST /api/mdm/receive`，推荐 `multipart/form-data`：`dataType=full`，文件部件必须名为 `file`。发送工具应自动生成 multipart boundary。

代码虽声明接受 `application/json`，却没有 `@RequestBody` 或读取原始请求流，仅读取 `file`、请求参数 `payload/body`。因此 `curl -H 'Content-Type: application/json' -d @文件` 不能作为当前实现的有效导入方式，可能保存空文件并返回成功。

`sync-demand` 或 `sync_demand` 且没有负载时仅登记准备通知；Demo 对这两种 dataType 即使带文件也直接返回，不解析文件。正式服务带文件时会继续处理。

## 4 配置核查

### 4.1 确认运行程序

| 程序 | 配置前缀 | 默认端口 | 行为 |
| --- | --- | --- | --- |
| 正式 `dts-admin` | `dts.mdm.gateway` | 容器 8081，标准发布 38012 | 落盘并异步导入 |
| `mdmdemo` | `mdm.demo` | 18080 | 落盘校验，不入库 |
| `mdm-upstream-mock` | `mdm.mock` | 28080 | 模拟院方推送 |

Demo 的 `application.yml` 不能作为正式服务配置直接使用。`DTS_MDM_GATEWAY_*` 不是 Demo 的配置前缀。Demo 握手 `sysCode=BI9010` 等 JSON 字段及表单参数在 `MdmDemoService.handshake()` 内写死，修改 `registry.*` 不会改变这些请求值。

### 4.2 核对文件是否真正加载

正式 Compose 将宿主 `./config` 挂到 `/opt/dts/config`，通过 `SPRING_CONFIG_IMPORT` 导入 `/opt/dts/config/mdm/mdm-gateway.yml`；导入为 `optional`，文件缺失不一定阻止启动。

```bash
# 只显示 MDM 环境和配置加载入口，隐藏 token/secret 值；不要输出完整容器环境。
docker inspect <容器ID> --format '{{json .Config.Env}}' |
  python3 -c 'import json,sys; rows=json.load(sys.stdin); print("\n".join((s.split("=",1)[0]+"=<redacted>" if any(w in s.split("=",1)[0].upper() for w in ("TOKEN","SECRET","PASSWORD")) else s) for s in rows if s.startswith(("DTS_MDM_","SPRING_CONFIG_"))))'
docker exec <容器ID> sh -c 'test -r /opt/dts/config/mdm/mdm-gateway.yml && echo MDM_CONFIG_READABLE'
```

按容器 Compose 标签找到实际 `-p`、`-f`、环境文件组合，在部署目录使用同一组合执行 `docker compose ... config --quiet` 做语法核对，并在现场对照渲染后的 `dts-admin.environment` 与上述实际容器环境。渲染输出可能包含密钥，不要直接外发。

`.env` 供 Compose 插值，不代表所有变量自动进入容器。当前 `docker-compose-app.yml`、`docker-compose.legacy.yml` 未透传 `DTS_MDM_GATEWAY_UPSTREAM_TARGET_NODE_CODE`、`TARGET_DOMAIN_CODE`、`TARGET_SERVICE_ID`、`SOURCE_SERVICE_ID`、`APPROVAL`、`TITLE`、`DATA_TYPE`、`SECURITY_LEVEL`、`FILED_TYPE`、`VERSION`、`PUSH_MODE`（后续项均带相同 `DTS_MDM_GATEWAY_UPSTREAM_` 前缀）。只在 `.env` 新增这些键不足以覆盖文件占位符默认值；须核实实际容器环境或已加载 YAML 中的值。

环境变量占位符还可能覆盖操作者只修改的 YAML 默认值。修改环境后仅 `docker restart` 不会刷新容器创建时的环境；需通过原正式发布流程重建该服务容器，再核对环境与挂载。

### 4.3 高风险配置项

| 配置项 | 核对内容 |
| --- | --- |
| `upstream.base-url` + `pull-path` | 代码直接拼接；path 应有前导 `/`，不要重复路径。正式服务仅发 POST，不能把 GET `v1/users/` 或 `v1/depts/` 填成握手接口 |
| `localhost:28080` | 在容器中指容器自己；应使用容器可达的真实院方地址 |
| `callback.url` | 当前正式握手代码不自动发送此值，也不自动发送 callbackSecret。应核对院方实际登记地址；Mock 使用自己的 callback-url 或表单 callbackUrl |
| `registry.system-code` | 外部 YAML 使用 `sysCode` 别名，但 Java 默认 `systemCode=10XT`，setter 仅在 systemCode 为空时采纳 sysCode。不要只改 sysCode；优先规范键 system-code 或其明确环境变量，并查实际出站文件 |
| 两处 `dataType` | registry 中是文件 JSON 字段；`upstream.form-params.dataType` 是外部表单字段，独立配置。示例默认分别为 sync-demand 和 9000，必须按院方协议逐项确认 |
| `upstream.auth-token` | 代码自动添加 Bearer 前缀，配置中只填令牌本体 |
| `callback.auth-token` / `signature-header` | 回调在指定头中传匹配值，默认 X-Signature。正式服务未 trim 配置值，注意前后空格 |
| `callback.allowed-ips` | 属性存在，但当前 MDM Java 接收链路未见执行校验，不能依赖其作为来源限制，也不要据此推断回调被拦截 |
| `storage-path` / `log-path` | 使用容器内路径，核对持久化挂载、运行用户权限、磁盘空间；不要直接填写只在宿主存在的路径 |

页面组织全量同步入口还会把 registry 的 sync-demand 改为文件中的 full，并用秒级 sendTime；直接 `/handshake` 默认使用毫秒 sendTime。现场对账时记录具体触发入口，不能假设两种请求完全相同。

## 5 已确认的文档与实现差异

| 优先级 | 差异与影响 | 处理和验收 |
| --- | --- | --- |
| P1 | 旧发布文档使用 `/api/mdm/callback` 和原始 JSON，当前控制器只有 `/receive` 等入口 | 改用实际 multipart 接口；确认 saved 后再查导入结果 |
| P1 | 缺字段曾导致整批终止导入；已改为逐条剔除并记录（人员进批次失败明细，组织写日志），完整记录照常导入 | 修正源数据缺字段；核对批次成功数 + 失败数 = 文件人员数，失败明细原因与源数据一致 |

## 6 修复后验收与回滚

1. 保存旧配置、失败文件和日志，记录现场镜像 ID、交付版本、Compose 组合和修改项。
2. 只修改已被证据确认的配置或源数据格式。涉及代码修复须在开发目录提交并推送，再由 `/opt/prod/s10/deploy` 快进同步 SHA，走正式测试、构建和发布；不得容器内打补丁。
3. 源数据修正后，选择一批经现场确认可重放的数据，仅触发一次。重放可能更新组织、人员和 Keycloak，不使用本文示例向生产造数据。
4. 核对 `saved` 文件大小与摘要，确认 `parsed` 的人员和组织数符合该批预期，无解析和必填告警。
5. 核对组织 applied、人员 success/failed、导入批次失败明细及实际页面记录。抽查部门归属、人员状态和所需 Keycloak 结果；文件接收、数据库导入、页面验收分别记录。
6. 配置回退通过原 Compose/发布流程恢复旧配置和服务。**配置回退不会撤销已经导入的数据**；部分导入须按批次评估，不清空业务表重试。
