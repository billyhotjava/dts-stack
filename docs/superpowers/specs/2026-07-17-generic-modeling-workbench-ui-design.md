# 通用建模工作台与前端旅程收敛设计

> **状态：已废止（Superseded，2026-07-18）**
> 本文件保留通用内核和页面审计作为历史输入，但“关系建模/维度建模/dbt 原生建模并列”与四阶段旅程不再是现行方案。现行架构以 [`2026-07-18-classic-warehouse-planning-golden-path-design.md`](./2026-07-18-classic-warehouse-planning-golden-path-design.md) 为准：经典数仓规划为默认主线，关系建模为可选设计视图，dbt 为高级实现工具。

**日期**：2026-07-17
**状态**：已废止，内容仅供迁移追溯
**范围**：DTS 数据建模前端信息架构、通用模型边界、现有页面与路由收敛
**首期实施边界**：优先使用现有 API 完成前端重排；缺少真实 API 的能力只记录为后续契约，不提供假按钮或假状态

## 1. 决策摘要

DTS 的建模主流程不再以 DataWorks/Kimball 的“业务过程 → 一致性维度 → 总线矩阵”为固定骨架，改为与具体建模方法无关的四阶段旅程：

```text
范围与来源 → 逻辑模型 → 实现与验证 → 发布与运行
```

通用模型内核以模型、实体、字段、粒度、关系、来源映射、版本和血缘为中心。维度建模、关系建模和 dbt 原生模型是该内核的不同使用方式，不是互相排斥的产品孤岛。

总线矩阵不再是独立菜单、强制步骤或发布门禁。底层模型关系才是来源真值；在维度建模模式下，系统以后可以从事实模型与维度模型的关系自动生成只读“分析关系概览”。

## 2. 问题与证据

### 2.1 当前主题域页面承担过多职责

`/governance/subjects` 同时承载：

- 主题域树和主题域 CRUD；
- 数仓分层方案和标准落标入口；
- 业务过程登记；
- 一致性维度登记和模板候选确认；
- 总线矩阵编辑；
- 资产、指标、质量规则和子域统计。

这些能力全部纵向排列，导致页面顶部按钮多、说明多，用户无法判断第一步。

### 2.2 当前语义工作区的顺序不等于业务完成状态

`SemanticWorkspaceFrame` 当前按“指标工作台 → 业务对象 → 指标管理 → 模型管理 → 发布审核”排列，并通过页面索引把前面步骤显示为已完成。页面位置不能证明业务事实已经完整，容易形成假进度。

### 2.3 现有产品已经有可复用的真实能力

首期不需要重新建设整套后台：

- `/governance/subjects` 已有主题域、业务活动、候选维度和分层上下文；
- `/modeling/semantic/objects` 已有业务对象、表映射和关系预览；
- `/modeling/semantic/models` 已有模型台账、粒度、分层、实现模式和发布门禁；
- `/modeling/dbt-files` 已有 dbt 文件编辑、运行和 manifest 状态；
- `/modeling/semantic/publish` 已有审核、dbt 发布、BI 注册和血缘注册；
- `/catalog/lineage/import` 已能导入 dbt manifest，但当前只登记血缘，不能宣称已反向登记逻辑模型。

问题主要是这些能力散落在不同页面、入口命名不一致、上下文容易丢失。

## 3. 设计目标

### 3.1 用户目标

- 新用户进入建模后能看到唯一明确的当前阶段和下一步。
- 治理维护人与建模人员是同一个人时，不需要切换工作身份或进入两套控制台。
- 熟手可以通过菜单和深链直接进入任一阶段，同时保持主题域、范围和模型上下文。
- 已有 Excel、ODS 和 dbt 的客户可以从现有资产开始，不被迫从空白本体开始登记。

### 3.2 产品目标

- DTS 可以支持关系建模、维度建模和 dbt 原生建模，不绑定某个行业或方法。
- 页面只展示真实可用能力；缺少后台契约时给出明确边界，不放置禁用占位按钮。
- 现有候选确认、模型台账和发布能力继续可用，不因前端重排丢失数据。

### 3.3 非目标

首期不实现：

- 可编辑 ER 画布的全新后台；
- 模型版本快照、差异和回滚后台；
- Excel 数据剖析与自动推断后台；
- dbt manifest 到业务对象、粒度和逻辑关系的完整反向登记；
- Data Vault 等新增建模方法。

这些能力进入后续架构契约，但首期页面不得伪装为已经具备。

## 4. 通用模型边界

### 4.1 通用核心概念

长期模型契约以以下对象为中心：

| 概念 | 回答的问题 |
|---|---|
| ModelSpec | 这是什么模型，属于哪个范围和分层 |
| ModelEntity | 模型里有哪些逻辑实体或逻辑表 |
| ModelField | 每个实体包含哪些字段及其业务含义 |
| GrainDeclaration | 一行数据代表什么 |
| ModelRelationship | 实体、事实、维度或父子对象如何关联 |
| SourceMapping | 来源表/字段如何映射到逻辑实体/字段 |
| ModelVersion | 当前编辑、审核和发布的是哪个版本 |
| LineageReference | 模型与 ODS、dbt、下游数据集之间的血缘 |

### 4.2 建模方法扩展

| 建模方法 | 通用核心上的扩展 |
|---|---|
| 关系建模 | 实体、主外键、基数、ER 关系 |
| 维度建模 | 事实、维度、角色维度、事实类型、可选分析关系概览 |
| dbt 原生 | SQL 节点、`ref/source`、测试、manifest 和实现所有权 |

建模方法只影响编辑器和校验规则，不改变顶层四阶段旅程。

### 4.3 总线矩阵的定位

- 不作为通用核心对象。
- 不作为客户必须填写的表单。
- 不成为发布条件。
- 现有矩阵数据和 API 首期保留兼容，避免破坏既有客户数据和维度推荐。
- 通用关系契约具备后，可将现有矩阵迁移为维度建模关系，再由关系自动投影只读概览。
- 客户界面不再使用“总线矩阵”作为一级标题；可选视图使用“分析关系概览”，帮助文字说明“维度建模中也称总线矩阵”。

## 5. 信息架构

### 5.1 顶层入口

数据建模菜单收敛为：

1. **建模工作台**：默认入口，恢复上次主题域、建模范围和阶段。
2. **模型台账**：跨范围查找模型、状态、分层和实现模式。
3. **高级 dbt**：面向需要直接维护 SQL、宏和运行参数的熟手。
4. **运行记录**：查看构建、发布和失败证据。

主题域、标准和参考数据仍属于治理能力，但建模工作台的“范围与来源”阶段提供上下文入口，用户不需要先理解组织边界再寻找建模入口。

### 5.2 四阶段工作台

```text
1 范围与来源
  选择主题域，并从已登记的数据资产或现有模型进入；确认本次建模范围

2 逻辑模型
  定义实体/逻辑表、字段、业务键、粒度、关系和来源映射

3 实现与验证
  选择设计器生成或 dbt 原生实现；生成、预览、测试并查看门禁

4 发布与运行
  审核、发布 dbt、注册 BI/血缘并查看运行证据
```

阶段导航是导航器，不按当前页面索引伪造完成状态。完成状态只根据真实数据和 API 结果推导。

### 5.3 页面与现有能力映射

| 阶段 | 首期复用页面/能力 | 后续增强 |
|---|---|---|
| 范围与来源 | 主题域、分层上下文、现有业务范围、模型/资产入口 | Excel 剖析、ODS/dbt 反向登记、来源覆盖诊断 |
| 逻辑模型 | 业务对象、表映射、关系预览、粒度登记 | 可编辑 ER、字段字典、关系基数、版本草稿 |
| 实现与验证 | 模型台账、模型预览、制品生成、dbt 文件和发布门禁 | 统一编译诊断、模型差异 |
| 发布与运行 | 审核、dbt 发布、BI 注册、血缘注册 | 版本发布、回滚、失败到模型的修复回路 |

## 6. `/governance/subjects` 页面重排

### 6.1 页面外壳

- 左侧保留主题域树，作为所有 Tab 的稳定上下文。
- 页面只保留一个标题区，不再使用“页面标题 + 统计卡 + 概念卡”多层顶部结构。
- 顶部只保留一个主动作：“新增主题域”；编辑和删除选中主题域进入“更多”菜单。

### 6.2 三个职责 Tab

#### 建模范围（默认）

- 展示当前主题域正在建设的模型范围和已有模型数量。
- 已有业务过程保留为“业务活动（维度建模辅助）”，不再假装所有建模方法都需要。
- 一致性维度和行业模板候选放入“维度建模辅助”抽屉或折叠区。
- 不展示可编辑总线矩阵。
- 主动作根据真实状态在“确认建模范围”“继续逻辑模型”之间选择一个。

#### 主题域信息

- 主题域名称、编码、负责人、说明和子域。
- 分层方案与标准落标入口。
- STG 等技术选项进入“高级设置”，默认不占据主要工作区。

#### 治理概览

- 数据集、指标、质量规则和发布状态等统计。
- 关联术语功能未完成前不显示禁用按钮。

### 6.3 全域视角

未选择主题域时，不展示所有建模卡片。只展示：

- 主题域列表；
- “选择一个主题域继续”；
- 没有主题域时的唯一动作“新增主题域”。

## 7. 逻辑模型工作台

### 7.1 首期布局

参考用户提供的模型管理界面，但只复用其有效模式：

- 顶部稳定展示当前模型、范围、方法、实现模式和状态；
- 中部展示逻辑结构或关系预览；
- 右侧抽屉/属性面板编辑当前实体、字段映射和粒度；
- 同一模型内用少量 Tab 分离结构、字段映射和关系预览。

首期没有真实版本 API，因此不显示“保存为新版本”或“版本记录”假 Tab。

### 7.2 首期 Tab

1. **模型结构**：逻辑实体/表和粒度。
2. **字段映射**：来源表字段到逻辑字段的映射。
3. **关系预览**：显示已保存关系，不承担从零绘制完整 ER 的承诺。

未来具备真实 API 后，再增加“关系设计”和“版本记录”。

### 7.3 建模方法

- 目标架构允许建模范围声明：关系建模、维度建模、dbt 原生。
- 关系建模优先展示实体和 ER 属性。
- 维度建模增加事实/维度角色、事实形态和时间角色。
- dbt 原生优先读取已登记模型、SQL、`ref/source` 和测试状态。
- 选择建模方法不会自动安装行业事实，也不会用示例数据填充客户业务。

首期不新增只保存在浏览器里的“建模方法”选择器。已有 `DBT_MANAGED` 模型识别为 dbt 原生，已有维度规划上下文识别为维度建模；其他存量模型保持“未声明”，只展示通用实体、字段、粒度和关系。待后台提供持久化方法字段后，再开放显式选择和方法专属校验。

## 8. URL 与上下文

### 8.1 统一上下文

前端使用通用 `ModelingJourneyContext`：

```ts
type ModelingJourneyContext = {
  domainId?: string;
  scopeId?: string;
  scopeKind?: "DOMAIN" | "PROCESS" | "OBJECT" | "MODEL";
  modelId?: string;
  method?: "RELATIONAL" | "DIMENSIONAL" | "DBT_NATIVE";
  stage?: "SCOPE" | "LOGICAL" | "IMPLEMENTATION" | "RELEASE";
};
```

URL 是跨页面上下文真值；session storage 只用于“恢复上次工作”，不能替代后台事实。

### 8.2 规范深链

```text
/modeling/workbench?domainId={id}&scopeId={id}&modelId={id}&stage=logical
```

首期允许工作台根据阶段跳转到现有真实页面，并把上下文参数完整透传。

### 8.3 旧入口兼容

- `active={domainId}` 兼容映射为 `domainId`。
- `focus=business-processes` 映射为范围阶段的维度建模辅助区。
- 既有 `processId` 继续透传给仍依赖该参数的后台接口，但前端通用上下文不把它当成所有方法的必填项。
- `/modeling/semantic/*`、`/studio/sql-modeling` 和 `/modeling/dbt-files` 保持可访问。

## 9. 操作层级与文案

### 9.1 每页一个主动作

| 页面/阶段 | 主动作示例 |
|---|---|
| 没有主题域 | 新增主题域 |
| 已选主题域但没有范围 | 确认建模范围 |
| 范围已确认 | 继续逻辑模型 |
| 逻辑模型未完整 | 完善当前模型 |
| 模型可生成 | 生成并验证 |
| 门禁通过 | 提交审核/发布 |

预览、删除、模板候选、高级 SQL、日志和制品进入次级按钮或“更多”菜单。

### 9.2 客户语言

- “粒度”第一次出现时写成“一行数据代表什么”，技术词放在括号或帮助中。
- “物化”改为“生成数据库表/视图”。
- “落标”在主流程中改为“关联字段标准”。
- “总线矩阵”不作为主界面术语。
- 不把分析结论、架构说明或大段教学文字放进工作区；帮助内容通过按需展开呈现。

## 10. 状态、失败与恢复

### 10.1 完成状态

- 范围完成：存在已保存的主题域/业务范围，或 URL 指向一个后台真实存在的模型；已有 dbt 模型可直接形成范围。只有后台已经支持建模方法字段时，方法才参与完成校验。
- 逻辑完成：至少一个实体/模型具备已保存粒度和来源映射；具体方法可追加校验。
- 实现完成：存在实现制品，且解析、测试和漂移门禁返回真实结果。
- 发布完成：后台返回发布、BI 注册和血缘注册结果；部分成功不得显示为全部完成。

### 10.2 错误处理

- 阶段数据加载失败时保留主题域和模型上下文，显示局部重试，不清空整个工作台。
- 表单保存失败保持输入和抽屉打开。
- 跳转到后续阶段但缺少前置事实时，显示一个返回修复动作，不堆叠多个 Alert。
- dbt 发布、BI 注册、血缘注册继续分别显示成功/失败，不合并为模糊状态。
- 权限不足时显示只读事实和简短原因；不展示点击后才报错的主按钮。

### 10.3 恢复

- URL 有完整上下文时优先使用 URL。
- URL 不完整时可读取最近一次工作快照并提示恢复。
- 恢复只恢复导航上下文，不在浏览器伪造已保存模型、关系或发布状态。

## 11. 现有候选确认能力的兼容

先前完成的手工业务过程、一致性维度、行业模板候选和确认状态继续有效：

- 模板内容仍然必须显式安装和确认；
- 未确认候选不能进入维度推荐；
- 手工登记内容继续作为客户事实；
- 这些能力迁入“维度建模辅助”，不再决定通用建模旅程；
- 现有总线矩阵关系暂不删除，避免破坏已保存数据和现有推荐逻辑。

## 12. 首期组件边界

为了结束单文件堆叠，首期前端拆分为：

- `ModelingJourneyFrame`：四阶段导航、上下文和真实完成状态；
- `ModelingJourneyContext`：URL 解析、旧参数兼容和跨页路由构建；
- `SubjectDomainShell`：主题域树和稳定上下文；
- `SubjectModelingScopeTab`：建模范围与下一步；
- `SubjectDomainInfoTab`：主题域、分层和标准；
- `SubjectGovernanceOverviewTab`：治理统计；
- `DimensionalModelingAssist`：业务活动、候选维度和模板，按需加载；
- `LogicalModelWorkspace`：模型结构、字段映射和关系预览。

数据加载和写操作保留在清晰 Hook/服务边界中，组件不复制 API 契约。

## 13. 首期实施顺序

1. 建立通用旅程上下文和旧路由兼容测试。
2. 重构 `SemanticWorkspaceFrame` 为真实四阶段导航，移除按索引伪造的完成状态和常驻概念卡。
3. 拆分 `SubjectAreasPage`，落地三 Tab 和单主动作。
4. 将业务活动、维度候选和模板迁入维度建模辅助区；从主页面移除可编辑矩阵。
5. 收敛模型台账行操作，把高级 dbt、生成、运行、审核按职责分层。
6. 用现有业务对象、表映射和关系预览形成首期逻辑模型工作台。
7. 更新菜单深链和旧入口重定向。
8. 运行定向测试、构建和 Chrome 95 浏览器回归。

首期结束后再评估后台工作：通用关系契约、Excel 剖析、dbt 反向登记、可编辑 ER 和版本管理。

## 14. 测试与验收

### 14.1 自动化测试

- URL 上下文解析、合并和旧参数兼容。
- 阶段完成状态只由真实数据推导。
- 主题域三 Tab 和默认 Tab。
- 矩阵不再出现在通用主流程、菜单和发布门禁文案中。
- 维度建模辅助仍能完成手工登记、模板安装和候选确认。
- 模型台账主次操作层级和上下文透传。
- 发布的部分成功和失败状态不回归。
- `pnpm build` 通过。

### 14.2 Chrome 95 回归

- 1366×768 下左侧主题域树、Tab、主动作和工作区首屏可见。
- 窄视口下阶段导航可横向滚动或紧凑换行，不遮挡主动作。
- 不使用 `:has()`、容器查询、`toSorted()` 等 Chrome 95 不兼容能力。
- 所有主入口、深链、抽屉、表单保存和返回路径完成浏览器 smoke。

### 14.3 产品验收

- 新用户进入“建模工作台”后知道当前阶段和唯一下一步。
- 用户不需要理解总线矩阵即可完成关系建模或 dbt 原生建模。
- 维度建模用户仍可使用候选维度和模板辅助，但它们不是全局前置门槛。
- 治理维护和建模在同一旅程内完成，不要求切换角色控制台。
- 现有主题域、候选确认、模型台账、dbt 和发布数据不丢失。
- 页面不新增无后端支撑的按钮、Tab、版本状态或自动推断结果。

## 15. 与既有规格的关系

本规格取代 `2026-07-17-domain-modeling-candidate-review-design.md` 中以下 UI 决策：

- “主题域页面固定三块：业务过程、一致性维度、总线矩阵”；
- “总线矩阵作为候选确认后的主要消费界面”；
- “本阶段不整体重构主题域页面布局”。

既有规格中已经实现的后台不变量继续有效：模板必须显式安装、候选必须确认、未确认候选不能进入现有推荐/矩阵、权限与审计保持不变。
