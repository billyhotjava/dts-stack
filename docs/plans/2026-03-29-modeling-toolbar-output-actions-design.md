# 逻辑建模工具栏与产出表回退补完设计

## 背景

当前 `dts-platform-webapp` 逻辑建模页面顶部工具栏中，`提交变更`、`同步模型`、`文档`、`回退` 四组能力对外已经可见，但实际状态并不一致：

- `提交变更` 已接通 Git commit 能力，但页面语义容易被误解为“提交流程”而非“提交到工作区 Git”
- `同步模型` 已能从 dbt manifest 同步资产，但验收语义尚未在 Sprint 中单独收口
- `文档` 仅触发 `dbt docs generate`，没有形成“生成后可浏览”的完整用户闭环
- `回退 -> 清空产出表 / 重建产出表` 在执行前都会先检查产出 relation，而这一步依赖 `dts-platform` 进程直连目标数仓 JDBC；现场当前直接报 `The connection attempt failed.`

这说明工具栏表面完整，但能力定义、错误语义和验收标准还没有真正补齐。

## 目标

把逻辑建模页工具栏中高频但仍未闭环的动作收口成一组可交付能力：

1. 明确 `提交变更`、`同步模型`、`文档` 的实际产品语义和完成标准
2. 将 `文档` 从“仅生成”升级为“生成 + 可访问/可解释结果”的闭环
3. 修复 `清空产出表 / 重建产出表` 在目标数仓连接检查阶段的失败语义，使其在现场环境下稳定可执行或至少明确可解释
4. 将自动化验证和人工验收项写入 `Sprint-24`

## 设计方案

### 方案 A：只修报错，不调整能力定义

只针对 `DbtOutputRelationService` 的连接失败做兼容，保留 `文档` 的当前行为不动。

优点：

- 改动最小
- 可以快速止血回退失败

缺点：

- `文档` 仍然是半成品
- `提交变更`/`同步模型`/`文档` 的验收语义仍不清晰
- Sprint 仍然缺一组明确的工具栏能力闭环

### 方案 B：推荐方案，补齐工具栏能力定义并修复回退链路

把本轮工作分成两层：

1. 语义层：明确四组动作各自的真实能力边界和用户提示
2. 技术层：修复产出表检查链路，并为文档动作补一条结果闭环

具体策略：

- `提交变更` 保持 Git commit 语义，但在 Sprint 和页面文案中按“提交当前工作区改动”验收
- `同步模型` 继续以 manifest 同步资产为准，补 Sprint 验收项
- `文档` 保留 `dbt docs generate`，同时增加“生成结果就绪”的反馈或入口，避免用户误以为只是空操作
- `回退` 的产出表检查链路从“直接 JDBC 打开目标数仓连接”改为更稳的策略：
  - 先校验 dbt 配置与目标数据源元数据
  - 对连接失败给出明确、可诊断的错误语义
  - 视实现复杂度决定是否引入轻量探活或更可控的连接工厂

优点：

- 能把当前现场问题和产品语义问题一起收口
- 和 `Sprint-24` 的“主工作流补完”目标一致
- 后续验收可以直接按 Feature 清单执行

缺点：

- 比单点修复稍大
- 需要同时动前端文案/反馈和后端回退链路

### 方案 C：把所有工具栏动作都改成统一作业中心模式

把 `提交变更`、`同步模型`、`文档`、`回退` 全部重构成后台任务，并统一结果页。

不推荐当前直接做，原因是范围已经超过“补完逻辑建模主工作流”的边界，会把简单动作一并拉进大重构。

## 推荐设计

采用方案 B，并把这轮工作并入 `Sprint-24` 新增 `F7-工具栏动作与产出表回退补完`。

### 能力定义

- `提交变更`
  - 定义为：将当前 dbt 工作区变更提交到本地 Git 仓库，并把受影响模型状态提升到 `COMMITTED`
  - 不承诺评审流、审批流、远端仓库推送

- `同步模型`
  - 定义为：根据 `target/manifest.json` 和 `run_results.json` 将 dbt 模型、字段、血缘同步到平台资产目录

- `文档`
  - 定义为：触发 `dbt docs generate` 并明确反馈“文档产物已生成/未生成”
  - 如果当前系统暂不提供在线浏览页，也要在 UI 上明确告知“当前仅生成文档产物，不提供内嵌浏览”

- `回退`
  - `清空产出表`：仅在识别到物理表时允许执行 `TRUNCATE`
  - `重建产出表`：不先删表，统一走 `dbt build --full-refresh`
  - 两者都必须先经过稳定、可解释的产出 relation 分析链路

### 产出表检查链路

当前根因在于 `DbtOutputRelationService.analyze()` 直接通过 `DriverManager.getConnection()` 打开目标数仓连接。

这轮建议的收口方向：

- 保留“执行前先分析 relation”的产品流程
- 但把错误语义从 JDBC 原始报错提升为平台侧可诊断消息
- 为连接失败区分至少三类情况：
  - 未配置目标数仓
  - 数据源元数据不完整
  - 网络/JDBC 连接失败

是否进一步改成 DataSource 池化或专用探活接口，留到实现阶段根据现有基础设施决定。

## 验证策略

自动化验证至少覆盖：

- 工具栏动作 helper / API 绑定未回退
- `DbtOutputRelationService` 在连接失败场景下返回稳定错误
- `EtlResource` 中 docs / sync / output rollback 相关接口回归

人工验收至少覆盖：

- `提交变更` 实际创建 commit，模型状态更新
- `同步模型` 有明确结果反馈
- `文档` 有清晰结果反馈
- `清空产出表` / `重建产出表` 在目标数仓可连时成功，在不可连时给出明确错误
